# ADR 0013：实时监听文件系统，增量反映到网格

- 状态：已接受
- 日期：2026-10-09
- 相关代码：`src/gallery/core/library/watcher.py`、`core/library/scanner.py`、
  `core/library/index.py`、`core/library/facade.py`、`ui/watch.py`、
  `ui/browser/model.py`、`ui/main_window.py`

## 背景

README 第一条主张是「打开文件夹即可浏览，磁盘上的变化立刻反映到界面」，而这一版
之前并没有兑现：新增照片不出现在网格里，删掉的照片仍然占着格子，外部工具改过 EXIF
之后元数据面板还显示旧值。用户实际做的事情（从访达里拖一批照片进来、用 Lightroom
改完参数再看）全都发生在 Gallery 之外，于是软件体感退化成了「导入式图库」。

`watchdog` 早就在依赖里躺着（`pyproject.toml`），源码里一次都没用过。

真正的问题不是「怎么拿到事件」，而是**拿到之后怎么不让界面乱**：

1. **访达拷贝 500 张 = 500 个 create 事件。** naively 一事件一处理，等于重扫 500 次。
2. **改名在事件流里长成「删除 + 新增」。** 它其实是一个动作，用户期待的是那一格原地
   换掉名字、选中还在 —— 而不是一格消失、另一格在别处冒出来。
3. **Gallery 自己写的操作也会产生事件。** 用户在这里改的名、删的照片，会被监听器原样
   报回来；不区分的话，同一次改名会被应用两遍。
4. **索引以绝对路径为主键。** 文件消失之后那一行不会自己走（`FacetIndex.prune` 写好了
   却从来没被调用过），于是同一张照片在索引里永远留着。
5. **扫描是流式的，可能正在半路。** 变化与扫描交错会插重、插到旧位置上。

## 决策

### 1. 事件先归一成四种语义，按路径合并，再交给界面

`core/library/watcher.py` 把 watchdog 的事件映射成 `ADDED` / `REMOVED` / `MOVED` /
`MODIFIED`，然后按路径合并：

- 新增之后又改 → 还是新增（界面反正要重新取一次缩略图）；
- 新增之后又删 → 什么都没有（拷贝中途取消、临时文件）；
- 同一层里「删了 A、又出现 B」→ 认成一次改名（访达改名就是这么报的）。

合并在 core 里做成**纯函数** `coalesce()`：不碰线程、不碰 Qt，可以直接单测。

### 2. 去抖在 core，线程搬运在 ui

core 侧攒够一段静默（`DEBOUNCE_MS`，400 ms）才交出一批；一直在变的话最多攒
`MAX_HOLD_MS`（3 s）也交一次，所以「慢慢拷一个大目录」会一批批地出现在界面上，
而不是等全部拷完才出现。

`ui/watch.py` 的 `WatchBridge` 只做一件事：把 core 的回调用**排队连接**搬回主线程
（与 `ui/tasks.py` 同一套规矩）。

### 3. 界面按当前这一层就地改，不重扫

- 新增 → `model.insert_entry`（同一目录内按扫描器同样的顺序插）；
- 删除 → `model.remove_paths`，并丢掉预览 / 元数据 / 缩略图这三份内存缓存；
- 同层改名 → `model.replace_entry`，那一格原地换掉；
- 内容变 → 重新 `describe_entry` 刷新 `(大小, 修改时间)`，旧的那份内存缓存作废。

正在看的那张照片如果被改了就重新载入，免得面板显示的还是旧值。

### 4. 自家写操作的回声要吸收掉

`_apply_rename` / `trash_selected` / `_apply_restore` 都往一个**带过期时间的路径集合**
里记一笔（`WATCH_ECHO_TTL`，2 秒），监听器随后报上来的同一批变化里带这些路径的直接跳过。
集合会过期，所以用户之后真的在访达里新建一个同名文件，不会被误吞。

模型侧另有一道防线：`insert_entry` 与 `append` 都按路径去重 —— 同一个路径在网格上
只可能有一行。

### 5. 索引行按路径删，而不是整库重扫

`FacetIndex.forget(paths)` 按路径删行（缓存性质，失败也不影响浏览），由
`Library.forget_paths` 暴露给界面。它替代了那个一直没接上的 `prune`：按当前层去重
整库会在相册模式下把别的相册的行一起删掉。

### 6. macOS 上不逐个目录挂监听

watchdog 在 macOS 上用 FSEvents，一个 `schedule(root, recursive=True)` 天然覆盖整棵子树
（watchdog 自己也注明「fsevents 默认就是递归的」）。逐个目录再挂一遍等于为每个相册
开一个 FSEvents 流，几百个就够呛。因此新目录只在**非 macOS** 平台上补挂
（inotify 不递归，这是必须做的）。

符号链接一律不跟：`is_visible_path` 先把路径解析成真实路径再判断是否在库内，链接出去的
目录自动落到「库外」被拒掉。

### 7. 扫描在途时只记脏标记

变化撞上一次还没跑完的流式扫描时，不去插行（会插到旧位置、会插重），只记一个
`_watch_dirty`；扫描收尾时重扫这一层一次。

## 后果

- 拖照片进窗口、外部改 EXIF、外部删除与改名都会立刻反映，用户不需要重开库。
- 监听是**纯读**的：只 stat、不写不删，对用户文件的磁盘风险为零（与红线 1 无关）。
- 一次外部批量操作最多触发一次模型改动；网格用 `beginInsertRows` / `beginRemoveRows`
  增量更新，不闪回占位框。
- 分组 / 排序开着时，新增照片要读一次 EXIF 才能决定落在哪个组（走的是既有的
  `_start_facet_read`，其余照片命中索引不重读）。
- 分组视图（已经进入某个组）里的变化同样即时：消失的照片立刻从组里摘掉；来了新照片
  则**整个库重新分组一次再回到同一个组** —— 组的成员是上一次算出来的快照，靠它自己
  长出新成员需要每次分组都维护一份反向索引，代价与出错面都不划算。
- 代价：多了一个后台线程（watchdog 的 emitter）与一个 `Timer`；关窗、切库时都要显式
  停掉，否则会向已销毁的窗口发信号。
- `watchdog` 从「死依赖」变成真依赖，`.app` 的体积不变。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| Qt 自带的 `QFileSystemWatcher` | 每个目录要单独 addPath，递归库就是几万次调用；且它在 Qt 线程上派发事件，与「core 不碰 Qt」直接冲突 |
| 每个事件立刻触发一次整层重扫 | 访达拷 500 张会重扫 500 次；且整屏闪回占位框正是各处注释里反复回避的事 |
| 直接 `prune(当前层的路径)` 清索引 | 相册模式下「当前层」不等于「整库」，会把别的相册的行一起删掉 |
| 监听器与界面之间直接调函数 | watchdog 在自己的线程上回调；不改线程就等于让界面在后台线程上被碰（`ui/tasks.py` 开头那三条规矩） |
| 靠事件流里的 delete+create 判断改名 | 跨目录移动也长这样；只认同层配对足够好，跨目录就老老实实当成删除 + 新增 |
| 监听器里就把缩略图 / 索引一起更新 | 监听器只报告「磁盘变了什么」，缓存与索引的更新规则属于 core 的其他模块，混在一起两边都难测 |
| 每次变化重扫整层而不是增量改行 | 会闪屏、会丢选中、会把分组卡片全部重建；`_reorder_level` 已经有「顺序没变就不动」的短路，够用了 |
