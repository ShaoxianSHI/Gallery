# ADR 0072：导入退回「文件」菜单，影片按来源分三个入口

- 状态：已接受
- 日期：2026-10-22
- 修改：[0063](0063-movie-events-and-import.md) 决策 7（顶层「导入」菜单），并恢复
  [0047](0047-import-shows-from-yanji.md) 决策 1 的「导入演出在「文件」里」
- 相关 ADR：0068（影片的三个来源）、0043（事件体系）
- 相关代码：`src/gallery/ui/main_window.py`、`src/gallery/ui/window/event_flow.py`、
  `src/gallery/ui/write_ops.py`、`src/gallery/ui/dialogs/movie_import.py`

## 背景

0063 把所有导入收进「视图」右边的顶层「导入」菜单，当时只有两条命令。0068 之后一次影片导入要
面对三个来源（JavDB、YouTube、Bilibili），而面板上的例子、说明与标题仍是三合一的一份：用户从
「导入影片…」进来，得先自己判断手上这一个是番号还是链接，提示里也只能把三种写法都塞进一段话。

同时，顶层「导入」只为两件事存在，而它与「文件」里已有的「打开」「最近打开」是同一族 ——
都是「把外面的东西拿进来」。

## 决策

### 1. 不再有顶层「导入」，两条子菜单放进「文件」

「文件」菜单在「最近打开」之后放两层：**「导入影片」** 与 **「导入演出」**。两层都常驻，
事件库用不上时一起置灰（判据仍是 `_events_usable` 一处）。

### 2. 「导入影片」按来源分三个入口

子菜单里是 **导入 Bilibili… / 导入 YouTube… / 导入 JavDB…**，三个入口打开同一张面板。
**只有面板上的标题、说明与输入例子跟着来源换**（`movie_import.SourceCopy`）：B 站给 BV 号与
视频地址，YouTube 给地址与 11 位 videoId，JavDB 给番号。

**入口不限制用户贴什么**：哪一行属于哪个来源仍由 `core.events.sources.parse_ref` 按内容认，
所以在一行里混着贴也照常导入。来源只决定「该给什么样的例子」，不当校验规则 —— 用户手上常常
是三种链接混在一段聊天记录里。

### 3. 「导入演出」暂时只有「从「演迹」导入…」一条，仍单独占一层

一个条目的子菜单看起来有点空，但下一批来源（别的演出记录应用、日历导出）会加在同一个位置；
摊平回「文件」顶层的话，加第二个来源时又要改一次菜单结构。条目名从「从「演迹」导入演出…」
缩成「从「演迹」导入…」，因为上一层已经写着「导入演出」。

## 后果

- 菜单栏回到三条：文件 / 编辑 / 视图；「导入影片」「导入演出」的父菜单是「文件」。
- 宿主耦合面少一个 `_import_movies_action`，多出 `_import_movies_menu` / `_import_shows_menu`
  与 `build_import_menus`；`tests/ui/window/test_host_contract.py` 随之更新。
- 面板构造多一个必填的 `source`，三个动作各自把来源交进 `write_ops.import_movies_from_dialog`。
- **数据安全的边界没变**：导入仍然只写 Gallery 自己的库与那几个封面新文件，仍然只由用户在界面
  上亲手触发。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 保留顶层「导入」 | 它只为两件事存在，而这两件都属于「把外面的东西拿进来」，与文件菜单同族 |
| 把三个来源平铺成三条顶层动作 | 文件菜单会多出三条几乎同名的命令，而它们只差一句提示 |
| 按入口限制输入来源 | 用户常把三种链接混着贴；按内容识别已经够准，限制只会把能导入的条目挡住 |
| 「导入演出」摊平回文件菜单 | 现在只有一条，但下一个来源会立刻让菜单再改一次结构 |
