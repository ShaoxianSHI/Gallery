# ADR 0104：配色也能删掉 —— 出口在编辑对话框里，至少留一套

- 状态：已接受（保存与「+」的上限由 0105 取代）
- 日期：2026-10-25
- 相关 ADR：0100（文案口径）、0101（自定义配色）、0103（配色是一个对象）
- 相关代码：`src/gallery/ui/dialogs/backdrop.py`

## 背景

0103 之后这一行只有两个动作：**双击编辑那一格的颜色**、**「+」新增一套**。于是候选只增不减 ——
点开生成对话框，八套预设永远在那儿，自己试出来的几套也永远在那儿。用户挑腻了某一套，界面
上没有第二个出口；删掉它只能关掉对话框重开（而新增的那几套一关就没了，等于换另一批；
它们从 0105 起会留下来）。

## 决策

### 1. 出口挂在编辑对话框上

删的是「一套配色」，而这个对象的入口已经在编辑对话框里（0103 决策 1），所以删除也放进去：
**左下角一个红字的「删除这套配色」**，与逐行那个「移除」（删一个颜色）分开摆，间距也分开。

放在左下角而不是跟在「保存」旁边，是因为它和「保存」不是一类结果：一个是把改动写回这一格，
一个是不让这一格存在。

### 2. 八套预设也删得

预设是 `PALETTES` 里的常量，界面从来不改它们 —— 删掉一格只是把它从这一轮对话框的那一行里
拿掉。**0105 之后删掉的也会写进清单**：重开不会自己回来，要它们回来走「恢复预设配色」。

### 3. 至少留一套

只剩一格时编辑对话框不再给出那个按钮：一张背景总得有一套颜色可算，没有「零套」这种状态。
这条与「一套配色至少两个颜色」是同一种约束，只是粒度不同。

### 4. 删掉正在用的那一套，落到原位那一套上

删的是第 3 格就用第 3 格现在的内容（原来第 4 格）；删的是末一格就用前一格。预览与配色名字
跟着换，不跳回第一套 —— 那样离用户刚才看的那一格太远。

### 5. 「+」的上限按这一行摆了几套算（已由 0105 决策 5 取代）

0103 的上限记的是「新增了几套」。删掉一格之后那条计数不会退，于是「+」还按不动 ——
而它按不动的理由是**那一行放不下**，与「预设占了几格」无关。当时改成看 `len(_palettes)`：
删掉任何一格都腾出位置。

0105 起改回「按「+」新增的几套算」：删掉一套预设不再腾出位置，否则「恢复预设配色」把八套
放回去时那一行会放不下。

### 6. 不弹确认，也不写任何文件（「不写任何文件」由 0105 取代）

删的只是这一次生成的候选：没动清单、没动缓存、没动用户照片，取消这个对话框就什么也没发生。
在这种动作上再问一遍「确定删除吗」只会让用户多按一次。

## 后果

- `BackdropPaletteDialog` 多两个出路：`can_delete` 说明要不要摆那个按钮，`deleted()` 说明
  用户按的是它。**新增配色时 `can_delete` 为假**（那时还没有「这一套」）。
- `BackdropGenerateDialog` 删掉一格之后**整行重造**（`_rebuild_chips`）：这一行每一格的回调
  都按序号取值，删掉一格后面那些序号全变了。重造比逐个改序号可靠。
- 旧的那几格要先 `setParent(None)` 再 `deleteLater()`：只 `deleteLater()` 的话它们到下一轮
  事件循环才消失，`findChildren` 还会找到它们，屏幕上也还留着。
- 丢掉的那一套如果真的已经存成过背景图，那张图不受影响 —— 配方里整份写着颜色，不靠配色名。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 右键或长按色块删除 | 不可发现；而色块上已经装了单击（选中）与双击（编辑），再加一手就藏在第三个手势里 |
| 在生成对话框里放一个「删除当前配色」 | 得先选中再按，位置上离配色那一行远，还容易被读成「删掉这张背景图」 |
| 干脆不显示预设 | 那是「隐藏」，得另存一份「哪几套不要」的偏好；而用户填的东西要能在缓存之外重建，为一个会话内的候选不值得 |
| 删完固定选第一套 | 会跳走；删第 6 格之后落到第 1 格，比落到原位那一格更让人意外 |
| 用一个结果码代替 `deleted()` | 调用方要记住「2 等于删除」，而 `deleted()` 与 `colours()` 分开问，读一眼就懂 |
