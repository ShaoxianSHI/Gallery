# ADR 0025：大图页的改名字段就在窗口标题栏里，标题文字改由我们自己画

- 状态：已接受
- 日期：2026-10-03
- 相关代码：`src/gallery/ui/title_bar.py`、`src/gallery/ui/rename_edit.py`、
  `src/gallery/ui/theme.py`、`src/gallery/ui/main_window.py`、`src/gallery/ui/write_ops.py`
- 相关：[ADR 0021](0021-viewer-context-menu.md)（大图页的右键菜单，决策 5 说「重命名…」先摆着置灰）、
  [ADR 0004](0004-rename-on-disk.md)（改名改磁盘上的真名）、[ADR 0005](0005-one-background.md)（整块窗口一块底色）、
  [ADR 0023](0023-menu-groups.md)（五张菜单共用四个组）

## 背景

[ADR 0021](0021-viewer-context-menu.md) 把大图页的菜单摆好了，但「重命名…」那一行是**灰的**：
它当时说清了原因 —— 「行内改名的输入框在网格里，大图页的改名字段还没有」。

用户的要求很具体，两句话：

1. 点开大图时，窗口标题栏里的文件夹名字换成**照片文件名**；
2. 重命名就在标题栏这一行里改，快捷键 `⌘R`。

这与网格那侧是**两处改名的入口**：网格里输入框浮在缩略图的名字上（ADR 0004 决策 6），
大图页里没有名字那一行，于是最自然的位置就是窗口顶部 —— 访达就是这样：在预览里改文件名，
改的就是标题栏那一行。

真正要定的是**标题栏那一行归谁画**。今天那一行是 macOS 自己画的：窗口设了
`NoTitleBarBackgroundHint` + `ExpandedClientAreaHint`（`ui.theme.unify_title_bar`），
底色已经换成我们自己的，文字却仍是系统按相册名画的。要在上面摆一个输入框，就有三件事要定：
标题文字还让不让系统画、那条输入框是哪来的、它与网格那个输入框是不是同一样东西。

## 决策

### 1. 标题文字**始终由我们自己画**，系统那份置空

标题栏那一行于是变成一个普通的子控件 `TitleBar`，贴在窗口顶边、正中显示当前这一层的名字：
网格页是相册名，大图页是正在看的那张照片的文件名。

**为什么不让系统继续画**：一旦要在这里编辑，就必须能把系统那份文字**收起来** ——
系统画的标题不可编辑、也不肯让位，两份文字叠在同一处是最难看的失败方式。而
「平时系统画、编辑时换控件」那条路要多一套切换逻辑，还会在进编辑与退出编辑时出现一次
可见的字体跳变（系统标题与 `QLineEdit` 的字号、字重、选区都不是一套）。
自己画之后，**显示与编辑共用同一个字体与同一个位置**，切换是无感的。

代价要写清楚：窗口标题（Mission Control、辅助功能读的那一份）从此是空的，窗口靠应用名识别。
这一版是 macOS 优先（`unify_title_bar` 早就只在 macOS 上动手），可接受。

### 2. 那一条只在 **macOS** 上存在

`unify_title_bar` 返回「标题栏是不是已经归我们了」（本 ADR 之前它没有返回值）。
只有归我们了才摆 `TitleBar` 并把系统标题置空；别的平台原样走 `setWindowTitle`，
与改动之前完全一样。理由与 `unify_title_bar` 相同：那一条高度来自**安全区**
（`WA_ContentsMarginsRespectsSafeArea`，实测顶出 28 点），别的平台上压根没有这一条 ——
硬摆一个上去只会盖住内容。

全屏时系统自己也不画标题栏，于是这一条跟着收起来（高度置 0、控件隐藏），
否则它会盖在照片上面。

### 3. 大图页的 `⌘R` 改的就是标题栏那一行

`_update_action_states` 里「重命名」的判据从「在网格页」放宽成「在网格页或大图页，
且指向的确实是一个磁盘上的文件」。这一条同时把 ADR 0021 决策 5 留下的那条灰行点亮 ——
菜单与接线都已在位，要改的只有这一个判据。

落点是同一个写操作入口：标题栏输入框提交后走 `WriteOpsMixin._on_rename_committed(row, text)`，
与网格那个输入框**同一条路**，因此记账、横幅、撤销、监听器回环一样都不少
（约束 1、ADR 0004 决策 4）。`ui/title_bar.py` 自己一个文件都不碰。

网格那一侧一个字没改：行内输入框仍在（ADR 0004 决策 6）。

### 4. 标题写什么只有一处说了算：`_refresh_title()`

**大图页是正在看的那张照片的文件名，其余是相册名。** 它由一个方法从
「现在在哪一页 + `_current_row` 那一格是谁」推出来，在翻图、退回网格、改名（含撤销）、
换库时各调一次。写成散落各处的 `set_text` 调用时，第一个漏掉的地方就是「改名之后标题还写着旧名」
—— 而那恰恰是用户盯着标题栏改的名字。

**改完名立刻刷新**：`_apply_rename` 末尾调一次，于是网格里改完名回到大图、`⌘Z` 撤回名字，
标题都跟着走。

### 5. 两个输入框是**同一个** `RenameEdit`

它原先住在 `ui/browser/rename_edit.py`，现在被网格与大图页两处共用，因此提到
`ui/rename_edit.py`（顶层判据见 ADR 0006：改了它会不会牵连另一个包 —— 会）。

同一套语义因此只有一份：回车提交、`Esc` 取消（并先把 `Esc` 从「上一级」那个 `QAction` 手里抢过来）、
点到别处也提交、照片只选中主干不选中扩展名、提交后自己收起来所以不会提交两遍。
**在标题栏里另写一个输入框，等于把这一整套语义抄第二遍**，抄的那份迟早和第一份不一样。

**外观也只有一份**：样式挂在 :class:`RenameEdit` 自己身上（`rename_edit_style`），不挂在
任何一个调用方身上。于是网格里那个输入框也跟着变成同一个圆角面，而两处的**高亮都取
调色板的 `Highlight` / `HighlightedText`**，与系统、与网格那一处（它本来就走系统样式）
永远一致。

这一条是改出来的，不是设计时就想到的：标题栏那一份最初自己硬编码了一个链接色当选区底色，
深色下那一片比正文还沉，「主干已经选中了」这件事反而看不出来；网格那一边又是另一副样子。
**凭手感调出来的高亮色迟早会与系统脱节**——写下来的必须是「取调色板的那一档」，不是
「挑一个看着顺眼的蓝」。

输入框摆在标题栏的哪儿是一个纯函数（`title_bar.editor_rect`）：以文字为中心、两边留白、
宽不过标题栏、窄窗口时不压到左上角那三个按钮上。摆位置的算术不掺任何 Qt 窗口状态，
于是它能被单独测。

### 6. 改名的过程中，别的会动文件的命令一起让开

网格那个输入框有焦点时 `⌘⌫` / `⌘⏎` / `⇧⌘N` 都会让开（见 `_update_action_states` 里的 `idle`），
标题栏这一个也一样：编辑期间键盘归输入框，`⌘⌫` 不该把正在改名的照片删掉。
于是 `idle` 现在是「两个输入框都没在编辑」。

## 后果

- ADR 0021 决策 5 那条灰着的「重命名…」亮了，那一行点下去改的是标题栏。
- 大图页与网格页**用的是同一个 `⌘R`**，作用对象分别是「正在看的那一张」与「选中的那一格」
  —— 与「移到废纸篫」在这一页上的处理方式一致（ADR 0021 决策 3、4）。
- 窗口标题（`setWindowTitle`）在 macOS 上恒为空串。**这不是漏写**：那一行现在由
  `TitleBar` 画，写进 `setWindowTitle` 只会多出一份系统画的字。想让窗口自我介绍一下，
  要写的是 `TitleBar.set_text`。
- 标题栏那一段仍然能拖窗口：不在编辑时 `TitleBar` 对鼠标是透明的，按下照旧落到
  `MainWindow.mousePressEvent` 去 `startSystemMove`（见那里）。
- 长文件名会被省略号截断（`ElideMiddle`，与系统标题一致），全文挂在提示气泡上。
- 测试：输入框的几何算术单独测（`test_title_bar.py`），窗口上的行为测「大图页标题显示文件名、
  `⌘R` 改的是标题栏、回车真的改名、撤销把名字与标题一起带回来、网格那侧一字未动」，
  另有一条锁定「两处的输入框是同一个外观」（改样式时最容易只改一处）。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 平时让系统画标题，只在编辑时换成输入框 | 进编辑与退出编辑各一次可见的字体跳变；显示与编辑是两套字形与两套度量 |
| 在大图页底部另开一行文件名并在那里改名 | 那是网格那一侧的答案（浮在格子下面）。用户要的就是标题栏这一行 |
| 用 `QInputDialog.getText` 弹一个改名对话框 | 弹窗把「就地改」换成了「打断」，而访达两处都是就地改 |
| 标题栏自己写一个输入框，与网格那个各写各的 | 同一套语义两份实现，抄的那份迟早和第一份不一样（见决策 5） |
| 在别的平台上照样摆这一条 | 那一段高度来自 macOS 的安全区，别处没有这一条，硬摆只会盖住内容（见决策 2） |
| 大图页的 `⌘R` 也走网格那个输入框 | 网格那一页不在前台，输入框浮在看不见的格子上；用户说的是「在标题栏这里改」 |
| 让 `⌘R` 在大图页上也去改**下一层**的照片 | 一次改一条、改的是正在看的那一张 —— 与删除、在访达中显示同一套判据（ADR 0021 决策 3） |
