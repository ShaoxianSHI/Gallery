# ADR 0074：按名称排序时中文走拼音字母序

- 状态：已接受
- 日期：2026-10-24
- 相关 ADR：[0009](0009-metadata-grouping-and-sorting.md)（分组 / 排序与「同值按文件名回退」）、
  [0049](0049-one-sort-direction-for-everything.md)（相册、组卡片、照片共用一个方向）
- 相关代码：`src/gallery/core/collation.py`、`src/gallery/core/metadata/facets.py`、
  `src/gallery/core/library/groups.py`、`src/gallery/core/library/calendar.py`、
  `src/gallery/core/library/scanner.py`、`src/gallery/ui/browser/model.py`、
  `src/gallery/ui/window/ordering.py`

## 背景

按文件名排序原先用的键是 `name.casefold()`，也就是逐码点比较。对拉丁字母没有问题，但汉字在
Unicode 里按部首与笔画排列，于是「张、李、王、赵」被排成「张、李、王、赵」而不是用户按拼音
翻名字时期待的「李、王、张、赵」。相册卡片、组卡片（相机 / 城市等文本字段）与同一时刻照片的
回退顺序也共用这把尺子，因此问题不止出现在「排序 → 文件名」那一项上。

## 决策

### 1. 排序键 = 不带声调的拼音 + 原名字

`core.collation.collation_key(text)` 把名字里的汉字转成拼音（`Style.NORMAL`，不带声调），
拉丁字母保持原样并 `casefold`。键里再接一个 NUL 与原名字，只为同音字（张 / 章）之间给出
稳定次序 —— 它不影响拼音本身的先后。

纯拉丁名字走 `casefold` 快路径，键与改动前逐字相同，既有排序行为不受影响。

### 2. 一个键，所有按名称比较的位置共用

范围包括：文件名排序字段、「同值回退到文件名」、相册卡片、组卡片（文本字段与无值组）、
日历同一时刻内的回退、扫描顺序、网格插行位置、相册路径序。**方向开关不参与**：升序仍按
拼音 A→Z，逆序仍是字面的 `reverse`，没值仍沉底（ADR 0009 / 0049 的约定一条都没有改）。

### 3. 依赖 `pypinyin`，不用系统 locale

系统排序（`locale.strxfrm`、CoreFoundation）在 macOS 上确实能给出拼音序，但它依赖进程级
`LC_COLLATE`、结果随系统数据与平台变化，测试也就只能在某一台机器上通过。`pypinyin` 是
纯 Python、MIT、约 840 KB、自带类型标注，**同一份名字在任何平台上得到同一个键**。词组表
还能处理「重庆」「长沙」「银行」这类多音字，这是逐字取第一读音做不到的。

## 后果

- 中文名字按拼音排，英文名字的既有顺序不变；中文与英文混排时按读音共用一套字母序
  （`apple` → 北京 → `banana` 这一类先后由读音决定）。
- 每个汉字名字第一次转换约 20 µs。整层按名称重排才需要算一遍（3 万张约 0.6 秒），模型与
  排序流程各自另有缓存 / 只算一次的处理；日常浏览不经过这里。
- 同音字仍可分先后（原名字做次键），但读音本身由词组表决定：多音字在离开词组时可能取到
  一个合理但未必符合用户想法的读音，排序只保证稳定，不承诺语义正确。
- 新增运行时依赖，随 Nuitka 一并打进 `Gallery.app`；`uv.lock` 锁定版本。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 继续用 Unicode 码点 | 汉字按部首 / 笔画排，正是这次要修的问题 |
| 用 macOS 的 `locale.strxfrm` / `CFStringCompare` | 进程级 locale 与平台数据决定结果，测试不可复现，跨平台还会变 |
| 按 GB2312 编码排 | 只有一级汉字按拼音，二级汉字按部首；生僻字与繁体字会掉出去 |
| 只把第一个字转拼音 | 首字相同的一批（「张…」）仍会退回码点或原名字，等于只修一半 |
| 自己维护一份拼音表 | 与 `pypinyin` 的词组与多音字数据重复，且没人跟着修 |
