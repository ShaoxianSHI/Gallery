# 0041「我在哪」是一条栈，不是五个字段

## 背景

「我在哪一层」原先由**五个独立的可变字段**表达：`_browse_mode`、`_current_dir`、`_group_view`、
`_drill_photos`（连着 `_from_calendar` / `_drill_label`）。而它们之间有一堆**没人声明的互斥
关系**（有分组就不该有日历那一格、有条件时浏览方式的含义会变、……），于是每加一条路径都要靠人
记住「这五个该一起清哪些」。

漏掉的后果不是报错，而是**看起来完全正确的死路**：

- **搜索结果里按 Esc 没反应**（用户报的两处之一）。整库检索的结果「接管当前层」，而它既不是
  文件夹也不是分组 —— `go_up` 那串 `if` 里压根没有它，于是 `_can_go_up()` 恒为 `False`。
  搜索后直接按 Esc 能退出是**巧合**：那时焦点还在搜索框里，走的是搜索框自己的 Esc，与 `go_up`
  无关。进一趟分组、焦点回到网格，那条路就断了。
- **在大图页上搜一下**：`_reload_level` 无条件把栈顶换成网格页，照片帧凭空消失，之后退不出来。

而 `go_up` 与 `_can_go_up` **各手写一遍那串 `if`，顺序就是层级深度** —— 顺序错了的症状是「退错
了一层」，不是任何一句能自检的东西。加一种新层级要记得同时改这两处。

## 决策

### 1. 栈：帧的四种 + 栈底决定浏览方式

```
根帧（三种，决定浏览方式）：全部照片 │ 相册视图 │ 日历页  +  逐层压栈
  全部照片： 根 → 搜索结果
  相册视图： 根 → 相册* → [分组] → [照片]      每层都可插「搜索结果」
  日历视图： 根 → 日历格 → [分组] → [照片]      每层都可插「搜索结果」
```

四种帧：`AlbumFrame`（相册，磁盘路径）、`GroupFrame`（分组，`facet`+`key`+已排好的照片）、
`CalendarFrame`（日历那一格，照片 + 名字）、`SearchFrame`（整库检索的结果），
外加大图页那一帧 `PhotoFrame`。

**`SearchFrame` 之上不再压 `GroupFrame`**（决策 2a）—— 搜索结果是平的。

**栈底那一帧就是浏览方式**，所以 `_browse_mode` 这个独立字段没有了。这比「浏览方式是独立字段」
更彻底：两条链（相册链 / 日历链）**互斥** —— 日历格下面不可能是相册，那不是靠 `if` 判掉的，
是类型上就排除了。原来那种「有分组又有日历格、浏览方式的含义变了」的状态构造不出来。

四条规则：

1. **`Esc` = 弹栈顶一帧**；只有根帧时无事可做。`_can_go_up` 归 `stack.can_pop()`（= `depth > 0`）。
2. **筛选不入栈，但随帧存**（见决策 3）。
3. **切换浏览方式 = 清栈换根**，落在各自底部、不带任何残留。
4. **会话只存栈底的浏览方式**（用户明确要的）：重开永远是那个浏览方式的底部，**位置一律不记**。

`replace_top` 与 `push` 分开：在大图页里翻上下一张**不是**往深里走（否则 `Esc` 要按几十次才退得
出去），所以照片帧是「换栈顶」。

### 2. 筛选不入栈，**但随帧存**

用户定的：筛选不改变「我在哪」，它是当前这一层的收窄。所以它不是一帧。

但它**属于某一帧、跟着那一帧走**：压入搜索结果那一帧时把「这一层筛选前的样子」一起存进去，
弹回来时恢复。反过来做（全局一份、进出层时自己记着恢复）就是「清栈时忘了清筛选」那一类 bug 的
来源 —— 而现在正有这个：`set_browse_mode` 里「只有整库检索要清」的 `if` 就是这类手工同步。

### 2a. 搜索结果**平铺**，不压分组帧

用户定的：「搜索结果上不要再压分组帧了，搜索结果只允许平铺所有搜到的照片。想要分组就用筛选。」

**这一条顺带把 `_group_view` 的判据从「从底往上找最后一个分组帧」简化成「看栈顶」** —— 那不是
顺手的事：搜索结果既然平铺，分组就只可能压在相册 / 日历格上。而早先那个版本里「在搜索结果里
`_group_view` 仍非空」，29 个调用点里任何一处把它读成「我在分组里」都会做出分组专用的行为
（典型的是写操作只作用在组内照片上 —— 那是红线 1 那条）。所以这条产品决定同时收掉了一整类判断
歧义。

「想要分组就用筛选」在机制上成立的原因也在这里：筛选不改变「这一层是什么」，所以分组照旧作用在
这一层上；而搜索是**换了一层**（ADR 0026 决策 7），换的那一层是平的。

### 3. 作用域切换 = 纯粹的 push / pop

漏斗切换按钮那两档（`SEARCH_SCOPE_LIBRARY` / `SEARCH_SCOPE_LEVEL`）：

- 筛选 → 搜索：**压**一帧 `SearchFrame`；
- 搜索 → 筛选：**弹**掉那帧。

不管栈顶原本是什么（用户：「除了搜索外的其他位置都能压入搜索」）。所以这条是纯粹的 push/pop，
不牵扯「当前帧是什么」。

### 4. 大图页上发起搜索 = 弹掉照片帧、压搜索帧

用户定的：「在大图页搜索就把大图弹出，再把搜索入栈，和在进大图之前的分组/相册页搜索行为一致。」
不选「压在照片帧之上」—— 那条路能让用户「看一眼照片再搜」，但搜索结果里只给路径、不给「第几张」，
于是退回去找不到刚才那张。

### 5. 会话只记浏览方式

`LibraryUIState.browse_mode` **已经存在**，一个字段都不用加。栈不进会话：位置一律不记，
重开落在那个浏览方式的底部。理由与决策 3 相同 —— 用户在一个浏览方式里待了很久，切走再切回来
并不见得想回到刚才那个位置（他这趟去另一个浏览方式干的事，多半与刚才那个位置无关）。

## 后果

- `_browse_mode`、`_current_dir`、`_group_view`、`_drill_photos`、`_from_calendar`、`_drill_label`
  六个字段全部消失，换成一条 `LevelStack`。其中 `_group_view` 原来有 **7 处**改写、
  `_editing_condition` 有 **8 处**，现在各归一处。
- `_is_library_search` / `_is_filtering` 收敛成「栈顶是不是搜索帧」—— 原先那个
  「条件非空且 scope 不是 level」的判据要同时看两个字段，而它是七个调用点各自问一次的地方。
- 搜索结果里 `Esc` 退得出去、大图页上搜索不再弹回网格 —— 这两条不用专门修，它们是模型的
  结果而不是补丁。

## 实施（三批，每批全绿且都合得进 main）

1. **只加不改**（已合）：引入 `LevelStack`（纯数据、不碰 Qt），六个字段不动，行为完全不变。
2. **切到新栈**（已合）：六个字段全部变成**只读属性**（从栈算出来），赋值的地方逐个改成压栈 /
   弹栈 / 换根。**读的地方一行都没改** —— 25 处 `_browse_mode`、29 处 `_group_view`、12 处
   `_current_dir` 照旧工作，而**写的地方从 11 处降到 0 处**（只有 `_push_frame` /
   `_pop_frame` / `_pop_to` / `_set_root` 四个方法）。
3. **搜索帧与筛选随帧**（已合）：搜索结果与整库检索入栈，判据收敛成「栈顶是不是搜索帧」。

### 第三批：`go_up` = 弹栈顶

`go_up` 不再是那串手写的 `if`，而是「弹掉栈顶一帧 → 按那一帧的种类收尾」（`_leave_frame`）。
`_can_go_up` 与它**用的是同一句话**（栈深 > 1）—— 原来两者各写一遍那串 `if`，顺序还是层级深度，
而顺序错了的症状是「退错了一层」，不是任何一句能自检的东西。

`_leave_frame` 是唯一需要「认得帧」的地方，四种分支：相册帧 → 露出底下那一层并把刚离开的目录
重新选中；分组帧 → 同上但选中原卡片；日历格帧 → 回日历页；搜索帧 → 清条件并恢复底下那一层
（`_leave_search_frame`）。

**修掉的两处真 bug**（都是用户报的）：

- **搜索结果里按 Esc 退不出去**。根因不是「Esc 在分组里不管用」，而是搜索结果压根不在
  `go_up` 那串 `if` 里 —— 它既不是文件夹也不是分组，于是 `_can_go_up()` 恒为 `False`。
  「搜索后直接按 Esc 能退出」是**巧合**（那时焦点还在搜索框里，走的是搜索框自己的 Esc）；
  进一趟分组、焦点回到网格，那条路就断了。
- **在大图页上搜一下会被人弹回网格页**，而照片帧凭空消失、之后退不出来。

途中撞到三件：

- **相册链是「一层一帧」**：从库根点进「旅行/2024」要压**两**帧。压一帧的话「旅行/2024」与
  「旅行/2025」在栈上长得一样，退一次就掉回库根（实测：进去是 1 行，退一次却变成根的 2 行）。
- **`go_up` 是「先弹再收尾」**，所以 `_leave_frame` 里**不能**走 `enter_folder`（那会再压一帧，
  栈越退越深）。同理 `enter_folder` 里必须**先弹搜索帧、再压相册链** —— 搜索帧压在相册链之上，
  压完再弹的话弹掉的是刚压上去的那一层。
- **`_leave_search_frame` 必须用传进来的那一帧，不能重新查栈**：`go_up` 弹完之后
  `self._search_frame` 已经是 `None` 了，重新查会以为「压根没有搜索帧」而直接返回 —— 症状是
  「Esc 一次之后条件仍在、结果仍是搜出来的那几张」。

若干条测试的断言也跟着改了：`window._current_dir == library` 这类断的是**字段**，而它是栈的投影、
**在库根时是 `None`**；真正被各处用的是 `_current_folder()`（口径 `_current_dir or root`）。

### 第二批里学到的三件事

**一、`_group_view` 是「栈顶那一帧」，而这靠的是「搜索结果平铺」那条产品决定**（决策 2a）。
我第一版的 mixin 注释写的是「分组可以压在搜索结果上」，于是判据写成了「从底往上找最后一个分组
帧」。那条判据在 29 个调用点眼里都成立，而「在搜索结果里 `_group_view` 仍非空」意味着某些地方
会做出分组专用行为（典型的是写操作只作用在组内照片上 —— 那是红线 1 那条）。搜索结果既然平铺，
这个歧义从**类型上**就没了。

**二、`_drill_photos` 的空元组与 `None` 不能合成一处**，而我第一版合了。空元组是「点开的那一格
一张照片也没有」，`None` 是「不在那一格」；合成一处之后「在那一格里但空的」会变成「不在那一格」，
于是 `_reload_level` 里那句「条件非空就清掉日历格」反而**不**清它。是守护测试逼出来的（它立刻
红了，红得对）。

**三、一条守护自己曾经是「永远为绿」的**：扫源码的那个 `parents[2]` 写错了（那是 `tests/` 而不是
仓库根），路径指向不存在的目录，于是 `rglob` 扫到**零个文件**而两条守护一路绿。这比没有守护更坏
（AGENTS.md 说的）。修法是断言那个目录存在，并把它写进注释。现在三条注入违规都确认会变红。

**另外一条：「建栈那处」的例外不能按行号钉**（实测四个写入口分布在 163…190，写死范围之后只是
挪一行就红），改成**按 AST 判「是不是在 `__init__` 里」** —— 「在 `__init__` 里」与行号无关。
### 补：换浏览方式之后界面上还挂着上一层的胶囊

用户报：「在相册视图区搜索，然后切到日历视图。这是日历视图的条件栏那里残留着之前的搜索条件，
但是既没有用来搜索，也没有用来筛选。这个条件在 UI 上应该去掉才对」「再切到全部照片也会残留，
只有切到相册时会清掉」。

**栈是对的、模型也是对的**（切到日历时栈已经是空的、条件已清），**只有界面没跟上** ——
所以这一条与栈无关，是「状态改了但没人去刷新那一行」。

真因有**两层**，都要修才算修完：

1. **`_update_breadcrumb` 是唯一摆胶囊的地方，而它只由 `_reload_level` 调。**
   `set_browse_mode` 三条分支里只有「切到相册」那条经过 `_reload_level`，另两条走
   `_enter_calendar` 与直接换页 —— 于是正好是「只有切到相册会清掉」。修法是在**三条分支之后**
   无条件调一次，不在分支里各补一句（加一条新分支就又漏一次）。
2. **`QWidget.hide()` 只是不画，控件还留在布局里。** `_update_breadcrumb` 的两条早退原本只
   `hide()`，而它们的对面 `set_path` 开头是 `_clear()` —— **「不摆」与「摆成空的」被当成了同一件
   事**。所以 `_hide_breadcrumb` 现在**藏起来并真的清空**（`BreadcrumbBar.clear_content`）。
   只修第 1 层的话，面包屑那一行仍然是空的但控件还在：切到日历那一格（另一条早退）时它们就回来了。

顺带修掉一个**隐性耦合**：`set_browse_mode` 原本是 `if self._is_library_search(): self._conditions.clear()`，
而那个判据**读的就是 `_conditions` 自己** —— 现在碰巧成立（清之前条件还在），可那是「靠顺序正确」
而不是「靠语义正确」。现在走 `_leave_search_frame` 那一个入口（它清条件、弹搜索帧、恢复底下那一层
自己的筛选、刷面包屑），而**搜索帧要在 `_set_root` 之前抓住**（换根之后它已经不在栈上了）。

守护两条，都注入违规确认过会红：

- `test_switching_the_view_leaves_no_condition_chip_behind`：**六个转移全断**。只断「相册→日历」
  的话「切到全部照片也残留」正好漏过去 —— 而它恰恰说明病根不在日历上，而在「谁负责刷新」。
  量的是**日历工具条与面包屑控件树**（不只是模型），否则第 2 层那个「hide 不清」量不出来。
- `test_only_one_place_ends_a_library_search`：「退出整库检索」只有一个入口。眼下自己 `clear()`
  常常看不出差别（换浏览方式时栈已被换根清空），但那是靠别人顺手清了栈才成立的。

**这一条本身的教训**：修它时那条新守护第一次写出来是**恒红**的 —— 相对路径用 `parents[3]` 算，
前缀带上了工作区目录名，于是放行清单全不匹配。与上一批那条「恒绿」（扫零个文件）是同一种失效，
**两个方向都得防**：断言扫的目录存在（防恒绿），且相对路径以 `src/gallery` 为基准而不是仓库根
（防恒绿也防恒红 —— 仓库根带着工作区名，`Gallery-stack/src/...` 与 `src/...` 差一截）。

### 补二：日历格内检索之后，搜索条件被当成了筛选条件

用户报：「在日历视图搜索之后，切到全部照片，之前的搜索条件被用来作为筛选条件了」。

**问题出在「格内检索」这个动作本身，不在换视图那一步** —— 搜完之后那一刻状态就已经是矛盾的了：

```
栈 = []            ← 空
条件 = ['相机：Canon']  作用域 = library
_is_library_search() = True   ← 说在检索
_search_frame = None           ← 可栈上没有搜索帧
```

真因在 :meth:`MainWindow._reload_level` 里那一句
``_pop_to(lambda stack: self._calendar_frame is None)``（「检索不是日历这一层的一部分，条件非空时
把那一格忘掉」）。`_pop_to` 是**从栈顶连续弹到判据成立**，而真实时序里这一句跑在
`_apply_conditions` **之后** —— 那里面 :meth:`_sync_search_frame` 刚把**搜索帧压在日历格之上**，
栈是 ``[CalendarFrame, SearchFrame]``。判据「栈上没有日历格」在第一步永远不成立，于是它把
**刚压上去的搜索帧一并弹掉**，而那一帧不会再被压回来。

后果是上面那副矛盾状态。接着换浏览方式时 :meth:`CalendarFlowMixin.set_browse_mode` 抓不到帧
（``leaving_search`` 是 ``None``）、清不掉条件 —— 条件就落在了新的一层上，而那一层并不是它筛出来的
那一层。**这就是「被用来作为筛选条件」**。

修法是**摘中间那一帧**（`LevelStack.without_frame` + `_drop_calendar_cell_frame`），两个方向各有一
条用例钉着，写反任何一边都红：

- 写成 `_pop_to`（现在的样子）→ 日历格摘掉了，**搜索帧跟着没了**（本条新用例红）。
- 写成「栈顶是日历格才摘」→ 真实时序里栈顶是搜索帧，那一句永不成立，**日历格摘不掉**，撤光条件
  之后按 Esc 退到用户这一趟没去过的那一格（`test_a_search_from_a_calendar_cell_forgets_that_cell`
  红）。

**这一条的教训是「从底往上扫」与「从顶往下弹」不能混用**：混起来时，「栈上有没有 X」这个判据在
``[X, …]`` 上成立、在 ``[…, X]`` 上不成立，而 `_pop_to` 用的是后一种（它只能往上弹）。所以
「忘掉某一层」这件事需要一个与位置无关的写法 —— 摘掉它，而不是弹到它不在为止。

`without_frame` 越界时**抛** `IndexError` 而不是静默返回：静默会被调用方读成「摘掉了」，而这个
方法是纯数据、没有别的地方会兜。
