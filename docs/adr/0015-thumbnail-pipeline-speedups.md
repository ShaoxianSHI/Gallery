# ADR 0015：缩略图流水线的三处提速

- 状态：已接受
- 日期：2026-10-02
- 相关代码：`src/gallery/core/media/thumbs.py`、`core/constants.py`、
  `ui/thumbs/pipeline.py`、`ui/imaging.py`、`ui/browser/model.py`、
  `ui/main_window.py`、`ui/tasks.py`

## 背景

缩略图是整个软件里唯一一处「对每一张照片都做一遍完整像素处理」的地方，因此它的成本
结构决定了整个网格的体感。实测（10 核 Mac，`长边 512`，冷热各取真实照片）：

| 阶段 | 1440×1080 真实照片 | 4032×3024 合成图 |
|---|---|---|
| JPEG `draft` + `load` | 5.0 ms | 15.1 ms |
| `exif_transpose` + `convert("RGBA")` + `tobytes()` | 0.2 ms | 0.2 ms |
| 编码成 JPEG（现状 q85 `optimize=True`） | 0.84 ms | 1.6 ms |
| 原子写（`mkstemp` + `fsync` + `replace`） | 0.2 ms | 0.2 ms |
| **冷取一张合计** | **≈6.3 ms** | **≈19.0 ms** |
| **命中磁盘缓存** | **0.46 ms** | — |

结论很清楚：**磁盘缓存本身已经很有效（快 14~40 倍），冷路径的大头是 libjpeg 解码，
而 `draft` 已经把它砍掉了一半左右（12MP 那档 34.6 → 19.0 ms，1440×1080 那档
9.9 → 5.0 ms）—— 那部分没有便宜可占了。**
所以提速不该再往「解码得多快」上使劲，而该去看**缓存之外的固定开销**：那些开销
与照片内容无关，却在每张照片上都要付一遍。

逐项量下来，这样的固定开销有三处。

### 一、淘汰扫描是 O(条目数)，而且每写 64 张就做一次

`_write_entry` 每写满 `_LIMIT_CHECK_INTERVAL`（64）张就调一次 `enforce_limit`，
而 `enforce_limit` 走 `_entries()` —— `iterdir()` 全目录加逐个 `stat`，再按 mtime 排序。
代价随缓存线性增长：

| 条目数（≈占用） | 一次扫描 | 摊到每张图 |
|---|---|---|
| 500（0.1 GB） | 19 ms | 0.29 ms |
| 2 000（0.26 GB） | 67 ms | 1.05 ms |
| 8 000（1.0 GB） | 277 ms | 4.34 ms |
| 16 000（2.1 GB，正好是默认上限） | 635 ms | **9.92 ms** |

也就是说：**缓存越大，每次写入摊到的淘汰开销越大，而且从不收敛**。在默认的 2 GiB
上限上，这 9.92 ms 是冷路径里除了解码之外最贵的一项 —— 比编码加落盘加起来还贵一倍。
这一项与照片内容无关，是纯记账开销。

### 二、编码的 `optimize=True` 是个亏本买卖

`optimize=True` 会额外跑一遍哈夫曼表搜索。对 512 px 的缩略图来说，它换来的体积
少得可怜，代价却是编码时间的两倍多（真实照片，40 张 512×384）：

| 编码参数 | 耗时 | 体积 | PSNR |
|---|---|---|---|
| q85 `optimize=True`（现状） | 0.843 ms | 34.4 KB | 37.66 dB |
| q85 `optimize=False` | 0.365 ms | 35.1 KB | 37.66 dB |
| **q82 `optimize=False`** | **0.355 ms** | **31.8 KB** | **36.95 dB** |
| q80 `optimize=False` | 0.353 ms | 30.0 KB | 36.55 dB |
| q78 `optimize=False` | 0.351 ms | 28.7 KB | 36.20 dB |

选 q82：编码快 **2.4 倍**，体积还小 **7.6%**，代价是 PSNR 掉 0.71 dB。缩略图最终
只显示成 ≤288 逻辑像素，512→288 的降采样本身还要再滤一遍高频，0.71 dB 落不到
眼睛里。**又快又小，双赢。**

> 顺带记一条走过的弯路，免得有人重查一遍：这一项最初的理由是「给 JPEG 加
> `subsampling="4:2:0"` 能省 39% 体积」，**那个理由是错的**。把写出来的 JPEG 的
> SOF0 段拆开看，现状（不传 `subsampling`）的采样因子**本来就是** `[0x22, 0x11, 0x11]`，
> 即 4:2:0 —— libjpeg 在这个质量下自己就选了色度减半。显式写上它与不写在字节上
> 完全一致。真正省时间的是关掉 `optimize`，真正省体积的是把 85 降到 82。

### 三、缩放做在界面线程上

`PhotoListModel.set_thumbnail` 里 `QPixmap.fromImage` 之后紧跟一次
`pixmap.scaled(icon_edge, SmoothTransformation)`，跑在界面线程。实测 0.077 ms
（512→176）/ 0.096 ms（512→288）。单张不大，但它和 `QListView` 的排版、绘制抢同一个
线程，而缩略图是一到货就触发的（worker 满速时每秒几十张）。

关键在于：这条路本来不需要走。`QImage.scaled` 是线程安全的，实测和 `QPixmap.scaled`
一样是 0.078 ms —— 也就是说缩放本身不贵，**贵在它坐在错误的线程上**。

顺带量到 `default_thread_count()` 在 10 核机上只给 4 个线程，而 Pillow 解码确实会释放
GIL（是真并行，不是假并行）：

| 线程数 | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| 张/秒 | 142 | 254 | 384 | **493** | 514 |

4→8 线程吞吐 +28%，1→4 线程更是 2.7 倍。`MAX_THREADS = 4` 这个封顶定得太早。

## 决策

### 1. 缓存总量改成增量记账，只在真的超限时才扫目录

`ThumbnailCache` 多一个 `_total_bytes`（`None` 表示「还没数过」）：

- 第一次需要判断是否超限时，照旧真的数一遍目录，顺手播种 `_total_bytes`；
- 之后每写成功一张就 `+= len(data)`，判断超限是 O(1) 的整数比较；
- 只有 `_total_bytes > max_bytes` 时才调 `enforce_limit()`，而它扫完目录后会用扫描
  结果**重置** `_total_bytes`，于是下一次超限判断又是从准数出发。

这样扫描频率从「每 64 张一次」变成「只在真的越过上限时」，也就是每写入几百 MB 才有
一次，而不是每写 64 张（按默认体积约 8 MB）就爆一次。

播种那一次是**正确性要求**，不是优化：进程重启后计数归零，不数一遍就会以为缓存是空的，
上限彻底失效、缓存无限涨。

`clear()` 之后把计数归零；`relocate()` 只是改名、字节数不变，计数不动。

### 2. 关掉 `optimize`，质量降到 82，色度抽样写死

`JPEG_QUALITY` 从 85 降到 82，`optimize=False`，并把 `subsampling="4:2:0"` **显式**
写出来（值不变，理由见背景里那条弯路记录 —— 写出来是为了让「用哪一档色度抽样」
成为代码里的一行承诺，而不是继承来的 libjpeg 默认行为；因此有 `JPEG_SUBSAMPLING`
这个常量可以单独改）。

PNG 那条路（只有带透明通道的源图才会走到）**保持原样**：PNG 的 `optimize=True` 对
平坦色块收益明显，而它是罕见路径，不值得为它单独做取舍。

因为编码结果变了，`THUMBNAIL_SPEC_VERSION` 从 1 递增到 2。旧条目自动不再命中，
被淘汰时按 mtime 从旧到新走，不会造成「缓存突然空一半」的错觉。

### 3. 缩放搬到工作线程，结果连同「缩到了几」一起交回

`ThumbnailPipeline.set_window` 多收一个 `target_edge`，在**提交任务时**就把它连同代次号
一起定格进闭包（不在完成时现读 —— 否则切档瞬间回来的图会带着旧边长却被当成新边长记账）。
工作线程调 `to_scaled_qimage`（把包装与缩放合成一步，省掉中间那张没人引用的
`QImage.copy()`），界面线程只剩下 `QPixmap.fromImage`。

`ready` 信号因此从 `(路径, 图像)` 变成 `(路径, 图像, 实际边长)`，`PhotoListModel.set_thumbnail`
按这个边长记账。**尺寸对不上的结果会自愈**：`needs_thumbnail` 比较的是记账的边长与当前
`_icon_edge`，不一致就重新取一次 —— 所以切档瞬间在途的任务不会把格子填歪。

`target_edge=0` 表示「不缩放」，此时模型退回自己按 `_icon_edge` 缩（保留这条兜底，
让 `set_thumbnail` 仍可被直接调用）。

### 4. 线程数上限从 4 抬到 16

`default_thread_count()` 的算法不变（仍是「给主线程留一个核」），只是把
`MAX_THREADS` 这个封顶从 4 抬到 16 —— 原来的 4 是在没有实测数据时定的，实测表明它
在 8 核以上的机器上白白闲置了一半核心。16 是绝对封顶，用来挡住核心数报得离谱的机器；
在常见的 8~12 核机器上实际取到的就是 `cpu_count() - 1`。

## 后果

同一套量法在改动前后各跑一遍（真实照片，40 张，`max_edge=512`，10 核 Mac）：

| 指标 | 改前 | 改后 |
|---|---|---|
| 冷取一张（解码 + 编码 + 落盘） | 6.48 ms | **5.98 ms**（↓7.7%） |
| 命中磁盘缓存 | 0.465 ms | 0.455 ms |
| 单条缩略图体积 | 34.4 KB | **31.8 KB**（↓7.6%） |
| 8 线程冷解码吞吐 | 480 张/秒 | **564 张/秒**（↑18%） |
| 淘汰摊薄到每张图（16000 条时） | 8.85 ms | **0.33 ms**（↓96%） |

几点补充：

- **最关键的是最后一行**：淘汰扫描本身一点没变快（566 → 531 ms，噪声范围内），
  变的是它出现的频率 —— 从「每写 64 张」变成「只在真的越过上限时」。按默认 2 GiB
  上限、每张 32 KB 算，一轮淘汰要等再写满 10%（约 1600 张）才会再扫一次。
- 编码本身快 2.4 倍（0.843 → 0.355 ms），冷路径里占约 7.7% —— 绝对值不大，
  但它是纯赚的（时间省了、体积还小了）；
- 缩略图的像素有一处可见的取舍（PSNR 37.66 → 36.95 dB）。在 ≤288 逻辑像素的显示
  尺度上看不出来；但如果哪天把档位推到接近 512 像素，这个取舍要重新量一遍；
- worker 线程数变多带来 +18% 吞吐。代价是并发解码时多占几份中间缓冲
  （每张几百 KB 量级），可以忽略；
- `THUMBNAIL_SPEC_VERSION` 递增导致**升级后第一次浏览会重建整批缩略图**。这是一次性的，
  之后按 mtime 渐进淘汰；
- `ready` 信号签名变了，`MainWindow._on_thumbnail_ready` 跟着改。只有 pipeline 与
  model 之间这一处耦合，不影响外部。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 保留 `optimize=True`、只降质量 | 省不下编码时间（q82 下仍有 0.82 ms，是本次的一半价值），体积只比 q82 `optimize=False` 小 2% |
| 用 `optimize=True` 换最小体积（q82，31.2 KB） | 体积确实最小，但编码时间与现状持平 —— 这次改动的一半就在那 0.5 ms 上 |
| 把 `enforce_limit` 的扫描放到后台线程 | 扫描是同步删除，搬到后台只是让「超限」这件事晚一点被处理，而写入路径已经被它挡住了；要根治就得让记账变成 O(1) |
| 用 SQLite / 一个索引文件记录缓存条目的体积 | 引入第二个需要与目录保持一致的状态源，而缓存本来就是「随时可以整个删掉」的东西；为它维护一致性正是红线 5 说的设计缺陷 |
| 把 `THUMBNAIL_SIZES` 的最大档提到 512 | 与本次改动无关；档位是观感选择，且 512 会让网格在普通笔记本上排不下几列 |
| 缩放仍在工作线程做、但只按设备像素比放大缓存那张图 | 那是另一件事（这里记为待办）：现在模型把 512 降到逻辑边长 288（网格自适应后最大可到 370），dpr=2 时 Qt 再放大回设备像素，先降后升白丢细节。改它会动到缓存长边与档位的关系，超出本次范围 |
| 直接读访达的 QuickLook 缩略图 | 能直接砍掉解码那 15 ms，但引入外部依赖且输出尺寸与格式不可控，与「优先标准库」相悖 |
| 更快地解码 | `draft` 已经把 12MP 那档从 34.6 ms 压到 19.0 ms、1440×1080 那档从 9.9 ms 压到 5.0 ms，剩下的就是 libjpeg 解码本身 |
| 质量再降到 78/75 换更小的缓存（28.7 / 26.6 KB） | 省的是磁盘不是时间，而 PSNR 掉到 36 dB 以下后 512 px 下的涂抹开始能被看出来；缓存小 10% 不值这个风险 |
