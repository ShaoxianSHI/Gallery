# ADR 0082：影片导入接上腾讯视频、爱奇艺、优酷、芒果 TV

- 状态：已接受
- 日期：2026-10-24
- 修改：[0068](0068-movie-sources.md) 决策 1 的来源值域（3 → 7）与决策 3 的识别顺序（多一档「面板选的来源」）
- 相关 ADR：0063（影片事件与导入）、0072（导入菜单按来源分）、0068（三个来源与共用传输）
- 相关代码：`src/gallery/core/events/{tencent,iqiyi,youku,mango}.py`、`src/gallery/core/events/sources.py`、
  `src/gallery/core/events/transport.py`、`src/gallery/core/events/kinds.py`、
  `src/gallery/core/library/facade.py`、`src/gallery/core/metadata/download.py`、
  `src/gallery/ui/dialogs/movie_import.py`、`src/gallery/ui/window/event_flow.py`
- 调研：`docs/调研报告-更多影片来源.md`（本机笔记，不入库）

## 背景

0068 之后，「影片」这一类能接的来源只有三个：JavDB（番号）、YouTube（videoId）、B 站（BV 号）。
用户手上有同样性质的东西还散在四个国内平台上，希望「粘一个链接或编号就变成一格格能点开的照片」
这件事对它们也成立。

三条约束与 0068 一样：**只依赖标准库**、**游客态**（不登录、不带 cookie）、**编号识别是纯函数**。
新增的一条是「不做 Netflix 与 Disney+」的结论，理由见最后。

## 决策

### 1. 四个来源共用一个「影片」事件，来源值用站方自己的写法

`来源` 的值域从三个变成七个：`JavDB` / `YouTube` / `Bilibili` / `腾讯视频` / `爱奇艺` / `优酷` /
`芒果TV`。中文站就用中文名 —— 0068 那条「用网站自己的名字」对它们同样成立，译成拼音反而认不出。

新增来源**不动库结构**：`source` 早就只是一格文字，`MOVIE_SOURCES` 是下拉的值域，不是 CHECK 约束。
于是没有迁移，旧库里那些 `Bilibili` 之类的值原样有效。

### 2. 裸编号的歧义靠「面板选的来源」消

这一轮最大的识别风险不是新来的四家，而是**它们与已有的三个撞形状**：

- 腾讯的 vid（`d4102jjf5cm`）与 YouTube 的 videoId **完全同形**（11 位字母数字）；
- 芒果的 vid 与 Netflix 的 title id 都是纯数字，现在还会被当成番号送去 JavDB 搜。

所以识别多了一档，顺序是：

1. **网址**——按域名认来源（网址比面板可靠：在「导入腾讯视频」里粘一条 B 站链接，认出来的还是 B 站）；
2. **面板选的来源**——只有这一行不是网址时才看它；
3. 原有的形状规则（`BV` / `av` → B 站，11 位 → YouTube）；
4. 其余 → 番号。

0072 那张面板本来就按来源分开（「导入爱奇艺影片…」），把这个来源一路传到 `plan_movie_import` 即可，
不必新增控件。**纯数字的芒果 vid 只能是「面板说了算」**，因为没有任何形状能把它与别家的数字编号分开。

### 3. 四家的抓取路径都不一样，但都不超过两个请求

| 来源 | 请求 | 拿到的东西 |
|---|---|---|
| 腾讯视频 | `vv.video.qq.com/getinfo`（JSON） | 标题、时长 |
| | `m.v.qq.com/play.html?vid=`（HTML） | 发布日期、标签 |
| | 封面由 vid 拼：`puui.qpic.cn/vpic_cover/<vid>/<vid>_hz.jpg/1280` | 1280×720 |
| 爱奇艺 | `m.iqiyi.com/v_<qipu>.html`（HTML） | 数字 tvid（地址里那串接口不认） |
| | `pcw-api.iqiyi.com/…/playervideoinfo?tvid=`（JSON） | 标题、封面、专辑、标签、日期、时长 |
| 优酷 | `v.youku.com/v_show/id_<id>.html`（HTML） | 页面里 `__INITIAL_DATA__` 那一段 JSON |
| 芒果 TV | `pcweb.api.mgtv.com/video/info?vid=`（JSON） | 标题、封面、时长、剧名 |

**腾讯那一支：封面由 vid 拼出来（实测五个 vid 全是真图），`qqvideo_ori` 那一套会给 120×120 的
占位图，不能用。** `getinfo` 是播放器接口，拿它取元数据属于用它的另一面 —— 站方收紧时最先动的
就是它，所以日期与标签另外走一次 HTML，那一段断了只让这两栏空着（与 YouTube 那一支同一取向）。

**爱奇艺那一支必须两步**：地址里的 qipu 编号（`v_19rqxr146g`）接口不认，而接口要的数字 tvid
拼不出网址。所以先读移动页里那一段 `__INITIAL_STATE__`，再拿 tvid 去问 JSON。那一段是服务端渲染
的 HTML —— 站方改版就断，断了这一家整个用不了，报错要说清是「页面没给出编号」。

**优酷与芒果都只要一个请求**，代价是它们更依赖站方自己那份数据结构（见决策 5、6）。

### 4. 抓不到的字段留空，不猜

四家都不给导演 / 演员 / 评分；**芒果 TV 连发布日期都没有**（接口不给，页面的 og 标签也只在正式
剧集上填）。那一栏就空着 —— 从别处猜一个日期比空着更坏（列表会按它排序、分组，猜错看不出来）。

「系列」这一栏：爱奇艺用专辑名（专辑名等于片名时留空，否则单片电影会变成一集一个组），
优酷用 `showName`，芒果用 `plName`，腾讯没有。

### 5. 优酷的风控页要单独说一句话

优酷在请求密了之后会返回一个 **200 的 JS 跳转页**（`_____tmd_____/punish`），正文里什么都没有。
它不是一个 HTTP 错误，传输层不会重试；认不出来就会被说成「没有这个视频」，而用户该做的是
过一会儿再试。所以这一条要单独判：认出那一页 → 说「这次的风控没放行，过一会儿再试，
也可以先在浏览器里打开它」；**不自动重试**（那一段通常要等几分钟，重试只是白等）。

### 6. 封面的后缀按字节认，不按地址猜

`_cover_name` 原先按地址结尾挑后缀。实测这一批里至少两处会错：腾讯的图床同一批里混着给
`image/png` 与 `image/jpeg`，而 Disney+ 那种地址连后缀都没有（格式写在查询串里）。
**写错后缀的那张封面解不出来，却不报错** —— 网格上只是一个灰块。

所以 `cover_bytes` 拿到字节之后先按魔数认（JPEG / PNG / GIF / WebP / AVIF），认不出才退回地址里
写的那个后缀。这一条不新增字段、不改 `MovieSource` 的协议。

**封面文件名仍是「编号 + 后缀」，不加来源前缀。** 跨来源同号时 `save_downloaded_file` 会挑一个
空名字（`IPX-660 2.jpg`），不会覆盖；而编号在库里本来就按（来源, 编号）分开，文件名只是个提示。

## 后果

- **新模块**四个：`core/events/tencent.py`、`iqiyi.py`、`youku.py`、`mango.py`。
- **`sources.py`**：`_URL_PARSERS` 与 `_TEXT_PARSERS` 两张表、`parse_ref(..., source=)`、`movie_url` 四支。
- **`transport.py`**：多一个 `ua` 字段（爱奇艺的 `m.` 站点按桌面 UA 只给一个空壳页）与 `MOBILE_UA`。
- **`download.py`** 多一个 `image_suffix`，`facade._cover_name` 先问它。
- **界面**：导入菜单从三项变成七项，对话框多四份文案；**中文来源名的那几行不加空格**
  （「导入腾讯视频…」而不是「导入 腾讯视频…」）。
- **抓取请求数**：一次导入的请求数从「每部一到三」变成「每部一到两个」，仍然受一秒限速约束。
  优酷那一家可能被风控挡住，报错会指向「过一会儿再试」。
- **`来源` 的下拉从三项变成七项**，它出现在事件编辑器与「按影片分组」的字段子菜单里（ADR 0065 自动带上）。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 接 Netflix / Disney+ | Netflix 游客看到的是注册引导页：没有结构化数据、没有盒封，只有渲染结果；Disney+ 能靠 og 标签抓，但国内常见网络根本连不上。两者都属于「装上也用不了」（ADR 0082 的调研有实测） |
| 用爱奇艺的数字 tvid 当编号 | 它拼不出网址（`v_<tvid>.html` 是通用壳页），于是「⌥ 点开」会打不开 |
| 用优酷开放平台的 API | 要 `client_id`，而能用的那几个都是别人的应用凭据 |
| 为每一家单独开一类事件 | 同一类东西、同一套界面（0068 决策 1 已经否过一次） |
| 裸编号也按形状认腾讯 / 芒果 | 腾讯的 vid 与 YouTube 的 videoId 同形，芒果与 Netflix 都是纯数字，认错就是把片子导到错的站 |
| 优酷被风控时自动重试 | 那一段要等几分钟，重试只是白等；说清「过一会儿再试」更有用 |
| 封面文件名加来源前缀 | 会让已有用户下次导入时看到一批新写法；而同号撞名的后果只是多一个「… 2.jpg」，不覆盖 |
