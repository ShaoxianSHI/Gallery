# ADR 0046：搜索候选里每类事件独有的字段一律带类型前缀

- 状态：已接受
- 日期：2026-10-07
- 相关 ADR：0043（事件体系）、0045（第二类事件「演出」，本条取代其决策 4）
- 相关代码：`src/gallery/core/library/search.py`

## 背景

ADR 0045 决策 4 让重名的字段才带类型前缀：与照片那族或先声明的那一类撞名时，后来那个叫
「演出·城市」「演出·评分」；不同名的就保留裸名（「目的地」「花费」「艺人」）。

加进第二类事件之后候选列表一下子长到近四十项，而「哪一项属于哪一类」只在那几个重名字段上
看得出来。其余字段要用户自己记：「花费」是旅行、「票价」是演出。两个类型里同名的列（都有
`rating`）分不分前缀还取决于**声明顺序** —— 哪天旅行不先声明了，前缀就换一边。

## 决策

### 1. 每类独有的字段一律显示成 `类型·字段`

`_event_fields` 不再看有没有撞名，一律 `f"{kind.label}·{field.label}"`：旅行那一组是
`旅行·目的地` / `旅行·花费` / `旅行·评分`，演出那一组是 `演出·艺人` / `演出·票价` /
`演出·评分`。两类里同名的字段因此天然分得开，也不再和声明顺序有关。

### 2. 公共那两条不带前缀

`事件类型` 与 `事件` 对每一类都成立，没有某一个类型可挂，保持裸名。

### 3. 匹配只认带前缀的名字

`match_field` 比较的是 `label` 与 `id`，于是 `#旅行·目的地` 选中旅行那栏，而 `#目的地` 认不出、
按既有的规则退回按文件名搜（ADR 0026）。**不给裸标签留别名**：两类都有「评分」，留别名就得按
位置挑一个，那正是本 ADR 要去掉的那种含糊。

### 4. 敲类型名就是筛出那一组

候选按 `label` 与 `id` 子串匹配，于是敲 `#旅行` 只剩旅行那一组、敲 `#演出` 只剩演出那一组。

## 后果

- 候选列表里带 `·` 的名字一眼能分组，用户按类型名一敲就能收窄。
- 「演出·演出类型」这类自带类型名的字段会读着略重复；为一致起见不特判，改字段名要动面板标签。
- 既有筛选条件不受影响：条件的身份是 `(field.id, 原文)`，`id` 本来就已经带类型。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 维持「只在重名时加前缀」 | 前缀的有无取决于声明顺序，加第三类事件时又会重排；不重名的字段也看不出属于哪一类 |
| 保留裸标签当匹配别名 | 两类同名的「评分」只能按位置挑一个，用户敲 `#评分` 得到的哪一类说不清 |
| 给候选列表加不可选的分组标题行 | 列表每一行都要参与上下键换选与补全，标题行会打乱行号与几何；前缀已经能分组 |
