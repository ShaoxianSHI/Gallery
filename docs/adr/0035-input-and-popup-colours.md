# ADR 0035：输入面与窗口同一个底色；三处浮层的高亮只从一处解析

- 状态：已接受
- 日期：2026-10-05
- 相关代码：`src/gallery/ui/theme.py`、`src/gallery/ui/rename_edit.py`、`src/gallery/ui/menu_style.py`
- 相关：[ADR 0005](0005-one-background.md)（整个窗口共用一块底色）、
  [ADR 0016](0016-menu-stylesheet.md)（菜单改用样式表）、
  [ADR 0024](0024-main-window-and-menus-split.md)（菜单怎么画是同一层的事，弹出列表与弹出菜单同一套视觉语言）、
  [ADR 0025](0025-rename-in-the-title-bar.md)、
  [ADR 0034](0034-external-app-launch.md)（标题条上那个两半的按钮）

## 背景

两处都是「看得见但说不出哪儿不对」，用户先看见、再点名：

1. **「在外部打开」那个药丸与搜索胶囊的底色，比外面深一档灰。** 原话：「是 qt 的原生？」
   —— 那个猜测是对的一半：那一档灰**恰好就是 macOS 系统窗口的颜色**（`#ffffff` 压到
   `#ebebeb`，而系统窗口是 `#ececec`），所以它看着不像这个软件画的。两块输入面于是从
   整扇窗里凸出来，而它们是整个标题条上仅有的两个「凸出来的东西」。
2. **那个下拉菜单与搜索框的候选列表、右键菜单「有一点割裂」。** 三处的样式表都由
   `menu_style` 从**各自的**调色板生成，生成逻辑是同一份 —— 割裂来自它们的调色板**不是同一份**。

第 2 条量出来的原因在 Qt 身上：**一份没写全的调色板会被 Qt 按控件类型各解析一档。**
本仓库下发的调色板只钉了铺底色的三个角色（`Window` / `Base` / `AlternateBase`），
其余留给 Qt 自己填。实测 macOS 上同一份应用调色板：

| 控件 | `Highlight`（浅色 / 深色） | `WindowText` |
|---|---|---|
| 普通 `QWidget` | `#a5cdff` / `#314f78` | `@0.847` |
| `QListView` / `QTreeWidget` | `#084ad9` / `#0640c6` | `@1.0` |
| `QMenu` | `#548fff` / `#3974e4` | `@0.847` |

于是**同一个高亮角色有三种值**：候选列表与网格一族是 `#084ad9`，两张菜单是 `#548fff`
—— 后者偏浅，在近白的浮层上看着发白。用户在同一扇窗里点开三处浮层，看到三种蓝。

**这条为什么一直没被测出来**：测试跑在 `offscreen` 上（`fusion` 样式），那里每一类控件
解析出来的都一样（都是 `#308cc6`）。`tests/ui/test_search_flow.py` 里本来就有一条
「候选列表与右键菜单四个角色都要一样」，它在 macOS 上也是绿的 —— **它量的不是这个**。

## 决策

### 1. 输入面与窗口**同一个底色**，边界靠那一圈边框

`rename_edit.field_background()` 直接返回主题底色，不再派生一档。三处输入面共用这个
函数（搜索胶囊、那个药丸、改名输入框），所以它们一起变。

- **读得出来靠边框**：三处本来就都有一圈 1 点边框（`text_at(0.28)`），实测与窗外明显不同。
- **悬停仍然有反馈**：那个药丸两半的悬停是拿底色 `lighter/darker` 出来的，
  现在它是那一块唯一的变化 —— 以前药丸自己有底色，那点变化几乎看不见。
- 深色下同样：原来那一档是**比底色亮**的（「另一个面」），两套主题下看下来是两种
  不同的东西，现在一套。

### 2. 浮层读的那几个角色由 `theme` **解析成一档**再钉死

新增 `theme.RESOLVED_ROLES`（`Highlight` / `HighlightedText` / `WindowText` / `Text` /
`PlaceholderText`）。`theme.pushed_palette()` 用一个**菜单控件**问 Qt 要这一档的值
（问一次，每次下发主题算一次，不是热路径），逐个颜色组写进下发的调色板，于是：

- `apply_theme`（已经在的那些控件）与 `push_palette`（之后才建的控件：候选列表、那个
  下拉菜单）共用同一个函数，两处各拼一遍的缝没有了；
- 三处浮层的高亮、正文色只可能是同一个值 —— 不是「我们算成一样」，是**没有第二档可拿**。

**统一到菜单那一档**（浅色 `#548fff` / 深色 `#3974e4`）：两档都摆给用户看过，
**用户选了偏浅的那个**（「那个蓝色浅一点，我更喜欢」）。

**代价是量得出来的**：浅色下白字压那一档是 **3.11:1**（WCAG 正文要 4.5:1；大字与
图形要 3:1）。候选列表里选中那一行的字因此偏淡，网格选中格子的铺底
（`Highlight` @35%）也跟着变浅。深色下是 4.38:1，没有这个问题。
**要换回去只有一处**：`_resolve_roles` 里问的那个控件（`QMenu` → `QListView`）。

### 3. 那一档要问得**准**：给探针的是空调色板，且真下发推迟一轮事件

前两条做完，颜色在**启动时**是对的，换一次外观就不对了 —— 而且症状分两半：
深色那一轮三处浮层**不统一**，切回浅色之后**和之前不一样了**（用户原话）。查到两处：

1. **应用调色板里那几档有时带着「已解析」标记。** 带着标记时 `setPalette` 就是
   「原样继承」，于是「问 Qt 要菜单那一档」问出来的等于**应用调色板自己那一档**：
   浅色下是那个发白的 `#a5cdff`（白字 1.64:1）、深色下是 `#314f78`。启动时那份调色板
   没有标记，所以**第一轮看起来完全正常** —— 这一点最要命，它把问题藏到第二次换外观。
   修法：给探针一份**只写了铺底色**的空调色板（`theme._probe_palette`），
   Qt 才会按「控件是哪种」重新解析一次。
2. **换外观的信号是在半路上发的。** macOS 一轮换外观里那个回调被叫好几次：头几次拿到的
   还是**旧的**调色板，后几次才是新的。原先就地下发，等于把半路的调色板钉进整棵控件树
   —— 于是上面那个「原样继承」正好发作。修法：只排一个 **0ms 定时器**，等这一批事件
   走完之后下发一次（`ThemeWatcher._on_system_theme_changed`）。

两条必须一起做：只做 1 会在级联里拿到「旧的但没带标记」那一档（深色那轮不跟着换），
只做 2 而拿应用调色板去问仍会被带标记的那一份污染。

## 后果

- **菜单里悬停/选中那一行完全没变**（本来就是那一档），变的是候选列表选中那一行与
  网格选中格的铺底 —— 它们向菜单看齐。用户点的正是菜单那一档。
- 搜索胶囊聚焦时那一圈边框、面包屑编辑态的边框、输入框里的选区，也都跟着换成这一档
  （它们读的都是 ``Highlight``）。
- **测试里量的是「钉没钉死」「问的有没有带答案」「是不是就地下发」**，而不是「是什么颜色」：
  换成直接比颜色，在 `offscreen`（`fusion`）上永远相等 —— 那里只有一种解析结果，
  「取哪一档」这件事在测试里**量不出来**，它是产品选择不是不变式。已验过在旧代码上变红的有：
  `test_the_pushed_palette_pins_the_popup_roles`（钉没钉死）、
  `test_the_probe_is_not_handed_an_already_answered_palette`（用 `resolveMask` 看有没有带答案）、
  `test_a_theme_change_is_applied_after_the_events_settle`（是不是就地下发）。
  另有一条 `test_coming_back_to_light_gives_the_first_light_again` 把「浅→深→浅要与第一轮
  逐项相同」写死 —— 它在 `offscreen` 上旧代码也是绿的（那里本来就没有半路状态），
  它挡的是「将来谁又让往返变成了有损的」。
- 代价：换外观时**推迟一轮事件**才下发（最多晚一帧），期间屏幕上还是上一套颜色；
  `theme` 每下发一次还要造一个一次性的 `QMenu` 探针（不显示、不进控件树）。
- **一处已知的「不对齐」**：候选列表那个控件的 `Highlight` 在换完之后会停在上一轮那一档
  —— 装样式表会让 Qt 重新 polish 一遍并重算它的调色板（`QMenu` 不受这个影响）。
  它整块是样式表在画、没有任何地方读它的调色板，所以看不出来；
  顺序不能换（样式表里写死的是 `rgba(...)`，必须从刚推下去的那份调色板生成）——
  理由写在 `ui.search_field.SearchField._apply_theme` 那里。

## 被否决的替代方案

- **统一到列表那一档**（`#084ad9` / `#0640c6`）：它确实是界面上别处的选中色
  （网格选中格、输入框选区），对比度也最好（7.0:1 / 8.2:1）—— 但用户看过之后选了偏浅的
  那一档，**偏深的那个在近白的浮层上显得重**。
- **高亮取应用调色板里的 `Highlight`（`#a5cdff` / `#314f78`）**：那才是「系统强调色」最
  正式的说法，但浅色下它是**一档很淡的蓝**，配 `HighlightedText`（白字）只有 1.64:1 ——
  选中那一行等于看不见。三种候选的白字对比度都量过：1.64 / 3.11 / 7.02。
- **取链接色 `Link`（`#3586ff`）**：好看，但它不是选区，语义不对；用户改了系统强调色时
  它也不会跟着变。
- **让每处浮层各自写死那几个颜色**：那就回到 ADR 0024 之前的样子（各派生一遍，
  早晚差一档，而那时没人说得清是哪一档）。
