# ADR 0010：第一次打开库就把地点解析一遍存进索引

- 状态：已接受
- 日期：2026-10-02
- 相关 ADR：0003（离线反查）、0009（分组与排序）、0011（地点语言规则）
- 相关代码：`src/gallery/core/library/facade.py`、`src/gallery/core/library/index.py`、
  `src/gallery/ui/main_window.py`

## 背景

按坐标反查出来的行政地点（国家 / 省州 / 城市）有两处消费者：**分组**（读 facet 索引里的
三列）与**元数据面板**（「位置」组里的「地点（推断）」）。两处此前各算各的，时机都不对：
分组那条只有用户手动选一次需要读 EXIF 的排序时才顺带反查并写库，面板那条自己下载数据、
自己加载城市表、自己算，结论只存内存 LRU。于是同一张照片，面板写着「中国 · 浙江省 · 杭州」，
分组却是「国家未知」—— 同一个功能的两半，还各有一份结论。而 `_needs_place` 只看「三列有没有空」，
所以「附近 300 公里没有城市」的行每次都会被重新反查一遍，永远问不出同一个答案。

## 决策

### 1. 打开库时算一遍，之后两处都只读索引

`Library.resolve_places()` 递归整个库，把还没有地点结论的照片读一遍 EXIF、反查坐标、
写回索引，首次扫描完成后在后台跑一遍（`MainWindow._maybe_start_place_pass`），一个库只跑一次。
之后分组照旧从索引读，**元数据面板先读索引**，命中就同步显示，连后台任务都不起。

### 2. 索引要记住「查过了」，而不只是「查到了什么」

`facets` 表加两列（`SCHEMA_VERSION` 2 → 3，旧表整表重建 —— 缓存没有迁移的价值）：

| 列 | 含义 |
|---|---|
| `place_ok` | 已经按坐标反查过一次。**查不到也是结论**，记住了就不必重算 |
| `place_km` | 坐标离最近城市多远。面板要靠它说清「这只是最近的城市」 |

`place_ok` 是要害：没有它，「附近没有城市」与「还没查过」分不开，每开一次库就要把整库重算一遍。

### 3. 「没查成」不算「查过了」

`PlaceResolver` 因此多了一个 `ready` 属性：`place_for` 返回 `None` 有两种含义 ——
数据齐了还查不到（结论，记下来），以及城市数据没下好 / 下载失败（**这次没查成，不记**）。
后者必须能区分，否则这些照片会被永久固定在「未知」上。

### 4. 回退路也要写回索引，但绝不写半行

打开时那一遍还没轮到、或后来才加进库的照片，面板仍会现场反查一次，走
`Library.resolve_photo_place`：用面板手里已经读到的坐标去查，**并进已有的那一行**。索引里
还没有这一行时**只返回结论、不写** —— 写半行会被当成「EXIF 已经读过了」，挡住以后那次完整读取。

### 5. 城市数据仍然按需下载

保持 ADR 0003 的行为：解析真正需要时才下 3.3 MB，横幅如实说明。打开库不会去下它 ——
用户什么都没点就联网下载东西不合适。

### 6. 空跑要静默，而且后台进度不许抢横幅

这一遍**每次打开都会起**（检查有没有漏网的照片），但绝大多数时候无事可做：所有行要么有结论、
要么没有坐标。真正干活与否由 `resolve_places` 的 `on_work` 说出来 —— **空跑时界面一个字都不报**。
先亮「正在解析照片的地点…」再在几十毫秒后收掉，用户没法分辨「又在干活」和「软件出毛病」。

两条配套的规矩：**记账用集合**（`_place_pass_roots`）而不是「上一个库」，否则同一会话里
A → B → A 切回 A 时会再起一遍空跑；**横幅归值班的用** —— 横幅是全局共享的，后台进度是最没有
资格占着它的那一个，所以只在横幅空着、或还停在自己那句话上时才写，收尾也只收自己那一句。

## 后果

- 打开一个大库后会多一次全库 EXIF 读取（几百到几万张，取决于库的大小），在后台、可取消、
  不阻塞浏览；缩略图流水线是独立的一摊。顺带的收益是这一遍把整库的 facet 都填上了，按年份、
  相机分组也变成立刻完成。第二次打开同一个库会走一遍目录、查一遍索引（不读 EXIF、不反查、
  不写库），界面完全无感。
- 本层正在读元数据时**先让着**那一遍（`MainWindow._maybe_start_place_pass`）：两者读的是同一批
  照片，同时跑等于把同一件事做两遍。
- 打开库不再「完全不碰 exiftool」。原先「按文件名排序不读 EXIF」承诺的是**切换排序字段**不读，
  这一点仍然成立（测试改成比增量）。`.gallery/index.db` 旧表会被丢掉重建一次，代价是一次全量重读。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 保持现状：等用户分组时再解析，面板自己算 | 两份结论必然漂；这是本次要修的缺陷本身 |
| 每个文件夹首次进入时解析 | 首次打开快，但按城市分组跨层时仍要等逐层累积齐，且「文件夹」是界面概念、索引是库级的 |
| 打开库时后台慢慢补（低优先级） | 与首屏缩略图争 IO，用户会看到照片一张张出；先做完这一遍更好解释 |
| 打开库时静默预取城市数据 | 用户什么都没点就联网下载 3.3 MB |
| 面板的结论也另存一张表 | 两个真相来源；面板与分组正是要统一到的那一处 |
