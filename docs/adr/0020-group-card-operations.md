# ADR 0020：分组卡片的右键菜单按「对组内这批照片操作」来做

- 状态：已接受
- 日期：2026-10-12
- 相关代码：`src/gallery/ui/window/menus.py`、`src/gallery/ui/main_window.py`
- 相关：[ADR 0014](0014-context-menu.md)（决策 4：分组卡片只留打开与复制分组条件）、[ADR 0019](0019-copy-move-to-album.md)（决策 5：两条「到相册」只给照片菜单）、[ADR 0008](0008-delete-to-trash.md)（界面上的删除）、[ADR 0004](0004-rename-on-disk.md)（约束 1）、[ADR 0009](0009-metadata-grouping-and-sorting.md)（分组是什么）

## 背景

ADR 0014 决策 4 把分组卡片的菜单收窄成「打开」与「复制分组条件」两条，理由是**分组不是磁盘上的东西**。这一条对**改名**与**删掉分组本身**成立至今（那两条仍然不出现），但它顺带把另一些命令也一并挡在了外面，而那些命令要动的并不是「分组这个卡片」，而是**卡片所代表的那批照片** —— 用户站在「按相机：Canon · 128 张」这张卡片前面想要的就是**把这 128 张整体拷走、复制到别的相册、或者删掉**，现状却是得先双击进去、⌘A、再出来右键。

## 决策

### 1. 选区里出现分组卡片，就把它摊平成组内照片

摊平发生在**一处**：`MainWindow._selected_paths()` 收拢的「选区在磁盘上的东西」，遇到 `GroupRef` 时取它的 `photos`。因此「在访达中显示 / 拷贝 / 拷贝路径 / 复制到相册 / 移动到相册 / 移到废纸篓」这六条**一次都不用改各自的实现** —— 它们拿到的仍然是一串路径，只是这串路径里现在可能来自一张分组卡片。按路径去重、保持网格顺序（同一张照片既被单独选中、又被它所在的组一起选中时只算一次，与 `core.library.groups.flatten_groups` 同一个取向）；混合选区照旧；而**「摊平」只发生在命令的对象上，不发生在选区上** —— 网格里那张卡片仍然是选中的卡片，用户看得见自己选了什么。

### 2. 菜单里多六条，仍没有的那几条

```
打开                      ↵
────────────────
在访达中显示               ⌘⏎
拷贝                       ⌘C
拷贝路径                   ⇧⌘C
复制到相册 ▸
移动到相册 ▸
────────────────
移到废纸篓                 ⌘⌫
────────────────
复制分组条件
```

`移动到相册` 之所以能**进**这张菜单（ADR 0019 决策 5 说的是「只给照片菜单」）：摊平之后它作用于照片，那条限制的目的 —— 不搬相册、一次只动照片 —— 照样成立，摊平出来的是 `photos`，不是 `photos` 所在的目录。**「移到废纸篓」前面单独隔一道**：它是这张菜单里唯一会动文件的一条，前面几条点哪一个都只是把东西**递出去**（访达、剪贴板、别的相册，原件都在原地）；照片菜单里它紧挨着上一条，是因为那里的位置本来就让给「粘贴」，不是因为两者同族。

**仍然不出现**：重命名（ADR 0004 一次只改一条，且分组没有名字可改）、粘贴（它作用的是**剪贴板**，「把剪贴板里的东西粘到这一组所在的相册」是另一件事，见 ADR 0018 决策 3）、显示元数据信息与复制元数据（面板讲的是**一张**照片，组里哪一张都没有理由被指定）。**文案一个字都不改** —— 菜单栏里那一批 `QAction` 只有一份文案，两处分头改必然漂移（ADR 0014 决策 1）；张数已经在卡片上写着（「128 张」），菜单里再写一遍是噪音。

### 3. 快捷键与右键菜单说同一句话

选中一张分组卡片时，⌘C / ⇧⌘C / ⌘⏎ / ⌘⌫ **不再置灰**，与菜单里的那几条作用在同一批照片上。这不是新逻辑：`QAction` 本来就是菜单栏与右键菜单共用的（ADR 0014 决策 1），`MainWindow._update_action_states` 是唯一的可用性判据，而这份判据的输入（选区摊平后的路径）刚刚变了。代价是 ⌘⌫ 现在能一次把整组推进废纸篓 —— 接受它的理由与既有口径一致：废纸篓本身就是那层保险，⌘Z 再是一层，访达也不弹确认框（ADR 0008 决策 3）；而如果菜单里能做、快捷键却置灰，用户会学到「同一件事按右键能删、按键盘不能」这种更难记的规则。

### 4. 整组进废纸篓之后，那张卡片自己消失

废纸篓这一条是唯一需要**改网格**的：分组卡片没有路径可摘，`PhotoListModel.remove_rows` 摘的是行不是路径。组里的照片**全部**被移走时，这一行本来就代表一个「这些照片」，一张不剩的组不该还摆在那儿，摘掉它；只被移走一部分则卡片留着，张数在**下一次列这一层**时更新（与今天在分组视图里删掉组内几张照片的行为完全一样，见 `tests/ui/test_group_flow.py::test_group_cards_are_kept_when_photos_inside_are_deleted`）。刻意不在这里重算分组：重算意味着重扫整层，选中与滚动位置全丢，而监听器（ADR 0013）已经负责把该做的做完了。

### 5. 两条约束怎么讲

| 约束 | 摊平之后怎么满足 |
|---|---|
| 不主动动用户文件 | 摊平只发生在用户点了菜单项 / 按下快捷键的那一刻，没有任何后台整理 |
| 有据可查 | 每一项都进 journal；移到废纸篓可 ⌘Z 取回，移动到相册可 ⌘Z 一次撤整批（ADR 0019 决策 3） |
| 不做「批量整理」 | 摊平不新增任何自动行为：用户不点，照片就一步都不动 |

## 后果

- 分组菜单第一次有了**子菜单行**与最右列的键位列，`ShortcutColumnMenu` 早就为这件事准备好了（`owns_submenu_arrows`），样式表测试不受影响。「在访达中显示」对分组也不再说「分组不是磁盘上的文件夹」，那条横幅改为在**摊平后确实一个路径都没有**时才出现（正常情况下不会：组卡片必带至少一张照片）。`MainWindow.trash_selected()` 摘行的判据多认得一种条目（`GroupRef`：全部组员都被移走才算这一行走了），其余不变。
- **与大图页（[ADR 0021](0021-viewer-context-menu.md)）合流**：两条都改在「命令作用于谁」这一个出口上（`MainWindow._selected_entries` / `_selected_paths`），而大图页作用的是正在看的那一张 —— 那必然是照片，摊平对它没有影响。合并时两处冲突各留一半：`_selected_entries` 继续按页面分叉，摊平接在它后面。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 菜单里摆成「拷贝组内 128 张」并另做一套文案 | 同一批 `QAction` 只有一份文案，卡片上已经写着「128 张」 |
| 把组摊平成一个临时选区，再走原来的多选代码 | 那会改掉网格选区：用户右键了一张卡片，选区却变成组内 128 张照片 |
| 整组进废纸篓要弹确认框 | 与访达、与 Gallery 既有的废纸篓口径都不一致（ADR 0008 决策 3）；要防手滑就该在**整组**上防，而不是只在这里弹窗 |
| 删掉组内一部分时立刻重算分组 | 重算等于重扫整层，选中与滚动位置全丢；监听器已经负责（ADR 0013） |
| 让「粘贴」「重命名」「在默认应用中打开」也摊平 | 见决策 2：分别与这一组无关（ADR 0018 决策 3）、ADR 0004 明确排除、128 张一起交给系统默认应用说不清打开哪一张（ADR 0014 决策 7） |
