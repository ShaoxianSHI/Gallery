# ADR 0026：标题栏右上角的胶囊搜索框 + 面包屑右侧的筛选条件

- 状态：已接受
- 日期：2026-10-03
- 相关代码：`src/gallery/core/library/search.py`、`src/gallery/core/library/index.py`、
  `src/gallery/core/library/facade.py`、`src/gallery/ui/search_field.py`、
  `src/gallery/ui/panels/breadcrumb.py`、`src/gallery/ui/navigation.py`、
  `src/gallery/ui/main_window.py`
- 相关：[ADR 0009](0009-metadata-grouping-and-sorting.md)（facet 索引与批量读取）、
  [ADR 0010](0010-place-resolve-on-open.md)（打开库时先跑一遍后台索引维护）、
  [ADR 0013](0013-filesystem-watch.md)（监听器顺带维护索引）、
  [ADR 0025](0025-rename-in-the-title-bar.md)（标题栏那一行归我们画）、
  [ADR 0040](0040-filter-within-the-current-view.md)（同一套条件的第二个作用域：在当前视图内筛选）

> **本文描述的是作用域为「整库」时的那一种。** 条件还有第二种用法（收窄当前这一层、视图本身
> 不动），见 [ADR 0040](0040-filter-within-the-current-view.md)。本文里「横跨整个库」「结果就是
> 一层」那几条都只对整库检索成立 —— 筛选时月视图仍然是月视图，面包屑也照旧报完整路径。

## 背景

软件到 M6 为止只会**遍历**：浏览相册、按元数据分组、按字段排序。用户要找一张照片，
唯一的办法是「想起来它在哪个相册 → 逐层进去 → 用眼睛扫」。一张库几千张之后这条路就走不通了，
而照片里那些**没被用来分组排序的字段**（相机、镜头、关键词、地点）明明已经在索引里躺着。

需求很具体：

1. 能按**文件名**与**相册**搜，也能按**各种元数据字段**搜；
2. 搜索框在窗口标题栏**右上角**，胶囊状，放大镜在最左、文字在它右边；
3. 敲 `#` 弹出可选的字段（文件名、相册、各元数据字段）；**不带 `#` 默认搜文件名**；
4. 回车确认后清空输入框，这条条件出现在**面包屑那一行的最右侧**；
5. 可以连续提交多条条件，按顺序右对齐排开。

于是有三件事要定：**搜什么**（字段清单与匹配语义）、**存哪里**（索引）、**结果是什么**
（一个新层次，还是把当前层改小）。

## 决策

### 1. 范围是整个库，多条条件一律「全部满足」

检索**不限定在当前相册**，命中后横跨全库。需要范围时自己加一条「#相册 旅行」。

理由：用户找一张照片时，十有八九说不清它在哪个相册里 —— 那正是他要用搜索的原因。
限定在当前层等于先要他知道答案再用工具。

**这一条是「用户找照片」这个场景的答案，不是唯一的答案**：用户**浏览**时想要的是另一件事 ——
把眼前这一层收窄而视图不动（见 [ADR 0040](0040-filter-within-the-current-view.md) 决策 1）。
所以这不是一条被推翻的决策，而是有了作用域的那一半。

多条条件是 **AND**：每提交一条，结果集就再收窄一层。它是「筛选器」，不是「多选并集」 ——
后者会让「加一条条件之后结果变多」，那不叫筛选。

### 1b. 检索时面包屑只报**库名**：文件夹与分组都不报

在 `旅行/2024` 里搜，面包屑上写的是 `照片 ▸ 搜索结果（4） ▸ 文件名：jpg`，**不是**
`照片 ▸ 旅行 ▸ 2024 ▸ 搜索结果（4）`：检索横跨整库（决策 1），留着路径段读起来就成了
「在这个文件夹里搜到 4 张」，而实际这 4 张大半在别处。

**分组那一段同理（容易只做一半）**：`照片 ▸ 2024 年 5 月 ▸ 搜索结果（3）` 读起来是
「这一组里搜到 3 张」，而检索压根不看分组（见 `_start_scan`：条件存在时分组那条路不
参与）。实测过一个**空组** —— 里面搜出 3 张全库照片，面包屑还写着那个组名。

**反过来，筛选时这两段都要留着**（ADR 0040 决策 4）：范围没变，藏掉路径是在说一件不存在的
事。判据是「范围变了吗」，不是「有条件了吗」。

两条都是「那一行在说一件不存在的事」，比什么都不说更坏。范围要收窄自己加一条
「#相册 …」，那一条明明白白写在右端。

`_current_dir` 与 `_group_view` **都留着**：撤光条件之后回到原来那一层、那一组
（条件为空时 `_start_scan` 才轮到分组那条路）。

### 2. 条件 = 一个字段 + 一段文本，语法是 `#字段 值`

`#相机 Canon`、`#ISO >800`、`#拍摄时间 2024-05`、`#相册 旅行`，以及不带 `#` 的
`海边`（= `#文件名 海边`）。

**补全后自动补上尾随空格**，接着敲值即可。用户一定会打中文，所以 `#相机` 与 `#camera`
等价 —— 候选列表同时认 id 与中文名。

**值里可以有区间，但不是所有字段都有**：只有日期那一族认 `2023～2024`，两端各含自己那一段
（`2023-06 ～ 2023-08` 是那三个月）。**分隔符认全角 `～` 与半角 `~` 两种**，文档与提示
一律摆全角那个。

起初只认全角，理由是「多认几种只会让『为什么这条没生效』更难猜，而没人会去猜是自己敲错了
全角还是半角」。这条规则当场就撞了 —— 英文键盘敲出来的正是半角 `~`，而报错里半个字没提到
是**哪一种写法**不对，于是那句话等于没写，用户只知道自己写的东西被拒了。**判据反过来了**：
日期语法里根本不会出现波浪号，多认一种写法不产生歧义（成本为零），少认一种却只是把用户挡在
门外。归一放在 `search._split_range` 一处 —— 切分这件事有两个调用方（解析条件、给横幅找
理由），各切各的迟早一边认一种写法。

**区间里不认比较符**（`>2023～2024` 提交不了）：一句话里塞两个比较符说的是两件不同的事，
要单边就用 `>2023`。**写反了（`2024～2023`）宁可提交不了**：记录会生成
`>= 大的 AND < 小的`，于是安静地返回 0 条 —— 与「条件太严」长得一模一样，正是最该避免的
那种假答案。横幅上说清哪一端在后面（`search.unusable_reason`，界面上只接这一句）。

### 3. 索引：新增一张 `photos` 表，**不升 `SCHEMA_VERSION`**

现有 `facets` 表只有**读过 EXIF 的照片**才有行，因此单靠它搜不到没读过的照片。
文件名与相册检索必须覆盖全库，于是新开一张只存「扫描时就有的东西」的文件表：

```sql
CREATE TABLE IF NOT EXISTS photos (
    path     TEXT PRIMARY KEY,
    size     INTEGER NOT NULL,
    mtime_ns INTEGER NOT NULL,
    name     TEXT NOT NULL COLLATE NOCASE,   -- 文件名（含扩展名）
    folder   TEXT NOT NULL COLLATE NOCASE,   -- 相对库根，如 "旅行/2024"
    suffix   TEXT NOT NULL COLLATE NOCASE    -- ".jpg"
);
```

**为什么不升版本**：`SCHEMA_VERSION` 那一段的判据是「结构变了就整表重建」。这次是**纯新增**，
所有语句都带 `IF NOT EXISTS`，老库连上来自动多出这些表，一行已读好的 facet 都不用重读。
为一张新表把整库的 EXIF 重读一遍纯属浪费。（将来若要**改** `photos` 的列，那时才升版本，
并在那条注释里写清代价。）

**索引只对等值与前缀有意义**：SQLite 的 `LIKE` 只在前缀模式（`q%`）且列是 `NOCASE` 时才走索引，
`'%q%'` 一定全表扫。所以 `photos(folder)`、`photos(name)` 是给「相册」「文件名以前缀开头」准备的，
`facets(camera)`、`facets(city)` 同理；关键词这种子串条件用不上索引。几万行扫一列几十毫秒，
在后台线程里可接受 —— 不为了「看起来快」去铺一堆用不上的索引，那是拿写放大换不存在的好处。

`COLLATE NOCASE` 是白拿的：SQLite 的 `LIKE` 对 ASCII 本来就大小写不敏感，
不必再造 `name_lc` 这类小写列。

### 4. 不用 FTS5

本机 SQLite 3.53 带 FTS5，`trigram` 分词器确实能让子串检索也走索引。**但它要求查询至少 3 个
字符**，而「海边」「西湖」这种两字查询在中文里很常见，会直接一个都搜不到。
先不用；等实测几万张的子串扫描真的成为瓶颈，再把它写进这个文件（那时索引结构也要跟着改，
因此与升版本一起做）。

### 5. 照片表由打开库后的后台那一遍填，与 `resolve_places` 同一套路

`Library.index_photos()`：**只有真的有活干才起**（表里一行都没有），跑起来报进度横幅。
理由与 [ADR 0010](0010-place-resolve-on-open.md) 那一遍完全相同：索引是缓存，打开库这一遍
顺便填好，之后每次检索就只是一次查表。

监听器顺带维护它（[ADR 0013](0013-filesystem-watch.md)）：新增照片写一行，消失的照片删一行。

**检索前索引必须就绪**，否则用户会看到「搜不到」的假阴性。真的按下检索而索引还没建全时，
把这次检索挂起，等那一遍跑完再执行。

两次遍历（照片表 + 地点）目前是分开的；合并成一次遍历是明显的优化，但会动到 `resolve_places`
的签名与它的一批测试，这一版不做。

### 6. 匹配语义逐字段定死，SQL 只在 `core/library/search.py` 里生成

| 条件 | 落到哪一列 | 匹配 |
|---|---|---|
| 文件名（默认） | `photos.name` | `LIKE '%q%'` |
| 相册 | `photos.folder` | `= q OR LIKE 'q/%'`（含子相册） |
| 文件格式 | `photos.suffix` | `= '.jpg'` |
| 相机 / 镜头 / 国家 / 省州 / 城市 / 关键词 | `facets.*` | `LIKE '%q%'` |
| 拍摄时间 | `facets.captured`（epoch 秒） | `2024` / `2024-05` / `2024-05-16` 各自是一段；`2023～2024` 是一段区间；`>` `<` 取那一段之外 |
| 大小 / 光圈 / 快门 / ISO / 焦距 / 像素 | `photos.size`、`facets.*` | `800`、`>800`、`>=1.8`、`<60` |

多条 `AND` 拼成一条 `LEFT JOIN facets ON f.path = p.path`，取回 `(path, size, mtime_ns)`
**直接构造 `PhotoRef`** —— 不为每条结果再 `stat()` 一次。

**SQL 只在一处生成**（`search.build_query`），其余地方一律调用它。于是「哪个字段落到哪一列」
这件事在代码里是可 grep 的一段，而不是散在各个 `if` 分支里。

结果里可能混着已被删掉的文件（缓存不会自己少行），组装时逐条 `exists()` 剔掉。

### 7. 搜索结果就是**一层**，走与扫描完全相同的收尾路径

搜索结果与相册、分组一样是「一层」：面包屑追加一段加粗不可点的「搜索结果（128）」，
~~`Esc` 逐条撤销条件、撤光才回到「上一级」~~ —— **`Esc` 逐条撤销条件这件事已挪到 `⇧Esc`，
`Esc` 只管退位置**（[ADR 0040](0040-filter-within-the-current-view.md) 决策 11）：把条件排在
文件夹 / 那一格之前，于是只要有条件就永远退不出位置，而「按 Esc 结果少了一条条件」与「我退了」
在屏幕上分不出来。

关键在于**它复用 `_on_scan_done` 之后的一切**：facet 补齐、分组排序、缩略图预取、焦点恢复、
空层提示、监听增量（[ADR 0009](0009-metadata-grouping-and-sorting.md) 决策 6 那套「先累积后摆」也照旧）。
于是这次功能的界面侧改动只剩下「摆一个输入框」与「面包屑上多摆几个胶囊」，
状态机那部分几乎是零 —— 新写一条平行路径才是 bug 的来源。

排序与分组**沿用当前选择**：排序值从 `cached_facets()` 拿（纯查表），需要 EXIF 时走
`_start_facet_read` 那条已有的路。

### 8. 搜索框是 `TitleBar` 的**兄弟**，不是它的子控件

胶囊由 `MainWindow._layout_title_bar()` 与 `TitleBar` 一起 `setGeometry` 摆上去。
不能塞进 `TitleBar`：它不编辑时带 `WA_TransparentForMouseEvents`（那是
[ADR 0025](0025-rename-in-the-title-bar.md) 决策 5 为了「那一段仍然能拖窗口」留下的），
**那个标志会连子控件一起罩住** —— 塞进去的话放大镜那一块收不到点击。

于是新建 `ui/search_field.py`，与 `title_bar.py` 同属「窗口顶边那一行」，判据与 ADR 0006 一致。
标题文字与 `⌘R` 的输入框都要给胶囊让出右边那一份（`TitleBar.reserve_right`），
否则一个长相册名会从胶囊底下穿过去。

**`#` 的候选列表是胶囊的子控件，不是一个 `Qt.Popup` 窗口。** 弹出窗口一 `show()` 就会把焦点
从输入框抢走，于是「列表开着」与「输入框有焦点」没法同时成立，↑↓ 与回车都得绕一大圈
（Qt 自己的 `QCompleter` 为此加了 `WA_ShowWithoutActivating`，实测照样被 `focusOutEvent`
打断）。子控件不吃焦点，所有按键留在输入框里；画在窗口内容之上也不会被裁掉 —— Qt 不把子
控件裁到父矩形内（实测伸出去的那一段照常画出来）。

**输入框只认点击（`ClickFocus`）**：默认的 `StrongFocus` 会让窗口一打开就把光标送进这个框，
于是方向键在网格上立刻失灵（用户得先点一下照片区才找得回来）。要它进来有一条明路：`⌘F`。

**标题栏那一条比安全区高 12 点（`title_bar.EXTRA_PADDING`）**，高出来的部分**同时把内容区
往下推同样的点数**（中央控件加同样的上边距）。28 点的安全区里塞一个 22 点的胶囊，上下各剩
3 点 —— 胶囊的上边框几乎贴着窗口顶边，看上去像浮在边沿上。只加高那一段而不推内容是不行的：
那一段本身不画东西（标题文字不铺底色），但**胶囊是画的**，它一越界就是一块带边框的底色压在
照片区顶边上（回归测试 `test_innermost_layer_has_no_border` 量到过几百个非底色像素）。
胶囊离窗口右边 20 点（`search_field.MARGIN_RIGHT`）—— 那边没有交通灯，但它贴边时看着像被
窗口挤出去。**这一格是「右上角那一块」的右缘**：面包屑右端那几枚条件胶囊（决策 4）要与它
对齐 —— 两者是同一列东西、只是分两行摆着，右缘各说各话时那条竖线是折的。落实由
`BreadcrumbBar.set_right_inset`，换算在 `MainWindow._layout_title_bar` 里做（面包屑摆在一份
有边距的布局里，它自己的右缘已经比窗口右缘靠内 10 点）。

### 9. 候选列表与右键菜单是**同一种东西**

`#` 那份候选列表的颜色**不由它自己定**：`menu_style.popup_list_style()` 从控件自己的调色板
读 `Window` / `Highlight` / `WindowText` / `HighlightedText` 四个角色，与
`menu_style.style_sheet()`（菜单那一整份）取自同一个地方。理由与 ADR 0024 相同：「菜单怎么
画」是同一层的事，两处各派生一遍早晚差一档，而「下拉框比菜单深一点」正是那种没人说得清、
却一眼看得出的差别。

**列表不是菜单**，因此不共用那一整份样式表：菜单的行有快捷键列、分隔线与子菜单箭头，
列表两样都没有；复用的只是颜色与圆角那一层。

**悬停即当前项。** 挂了样式表之后 Qt 不再按 `State_MouseOver` 自己去挑高亮色（与
`menu_style.style_sheet` 里那条菜单的注释是同一件事），而「当前项」那一份高亮它是照画的。
于是候选列表把悬停的那一行设成**当前项**：高亮亮起来，顺带让鼠标与键盘说同一句话（点它就
补全它，不必有两套「选中」）。事件接在**视口**上而不是视图的 `mouseMoveEvent` —— 滚动区域
的视口是 Qt 自己的控件，落在它身上的事件不会再回到视图上（实测那次移动完全没反应）。

### 10. 胶囊上**点文字是改、点 ✕ 才是撤掉**

点一枚胶囊是**把它放回搜索框接着改**（`SearchCondition.as_input` 负责还原成
`#相机 Canon` 那一串，**字段前缀要带上** —— 只放值的话用户看到的是「旅行」，不知道这一条
是按哪个字段筛的，而改条件多半正是要换字段）。回车**就地替换**那一条，位置不变：换成
「删掉旧的、冒出一条新的」的话，面包屑上的顺序会跳，用户看着像是多了一条。正在改的那一枚
会换一种边框与底色 —— 不标出来的话，用户按回车会以为又多了一条。

删除留给两个明确的入口：**点右端那个 ✕**（按字体度量分的热区，见
`ChipButton._hits_mark`），以及**改到一半把输入框清空后回车**（这时输入框里没有别的意思）。
「点一下胶囊就没了」是不能有的意外 —— 改与撤必须是两个动作。

在搜索框里 `Esc` 分两种：正在改某一条时是**放弃这一次改动**（那一条原样留着），否则才是撤掉最后一条。
~~撤到 0 条才回到「上一级」~~ —— **「逐条撤销条件」已挪到 `⇧Esc`，`Esc` 只管退位置**
（[ADR 0040](0040-filter-within-the-current-view.md) 决策 11）。**在搜索框里那一处仍走 `⇧Esc` 的
那件事**（不转给 `go_up`）：它的语境是条件，不是位置。

平铺模式下平时不显示面包屑（那里没有文件夹可指），但**有搜索条件时必须显示** ——
否则条件没地方摆。

条件**不进会话**：搜索是临时的，下次打开就是一个干净的库。

## 后果

- 状态机留在 `main_window.py`（**不**另起一个 mixin）：它与换层、暂存区、代次那一套是
  同一件事，抽出去要把十几个字段传过边界 —— 而 ADR 0024 当初抽出 `write_ops` 的理由是
  **约束 1**（改动可以 grep 到一处），搜索没有那样的理由。
- 索引多一张表；`forget` / `prune` / `clear` 三条清理路径都要带上它。
- 打开库时多一遍后台遍历（有活才起）。
- 菜单多了「搜索…」`⌘F`（对齐访达把它放在「文件」里）与「清除全部搜索条件」。
- 结果**最多摆 5000 张**（`search.RESULT_LIMIT`）：一万张全进模型会让整屏重排慢下来，
  而用户多半只是想看看前几百张。命中总数写在面包屑上，被截断了用户看得见。
- 同一个字段可以有多条条件（「相机 Canon」+「相机 5D」）—— 用户想收窄就该能收窄。
  重复的同一条则原样再摆一条，删掉一条就少一条（**不去重**）。
- 测试：`tests/core/library/test_search.py`（解析、SQL、真实库里的过滤结果）、
  `test_index.py` 补 `photos` 表用例、`tests/ui/test_search_flow.py`（端到端）。
- **`SEARCH_FIELDS` 里那些列名要拿真 schema 执行一遍**（`test_every_searchable_field_survives_the_real_schema`）。
  曾经把拍摄时间那一项写成 `f.captured_at` —— 那是 `PhotoFacets` 上的**属性名**，列名其实是
  `captured`，两者只在这一项上不一样。解析与生成 SQL 两层都察觉不到，SQLite 直到执行才说
  `no such column`，而那条错误被包成了「检索没能完成」，界面上表现为「一条都搜不出来」——
  与「条件太严」长得一模一样。**手写的列名不属于「写完就算数」那一类**。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 只搜当前相册层 | 用户找照片时恰恰说不清它在哪个相册里，那正是他要用搜索的原因（**浏览**时想要的正是这个，于是成了 ADR 0040 的那第二种作用域） |
| 条件之间取并集 | 「加一条条件后结果变多」不叫筛选 |
| 靠 `facets` 表搜文件名 | 它只有读过 EXIF 的行，没读过的照片等于不存在 |
| 给 `facets` 加一张「每个扫描到的路径都补一行」 | 与新开 `photos` 表同解，但让「facet 快照」这张表同时装两件不同的事；新表还能独立地被监听器维护 |
| 升 `SCHEMA_VERSION` 到 7 | 纯新增而已，为一张新表把整库 EXIF 重读一遍纯属浪费（缓存本来就该整表重建，但不必每次都重建） |
| 上 FTS5 + trigram | 查询少于 3 个字符直接查不到，中文两字查询太常见（见决策 4） |
| 铺满所有 facet 列的索引 | 子串条件用不上索引，那是拿写放大换不存在的好处 |
| 搜索框作为 `TitleBar` 的子控件 | `WA_TransparentForMouseEvents` 会连子控件一起罩住，收不到点击 |
| 每次敲字实时刷新结果 | 每敲一下就是一次后台任务与一次整屏重排；用户要的是「敲完回车」 |
| 条件写进会话 | 搜索是临时的，跨启动记住一串筛选条件只会让人莫名其妙 |
