# ADR 0038：缓存位置统一（缩略图进系统目录，其余全进 `.gallery/`）

- 状态：已接受
- 日期：2026-10-05
- 相关代码：`src/gallery/core/paths.py`、`core/constants.py`、
  `core/library/index.py`、`core/library/config.py`、`core/library/session.py`、
  `core/library/facade.py`、`ui/window/library_flow.py`
- 取代：ADR 0001 决策 5、决策 6

## 背景

### 一、同一个库的两份缓存

实机排查发现「照片」库在两个地方各有一份 `index.db` 与缩略图：

| | `照片/.gallery/` | `~/Library/Application Support/Gallery/cache/` |
|---|---|---|
| `index.db` | 1.1 MB，1227 行，活跃 | 1.0 MB，10-04 09:57 停更 |
| `thumbs` | 1223 个文件 / 49 MB，活跃 | 1067 个文件 / 39 MB，10-04 停更 |

外部那 1067 张里 907 张与库内同名同内容，剩下 160 个是换了 key 的同一批照片。
也就是说外部那份 100% 可丢弃。

成因在 `LibraryFlowMixin._resolve_cache_location`：判据是「`.gallery/` 在不在」，
而不是记下来的用户选择，而 `.gallery` 一旦建出来就永远为真。于是

1. 启动时静默恢复（`silent=True`）、库里还没有 `.gallery` → 走系统目录；
2. 后来交互打开、在弹窗里选了「在库中缓存」→ 建 `.gallery`；
3. 从此永远库内。

**没有任何代码删除旧位置。** 而 ADR 0001 决策 5 把「写入用户目录」定义成整个应用
**只有一处**，那处是要问用户的 —— 于是就有了「同一个库两个位置各写一份」这个局面。

### 二、真正的代价不是字节，是文件数

缩略图与索引都是纯派生缓存（红线 5），但形态差了两个数量级：

| | 每张照片 | 外推到 10 万张 |
|---|---|---|
| 缩略图 | 1 个文件 / 38.7 KiB | **99 674 个文件** / 3.7 GiB |
| `index.db` | 1 个文件 / 931 B（合计） | 1 个文件 / 89 MiB |

云同步的成本主要在**文件数**：OneDrive / Dropbox 对每个文件都有元数据与限流，
十万个小文件来回传是这类软件自己给自己找的麻烦。而索引无论多大都只是**一个**文件。

顺带量到第二个毛病：`index.db` 在同步目录里跑 WAL 模式，旁边长期躺着
`index.db-wal` 与 `index.db-shm`（各 32 KB / 增长），**那两个也跟着同步**。
SQLite 明确不建议把活跃的 WAL 数据库放在网络或同步目录，两台机器各跑 Gallery
时互相同步 WAL 有损坏索引的风险。

### 三、external 模式的「零写入」承诺已经不成立

ADR 0001 决策 5 给「缓存到系统目录」的承诺是「照片文件夹保持一个字节都不写入」。
实际上 `paths.journal_dir` 不看 `cache_in_library` —— 改名 / 移到废纸篓 / 粘贴 /
移动到相册全部无条件写 `<库>/.gallery/journal/*.jsonl`（实机已有一份 191 KB 的日志，
而且 OneDrive 因为冲突又造了一份 `2026-10-05.jsonl 2.jsonl`）。

更糟的是**它自己把这个承诺拆了**：journal 一旦建出来，`.gallery/` 就存在了，
下次打开时 `has_config_dir` 变成真，**缓存悄悄从系统目录搬回库里，连问都不问**。
`config.toml` 那条路反而有闸门（`set_album_cover` 在没有配置目录时报错）——
一个承诺只剩下一半在守。

## 决策

### 1. 取消 external 模式，缩略图是唯一进系统目录的东西

缩略图按库路径摘要落在 `<app cache>/thumbs/<digest>/`；`config.toml`、`index.db`、
`journal/` 一律在 `<库>/.gallery/`。

理由如上：这两样都是「一万个小文件」与「一个大文件」的区别，而只有前者值得为它
单独设一个位置。索引留在库里还有一层好处：它与 `config.toml`、`journal` 同生共死，
三者都是「关于这个库」的，而缩略图是「关于这批像素」的。

**取消的不只是开关，还有承诺。** 「照片文件夹一个字节都不写入」这句话连同
`set_album_cover` 的那道闸门一起去掉 —— 没有零写入模式，就不该留着一段假装还有
零写入模式的代码与文案。

### 2. 开场不再问

`prepare_library` 从「弹窗里用户点了才建」变成「打开库时保证 `.gallery` 存在」。
首次打开直接建，不弹任何对话框；说明改放在 README、欢迎页与首次打开后的横幅里。

这不是红线问题（`.gallery/` 本来就是允许写的，红线 6 挡的是**它以外**的东西），
理由只是礼貌：在用户的 Dropbox 文件夹里凭空出现一个隐藏目录，说一声比不说好。

### 3. 建不出来就自动降级，不问

`.gallery/` 建不出来（只读卷、SMB 共享）时**自动降级并用横幅说一声**，不把用户
挡在门外。两条退路本来就存在：

- `FacetIndex` 的 `path=None` 分支 —— 只在内存里缓存，本次会话能用，下次重读元数据；
- `append_record` 写 journal 失败 —— 返回 `False` 不抛，由界面如实告知
  （改名照样落地，只是没有可回滚的记录）。

这条路上没有红线冲突：卷只读的话改名与移到废纸篓本来就做不了，journal 写不进去
不构成问题。所以**不需要问用户**：他其实没有第三个有意义的选择。

### 4. 库级界面偏好搬进 `config.toml`，应用级的留在 `state.json`

`state.json` 的九个字段其实是两类：

| | 字段 | 归属 |
|---|---|---|
| 应用级 | `recent_roots`、`window` | 打开软件时还不知道要开哪个库，放不进某个库的 `.gallery` |
| 库级 | `browse_mode`、`metadata_visible`、`group_facet`、`sort_descending`、`sort_facet`、`calendar_level`、`thumbnail_edge` | 换库就该重来 |

库级那七个进 `config.toml` 的 `[ui]` 表。两个附带的行为变化是**有意的**：

- 这七个从**全局**变成**每库各自一份** —— 用 A 库的地点分组习惯切到 B 库本来就该重来；
- `thumbnail_edge`（网格档位，≤ `thumbnail_max_edge`）与 `thumbnail_max_edge`
  （缓存规格）名字相近含义不同，写在同一处但分属两个层次。

升级时从旧 `state.json` 一次性迁移（`[ui]` 表不存在且旧文件里有值时才写），
用户看不到排序偏好被重置。

### 5. 索引关掉 WAL

`journal_mode=DELETE` + `synchronous=NORMAL`。

**性能实测（1227 行的真实库规模，冷热各一轮）：**

| 操作 | WAL | DELETE |
|---|---|---|
| 整库扫描写 1227 行 photos | 21.4 ms | 20.3 ms |
| 写 1227 行 facets | 2.5 ms | 2.8 ms |
| 读回全部 1227 行 | 8.2 ms | 7.6 ms |
| 监听器 30 次单行提交 | 2.2 ms | 6.5 ms |
| **运行期间落盘文件数** | **3 个** | **1 个** |

批量路径**没有差别**（在噪声内）。唯一变慢的是监听器那条「加一张照片提交一次」，
代价是每次多 0.14 ms —— 而一个文件事件引发的重扫远比这贵。

**关键在于 WAL 在这个代码里本来就没买到什么。** WAL 的主要优势是读写不互斥，而
`FacetIndex` 全程只有一个连接、一把 `threading.Lock`，每一个访问 `_connection` 的
方法都持锁 —— Python 层的锁已经把 SQLite 层的并发堵死了。所以 WAL 一直在为一个
用不上的特性，付 `-wal` / `-shm` 两个文件的同步代价。

`synchronous=NORMAL` 保留：索引是缓存（红线 5），为随时能重建的东西付满额断电
持久性是白付。

### 5b. 自动恢复失败时静默留在欢迎页

`open_library` 保留一个 `silent` 参数，但它的含义只剩一件事：**开不起来也不弹框**。
启动时自动恢复上次那个库走 `silent=True`。

这一条是**实现过程中被一个挂死的测试逼出来的**：把 `silent` 整个删掉之后，库被移走
（改名、挪窝、外接盘没插）的用户每次启动都会被一个模态错误框拦住 —— 而那是日常操作，
不是故障。用户自己点「最近打开」时仍然如实报错：那一下是他刚做的动作。

### 6. 存量清理

旧物在打开库时清掉，都是「只删自己写的」：

- `<库>/.gallery/cache/thumbs/` —— 缩略图搬去系统目录后它整块作废。**这正是用户最初
  看到的那份重复。** 收掉它之后**再收那个空壳父目录 `cache/`**（它只装过 thumbs）；
  `rmdir` 对非空目录会失败，所以里面还有别人的东西时它自然留在原地。
- `<app cache>/index/` —— 库外索引这条路整个没了。这一处是**整台机器一份**的
  （按库摘要分文件躺在同一个目录里），所以清理函数不接库根。
- 读不出来的库留下的孤儿摘要目录 —— **不做**（见下）。

## 后果

- 「照片」库立刻少 49 MB 的重复缓存；`<app cache>/` 从「可能有重复」变成「只存缩略图」。
- `Library.cache_in_library`、`FacetIndex.open(in_library=…)`、
  `paths.external_index_file`、`paths.external_thumbnail_cache_dir` 全部消失 ——
  **两处位置的代码本身就是那个 bug 的载体**，留着一个开关就还会有人重新打开它。
- `thumbnail_edge` 等七个偏好变成每库一份（决策 4）。
- **已知遗留：孤儿摘要目录清不掉。** `<app cache>/thumbs/` 下某个摘要对应的库如果
  被移动或删除，那个目录就再也无人认领 —— 摘要不可逆，无法反查路径。
  实机已有一个（`5b4530ebcaec57ba`，23 个文件）。目前只随磁盘增长，没有上限也没有
  驱逐。补它要单独一条决策（记录已知摘要 / 给系统缓存目录一个全局上限），不在本次范围。
- **这条遗留会被测试放大，所以测试必须隔离应用数据目录。** 界面用例每个用例一个
  `tmp_path`，摘要因此每个用例都不一样 —— 实测**跑两轮就在用户的真实缓存目录里
  留下 2509 个**没人认领的摘要目录（65 MB）。`tests/ui/conftest.py` 里 autouse 的
  `isolated_app_data` 把 `paths.app_data_base` 钉到临时目录上，那是 `state.json` 与
  系统缓存**唯一**的共同来源：逐个用例去传 `session_base` / `cache_base` 是三十多处
  各写一遍，漏掉任何一处都是同样的泄漏，而且漏了看不出来。
- 顺带在 `tests/ui/conftest.py` 加了一条 `no_modal_dialogs`：**模态对话框当场失败**。
  实现过程中一个用例打开了不存在的库 → `_report_error` → `QMessageBox.critical`，
  离屏下没人点确定，那个文件跑了五分钟不返回。症状是「慢」，不是一条红的断言。
  **第一版拦错了地方**（换掉实例方法 `exec`，而调用走的是 C++ 里的静态辅助函数），
  探针用例照样挂满五分钟 —— 一个永远为绿的守护比没有更坏。现在拦的是那几个
  `static` 方法（`critical` / `question` / `warning` / `information` / `about`），
  探针 3 秒内变红。

## 被否决的方案

- **保留 external 模式，只加一道清理。** 承诺已经只剩一半在守（决策 1 末段），
  而剩下那一半还在制造「同一个库两个位置」这种需要清理的局面。不值得。
- **索引也放系统目录。** 与 `config.toml` / `journal` 拆到两处，而它们都是
  「关于这个库」而非「关于这批像素」的；换机器时索引跟着库走才说得通。
- **索引留在库里但继续用 WAL。** 正是决策 5 要治的：`-wal` / `-shm` 跟着同步，
  两台机器互相覆盖有损坏风险，而实测性能收益本来就是零。
- **按用户选择分别存两份、打开时读取「上次用的那一份」。** 换来的是「换个机器上
  一半的照片要重解码」，而省下的是一份可以随时重扫出来的缓存。不划算。
- **仍然弹窗，只是把两个按钮换成一个。** 决策 3 已经说明那条路上用户没有第三个
  有意义的选择，弹窗只会让他在一个没有退路的对话框前点头。
