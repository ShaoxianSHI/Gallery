# ADR 0028：每个相册可以指定封面照片，存在 `.gallery/config.toml` 里

- 状态：已接受
- 日期：2026-10-18
- 相关代码：`src/gallery/core/library/config.py`、`src/gallery/core/library/facade.py`、`src/gallery/ui/write_ops.py`、`src/gallery/ui/menus.py`、`src/gallery/ui/banners.py`
- 相关：[ADR 0023](0023-menu-groups.md)（四段分组，它给第一段加了两行）、[ADR 0014](0014-context-menu.md)（右键菜单的取向）、[ADR 0021](0021-viewer-context-menu.md)（大图页作用的是正在看的那一张）、[ADR 0004](0004-rename-on-disk.md)（红线 1：只许用户亲手触发）、[ADR 0013](0013-filesystem-watch.md)（`.gallery` 是隐藏目录，扫描与监听都看不见它）

## 背景

相册卡片的封面今天是「文件夹里（含更深的层级）找到的**第一张照片**」——
`Library.folder_cover` 找到第一张就停，因为整棵子树可能很大，而封面只需要一张。

这条规矩有两个毛病，都是用户每天都会碰到的：

1. **第一张不是他想要的那张。** 同一个相册里，封面由文件名或建库时的顺序决定；
   用户整理完一遍之后，「苏州」那张卡片挂的往往是他随手拍的第一张，而不是海边那张。
2. **改不掉。** 想换封面只能去改文件名顺序，或者把照片挪到别处 —— 两条都是在动用户的文件，
   而「我想让这个相册看起来是这样」根本不需要动它们。

`config.toml` 是这个项目里**唯一不是缓存**的文件（README 的硬性约定），用户手改它是预期行为。
把「这个相册用哪一张当封面」记在那里，恰好落在它该在的地方。

## 决策

### 1. 命令挂在**照片**上，不是相册上

| 落点 | 菜单里那一行 |
|---|---|
| **单选一张照片**（网格或大图页） | 设为相册封面 |
| **恰好选中一个、且设过封面的相册** | 取消相册封面 |
| 多选照片 / 分组卡片 / 库根下的照片 / 空白处 | **不出现**（不是置灰） |

访达与「照片」app 都是这么做的，而且**它天然回答了「哪个相册」**：相册就是这张照片的父目录。
不问「现在站在哪一层」—— 在「全部照片」那一屏（照片是各个相册混在一起的）里，
用户说的仍然是它自己那个相册，答案就在路径里。

**分组卡片上不出现**：卡片不是磁盘上的东西，「把这个卡片当封面」没有对象
（与「重命名…」同一处置，ADR 0020）。哪怕组里恰好只有一张，那也是巧合而不是选择。

**库根下的照片没有这一条**：库根在网格上不是一张卡片，没有封面可设（决策 2）。

**不给真快捷键**：⇧⌘C 已经是「拷贝路径」，而这两条一年也用不到几次。
与「复制元数据」「复制分组条件」一样只活在右键菜单里（ADR 0014 决策 5）。

### 2. 存**相对库根的路径**，一张表两列

```toml
[album_covers]
"京都" = "京都/DSC_0001.JPG"
"2025" = "2025/苏州/海.jpg"
```

存相对路径是必须的：绝对路径在库里挪个位置、换台机器就全废了，而这是用户会手改、
也会跟着库一起提交进版本控制的文件（`.gitignore` 放行了 `config.toml`，就是为了这个）。

两列都是相对路径，**且封面必须在那个相册里**（子相册里的照片算数，它仍在这个相册的子树内）。
界面写进去的键与解析时读出来的键用的是同一个判据（`Library.set_album_cover` 与
`config._read_album_covers`），所以「写得进去」一定「读得回来」——
写进去一条下次打开库就报错的事故，在设计上就不可能发生。

**没有封面就整段不写**：刚建出来的库不该因为一节空注释像是有过设置。
按键排序写出去：这个文件是要进版本控制的，顺序抖动全是假 diff。

**用户手改整个表也认**：`[album_covers]` 是公开接口。非法取值（绝对路径、`..`、不是字符串、
封面不在相册里）一律给一句能照着改的中文提示，而不是「当作没设过」——
配置文件里的坏行不该被静默吞掉。

### 3. 没有配置目录的库**不写**，只说清楚

`.gallery/` 建不出来时（只读卷、网络共享），整个库退化成只读 —— 用户的一个字节都不写入
（ADR 0038 取消了「缓存放哪里」那个开场选择，这条约束不变）。而封面只能存在
`config.toml` 里，落盘那一步（`write_text_atomic`）又会顺手建出父目录。
于是这里只有两条路：悄悄建出来（毁掉那个承诺，而且毁在用户看不见的地方），
或者如实说「这个库里没有 `.gallery` 目录，封面设置没有地方保存」。

选后者。同理，**写失败时内存里那份配置不换**：换了就与磁盘对不上，
封面会「记得」一个压根没存下来的路径。

### 4. 指定的那张读不出来，就退回「第一张照片」；那一行配置留着

`folder_cover` 的判据顺序是「指定的那张 → 里面第一张」，而指定的那一张**照 `skip` 走**：
云盘上没下完的那张照片会进 `skip`（缩略图流水线早就为它备好了「换下一张」的机制），
于是它是**被跳过**，不是**被卡住**——否则一张半截的照片会让整张卡片永远挂着一张黑图。

那张配置**不删**：用户把照片挪出去又挪回来时，它又该是封面了。而界面上什么都不用说——
相册卡片本来就该有一张能看的封面，用户要的是封面，不是原因。

### 5. 只写 Gallery 自己的配置文件：不记 journal，不进撤销栈

`config.toml` 是 Gallery 自己的文件，用户的照片一个字节都不动，因此：

- **不触犯红线 1**，也不必进 `tests/test_guards.py` 那份「界面上会动用户文件的地方」的清单
  （那份守的是 `rename_entry` / `move_to_trash` / `copy_into` / `move_into` / `create_album` /
  `undo_last_write` 六个方法，封面一个都不属于）。
- **不记 journal**：那一摞记录的是「已经发生在硬盘上」的改动，而封面没有改动任何用户文件。
- **不进 `⌘Z`**：撤销那一摞是给「动了用户文件」的那些操作准备的。横幅因此**不提撤销**
  （说了就是在骗用户）。改回去是**对称的那条命令**——相册右键菜单里的「取消相册封面」，
  它只在真的设过封面时出现。

入口仍然收在 `ui/write_ops.py`：它确实是「用户按了一下之后才发生的写入」，
而那一整个文件就是为了让这种写入在代码里一处可查。

### 6. 换封面之后，那张卡片要**当场**重画

两处记忆都得清，少任何一处用户都看不到变化：

- **模型**里已经缩放好的那张 —— 相册卡片的键就是相册自己的路径，
  它并不知道封面换了人；不清的话 `needs_thumbnail` 说「这张我有了」。
- **流水线**里对这个相册的记忆（试过哪些照片当封面、`_empty`）——
  少了后一个，**一个原本空着的相册会永远停在文件夹图标上**：用户刚把里面唯一那张设成封面，
  看到的却还是那个图标。

## 后果

- 网格上会动用户文件的入口**仍然是那五条**（README 那句话没变）；封面另算，因为它写的是
  Gallery 自己的配置文件（决策 5）。
- ADR 0023 的四段分组**没有变**，只是第一段「看一眼」多了两行：
  它们改的是「这个相册在网格上长什么样」，与「打开」「在访达中显示」是同一族；
  而「会动文件」那一段留给仅有的两个会改用户文件的入口，往那儿塞一条无害的命令，
  恰好是那条分组最想避免的事。ADR 0023 的表已同步。
- 封面**不跟着改名走**：用户把相册或那张照片改名后，配置里那行指向了一个不存在的路径，
  退回「第一张照片」（决策 4）。让 `rename_entry` 去改配置就得同时处理撤销（⌘Z 把名字改回去时
  要把配置也改回来），两个真相源会把撤销栈变成第三份需要同步的状态 —— 不值当，
  而退回的行为本来就是对的（相册永远有一张封面）。
- 重写 `config.toml` 会**丢掉用户手写的注释**（标准库没有 TOML 写出来，字段是照模板拼的）。
  这与 `prepare_library` 一直以来的行为一致，而文件里的注释本来就在模板的那几行里。
- 换库时配置照常跟着库走：它本来就住在库里。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 右键**相册** → 「设为封面…」再挑一张 | 多一次弹窗与一次挑选，而照片那一侧一按就是；访达与「照片」都是挂在照片上的 |
| 相册封面写成 `.gallery/封面/` 里的缩略图副本 | 那是**缓存**：删掉就得重新生成，而「用户选了哪一张」是配置不是缓存（README 的硬性约定） |
| 封面塞进 `index.db` | 那是元数据快照，整库清缓存时会被重建 —— 用「只有缓存里才有」的数据当设置，是设计缺陷 |
| 用 macOS 的 `.DS_Store` 或 Finder 私有格式 | 那是系统的地盘，而且是二进制、手改不了 |
| 单独一个 `covers.json` | 用户手改的路径就该在人类可读的那个文件里；多一个文件就多一处能写错的地方 |
| 存绝对路径 | 库挪个位置、换台机器就全废了，而这个文件是要跟着库走的 |
| 让 `rename_entry` 顺手改配置里的封面 | 撤销时要把配置也改回来，两个真相源；退回「第一张照片」本来就是对的行为 |
| 封面进 `⌘Z` 撤销栈 | 那一摞装的是「动了用户文件」的操作；横幅因此也不能说「⌘Z 可以撤销」 |
| 封面读不出来就一直重试它 | 一张云盘上没下完的照片会让整张卡片永远挂着黑封面（流水线早就为这件事备好了 `skip`） |
| 多选时也摆这一条 | 把哪一张当封面说不清，与「打开」「重命名…」同一个理由 |
| 在菜单栏里也摆这两条 | 都要「当前这一格」才有对象，菜单栏上摆一个没有选区可依的命令没有处可用（与「复制元数据」同一处置） |
| 设封面时给真快捷键 | ⇧⌘C 已经是「拷贝路径」，为一年用不到几次的命令抢常用键位不值当 |
