# ADR 0004：重命名改磁盘上的真名

- 状态：已接受
- 日期：2026-10-01
- 相关代码：`src/gallery/core/metadata/rename.py`、`src/gallery/core/metadata/journal.py`、`src/gallery/ui/browser/rename_edit.py`

## 背景

用户对「相册」的心智模型就是访达里的文件夹：改名要在访达里做，看板上的名字
和在硬盘上的名字对不上，是这个软件最别扭的地方之一。于是有了这个需求：
**选中缩略图后再次点击即可重命名**。

这条需求与 AGENTS.md 的第一条红线（「绝不删除、移动或重命名用户照片」）正面冲突，
因此本 ADR 同时也是对那条红线的一次**显式豁免**：不是顺手绕过，而是写清楚边界、
写下后果，再改代码。

## 决策

### 1. 改磁盘上的真名，不搞「显示名」

`Path.rename` 直接改名。相册就是文件夹，所以相册改名 = 文件夹改名。

用户已经在这个软件的定位上明确选择了这一条。替代方案见文末。

### 2. 只改名，不搬家

目标永远是源文件所在的同一个目录，永不跨文件系统。因此：

- 不涉及「移动到另一个相册」这种需要复制大文件的操作；
- 不需要处理跨设备 rename 的拷贝 + 删除两段式；
- 失败只有一种：系统拒绝（同目录内的 `rename` 是原子的）。

### 3. 六条硬约束

| 约束 | 为什么 |
|------|--------|
| 目标已存在就报错，绝不覆盖 | POSIX 的 `rename` 会**静默**覆盖同名文件。被盖掉的是用户的另一张照片 |
| 照片不许改扩展名 | Gallery 按扩展名判断支持哪些格式；改成 `.png` 之后这个文件就不再被识别，等于删了它 |
| 名字不许以「.」开头 | 扫描器跳过以点开头的条目（`scanner.iter_entries`）。改完之后照片还在硬盘上，却从 Gallery 里消失了 |
| 名字不许带 `/` | 那是路径分隔符。改名不该变成移动 |
| 不许动库根目录与 `.gallery/` | 改了它们，Gallery 自己就找不到照片了 |
| 名字没变就什么都不做 | 连日志都不写：没有发生的事不该被记成发生过 |

### 4. 每次尝试都记账，撤销读的就是它

`.gallery/journal/YYYY-MM-DD.jsonl` 追加一行 JSON（时间、动作、从哪到哪、结果、失败原因）。
撤销读的就是它：重放整份日志，改名压栈、撤销弹栈，栈顶就是下一次 ⌘Z 要撤的那次。
（写这条 ADR 时这个重放还叫 `undo_last_rename`；后来「移到废纸篓」也进了同一摞栈，
代码搬到了 `src/gallery/core/metadata/undo.py`，见 ADR 0008。）

- **在动磁盘之前就被拦下的**（撞名、名字非法）不算一次写操作，不写日志：
  什么都没有发生，日志不该被用户的每一次回车淹没。
- **系统拒绝了 rename** 要写日志：用户需要知道「试过但没成」。
- **记账失败不撤销改动**，但界面必须如实说「没能记下操作日志，⌘Z 撤销不了」。
  两害相权：用户已经改好的文件不能因为记不上账就被说成没改成。

### 5. 相册改名不搬动内部内容

文件夹改名是 O(1) 的，文件夹里的照片一动不动，缩略图和路径全部照旧（缓存键含路径，
所以 `ThumbnailCache.relocate` 把磁盘缓存挪到新键上，避免留下永远命不中的孤儿条目）。

### 6. 界面照搬访达：再次点击 → 行内编辑

单击选中，**再点一次**进入行内编辑；双击仍然是打开。

**打开永远优先于改名**，这一点必须由机制保证，不能靠「两边的阈值刚好错开」：
Qt 是在第二次**按下**时判定双击的，而人的手不稳 —— 第二下按下去之后多按一会儿才抬起，
两次**抬起**的间隔就超过了双击阈值。按抬起时间判定改名的话，这一次操作会变成
「照片打开了，同时还弹出一个重命名输入框」。

所以第二次点击不立刻改名，而是**先按下双击阈值等一等**：这段时间里 Qt 若送来双击，
就去打开照片并撤销这次等待；一直没等到，才认定用户确实想改名。代价是输入框比手慢半拍
（约一个双击阈值的延迟），换来的是「双击打开」在任何手速下都不会被打断。

输入框盖在文件名那一行上（与绘制共用 `PhotoDelegate.label_rect`，保证严丝合缝）：
回车提交、Esc 取消、点到别处也提交；照片**只选中主干**，扩展名不会被手滑敲掉。

改名之后只替换模型里的那一行（`PhotoListModel.replace_entry`），**不重新扫描**：
改个名字而已，让整屏闪回占位框再一张张弹回来太蠢。内存里已经缩放好的缩略图顺手搬个家。

## 后果

- 红线不再是「绝不重命名」，而是「**除用户显式触发的改名外，绝不删除、移动或重命名**」。
  批量、脚本化、后台进行的改名一律不做。
- 改名会打断库外的引用：iCloud「优化存储」、Photos 图库、别的软件的收藏、
  别人分享出去的链接，都指向旧文件名。这是用户主动选择的代价，界面不隐藏它
  （改完立刻显示横幅告诉他新名字是什么），但也**不做任何补偿**。
- 相册改名等价于改名整个文件夹：里面的照片路径全变。Finder 里同名，同样行为。
- ⌘Z 只能撤销 Gallery 自己做过的改名，且以日志为准。用户在访达里改过的名字不会被撤销。
- 「存在即检查」与 `rename` 之间有一个极小的竞态窗口（在这两条指令之间、同一目录内、
  另一个进程恰好创建了同名文件）。单机桌面场景下这个窗口可以忽略；
  真要消除它得用 `link + unlink`，代价是对目录和不支持硬链接的卷都要分支，不划算。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 只改显示名、磁盘不动（存 `.gallery/`） | 与「`.gallery/` 里除 `config.toml` 外都是可重建缓存」冲突：用户自己起的名字删掉就没了，这正是 AGENTS 第 5 条说的设计缺陷 |
| 只改显示名、写进 XMP 标题（走 exiftool） | 照片可行，但**相册是文件夹、没有 XMP**，于是两张照片的功能不对称；而只改显示名在访达里看到的仍是旧名，绝大多数用户会觉得「这软件没改成功」 |
| 用 exiftool 改名而不是 `Path.rename` | exiftool 的 `-FileName=` 还要 `-overwrite_original`，且它的改名语义（改扩展名时同步改格式标记）正是这里要禁止的；多一个外部依赖换不来任何好处 |
| 批量重命名、模板改名 | 一次改错就是几十张照片找不到。v1 只做单个文件 |
| 不做撤销 | 这是唯一会动用户文件的操作，没有退路的设计不该存在 |
| 用标准 `QAbstractItemDelegate` 的编辑功能 | 它的触发时机与「再次点击」对不上，且照片的扩展名会被一起选中 |
