# ADR 0002：元数据面板的数据来源与展示形式

- 状态：已接受
- 日期：2026-10-01
- 相关代码：`src/gallery/core/metadata/exif.py`、`src/gallery/ui/viewer/metadata.py`

## 背景

M3 要展示照片的 EXIF / IPTC / XMP（只读）。**exiftool 子进程**格式覆盖最广，EXIF / IPTC / XMP /
MakerNotes 一次拿全且与将来的写回同源，代价是每个文件起一次进程（JPEG 约 40–80 ms）且本机不一定
装了它；**Pillow**读一张约 1 ms，但只读得到 EXIF，XMP 要额外引入 `defusedxml`，MakerNotes 完全拿不到。

## 决策

### 1. exiftool 优先，缺失时降级到 Pillow，并把降级如实说出来

优先跑 `exiftool -j -G -sort -charset utf8`，解析它输出的 JSON（键形如 `EXIF:Make`）。拿不到
exiftool（未安装、超时、输出不可解析）时改用 Pillow 读基础 EXIF，并在面板顶部写一行「少了什么、
怎么补上（`brew install exiftool`）」。**降级可以，假装没降级不行**：哪些字段是真的没有、哪些是
「这个来源读不到」，用户必须分得清 —— 实测 Pillow 只给出 12 个顶层标签，拍摄参数散落在 Exif 子 IFD
里，GPS 是三元组。

### 2. 只读，v1 不落盘

`core/metadata/exif.py` 不写任何文件；结果由界面按 `(路径, mtime_ns)` 在内存里做 LRU，`.gallery/`
里不新增只有这里才有的数据 —— 持久化留给 SQLite 索引。

### 3. 展示形式：右侧推挤式面板，精选字段 + 可展开全部

- `⌘I` 开关，状态记进会话；面板宽 300 px，**图片区域缩小并重新适配**。浮层式会盖住照片右半边，
  而用户此时正想看照片。
- 默认只显示一张**精选字段表**（拍摄信息 / 位置 / 图像 / 文件 / 内容），底部可切换「显示全部字段」
  看原始键值；空字段不显示、整组为空则整组不显示，否则面板大半是「—」。标签中文、值保持来源原样
  （`Canon EOS R6`、`1/500`），不翻译，避免自造术语。

### 4. GPS 与序列号正常显示

面板展示的是用户自己照片的元数据，全程本地、不上传；默认隐藏只会让用户更难确认「这张照片里到底有没有位置信息」。将来若做导出/分享，隐私处理放在那一步。

### 5. exiftool 调用可注入

`read_metadata()` 接受一个 reader 对象，默认实现去起子进程，测试注入假实现 —— 测试于是既不依赖本机装没装 exiftool，也不依赖它的输出格式细节。

### 6. 读取在后台线程

沿用 `TaskRunner`，面板先显示「正在读取元数据…」；那几十毫秒的进程开销放在主线程会让翻页卡顿。

## 后果

- 装没装 exiftool 功能都能用，只是信息量不同，**这一差异在界面上是可见的**。
- 面板字段表**集中定义**在 `core/metadata/exif.py` 的分组规格里，加字段只改一处；两个来源取值
  形态不同（exiftool 给 `1/500`，Pillow 给 `0.002`），格式化函数必须同时接受两种形态。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 只用 Pillow | 读不到 IPTC，XMP 需新增 `defusedxml` 依赖，MakerNotes 拿不到；与写回的字段集也不一致 |
| 只用 exiftool | 没装 exiftool 的用户在面板里什么都看不到，而装它需要 `brew install` |
| 面板做成浮层 | 会遮住照片；推挤式虽然让图片变小，但永远不挡内容 |
| 默认全量平铺字段 | 一张手机照片 60+ 字段，最该看的拍摄参数被淹没 |
| 把元数据写进 `.gallery/` 缓存 | 与「缓存可丢」原则无关的重复存储；SQLite 索引才是它的归宿 |
