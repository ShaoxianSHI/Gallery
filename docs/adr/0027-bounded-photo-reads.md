# ADR 0027：读一张照片必须有时限

- 状态：已接受
- 日期：2026-10-04
- 相关代码：`src/gallery/core/media/decode.py`、`src/gallery/core/media/thumbs.py`、
  `src/gallery/core/library/facade.py`、`src/gallery/ui/thumbs/pipeline.py`、
  `src/gallery/ui/tasks.py`、`src/gallery/ui/main_window.py`
- 相关：[ADR 0013](0013-filesystem-watch.md)（磁盘上多一张少一张就地改界面）、
  [ADR 0015](0015-thumbnail-pipeline-speedups.md)（缩放搬进工作线程）、
  [ADR 0005](0005-one-background.md)（一个后台入口）

## 背景

用户的照片放在 OneDrive 里。照片同步进来时，文件**已经在磁盘上**了 —— `stat` 给得出
正常的大小与修改时间，网格上立刻多一格，上级相册的封面也跟着换成了它。但数据本身
可能还没下载完，而 macOS 的文件提供器会让 `open()` **一直等**它把数据拉回来：没有
网络时，这一等就没有尽头。

于是出来三个现象，一个比一个严重：

1. 那一格的缩略图一直是黑的；
2. 大图打开也是黑的，元数据停在「正在读取」；
3. **⌘Q 退不出去，窗口关了、事件循环退了，进程还活着，只能强制退出**。

第 3 条是根因。缩略图流水线把解码放在 Qt 的线程池上，而 Pillow 的 `open()` 与
`load()` 都是**不可打断**的系统调用 —— 卡住的工作线程就永久没了。占满线程池之后
整条流水线停摆（于是 1 与 2）；而关窗时 `closeEvent` 等满 2 秒就放弃，紧接着 Qt 的
线程池在析构时又要 join 这些线程 —— **进程永远结束不了**。

顺带还查出一处同源的毛病：`Image.open(path)` 抛出来的 `OSError`（没权限、没下完）
原本一律被说成「文件可能已损坏或被截断」。那正是本仓库反复警告过不能说的话 ——
一次成功的移动会被说成数据损坏，用户很可能就此去抢救根本没坏的文件。

## 决策

### 1. 读文件放进守护线程，外面只等 :data:`READ_TIMEOUT_SECONDS`

`decode_rgba` 不再直接调 Pillow，而是把解码交给一个**守护线程**，自己最多等 20 秒。
超时就抛 `ImageDecodeError`，说的话是「可能还没下载完，或者正被别的程序占用」。

选守护线程而不是别的办法，是因为这是唯一能让「收不回来的那个」**不拖住进程**的做法：
`threading` 收尾时只 join 非守护线程。代价是超时的那个线程留在原地，因此另有一道前置条件
（`MAX_STUCK_READS`）：累积到 8 个就不再新开一个，直接报错 —— 真到了那一步，机器已经
读不动了，多等那 20 秒没有意义。

实测开销可以忽略：4000×3000 的 JPEG 冷解码约 45 ms，多开一次线程约 0.3 ms。

### 2. 等待的过程中问令牌，切库与关窗都能立刻放手

`decode_rgba` 接受 `should_cancel`（就是 `core.cancellation` 里那一个约定），等待时每
20 ms 问一次。`should_cancel` 一路从流水线与大图页传进来，于是关窗时那几个卡住的任务
会在几十毫秒内放手，⌘Q 不再被拖住。

### 3. 关窗丢掉排队里还没开始的任务

`cancel_all` 只动令牌，排队的那一批照样会一个个跑起来。`TaskRunner.abandon` 在取消
之后补一次 `QThreadPool.clear()`：一次丢进来几百张时，关窗要等的原本是
「排队个数 × 每个的时长」，那与「卡死」在界面上分不出彼此。

### 4. 「压根打不开」与「打开了但像素是坏的」分开说

文件由我们自己 `path.open("rb")`，然后把**文件对象**交给 Pillow。于是界线很清楚：
我们打不开 → 读不出 / 没下完 / 被占用；打开了之后 Pillow 失败 → 损坏或截断。
两个说法不会互相冒充。

### 5. 文件补完之后要能自己恢复

云盘下完会再报一次「创建」（同一个路径）。这一格必须**换一份新引用**，否则它一直挂着
半截时的大小与修改时间，缩略图缓存的 key 永远对不上；那份「这张读不出来」的记忆也要
一并清掉。否则用户看到的现象是「文件明明已经能读了，格子却永远是黑的」。

相册封面同理由 :meth:`Library.folder_cover` 的 `skip` 往后找：一张下到一半的照片不该
霸着一整张相册卡片的封面。整本相册都读不出来时要把原因说出来 —— 只画一个文件夹图形
等于什么也没说。

## 被否掉的备选

- **只靠 watchdog 忽略这些文件**：不成立。文件在 `stat` 层面完全正常，问题出在读。
- **把解码移出 Qt 线程池，换成自己的守护线程池**：能解决退出问题，但等于把 ADR 0015
  的优先级调度整个重写，而根因（没有时限）可以就地修掉。
- **只缩小线程池**：只是把停摆推迟，把退出问题原样留着。
