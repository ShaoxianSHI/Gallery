# ADR 0088：文件格式按格式名归组与检索，jpg 与 jpeg 是同一组

- 状态：已接受
- 日期：2026-10-24
- 相关 ADR：0009（按元数据分组与排序）、0026（搜索）、0049（统一的排序方向）、
  0074（按名称排序走拼音）
- 相关代码：`src/gallery/core/library/photos.py`、`core/metadata/facets.py`、
  `core/library/search.py`

## 背景

「分组 → 文件格式」的组键原先取的是**扩展名**，组名取的是**格式名**（`_FORMAT_LABELS`）。
两套口径在同一个格式有多个扩展名时就会撞车：`.jpg` 与 `.jpeg` 分成两张都叫「JPEG」的卡片，
`.tif` 与 `.tiff` 分成两张都叫「TIFF」的卡片。用户看不到任何区别，也不知道一张照片该进哪一组。

搜索那一侧同源：`#文件格式 JPEG` 只认成 `.jpeg`、`#文件格式 jpg` 只认成 `.jpg`，没有一种写法
能同时查到两批。界面说「格式」，实际做的是「扩展名」。

## 决策

### 1. 格式的判据只有 `_FORMAT_LABELS` 一处

- **分组**：组键与组名都用 `format_label` 的结果，组键不再带扩展名。
- **排序**：排序值也用格式名，同一格式的几个扩展名不会被排成两拨。
- **检索**：`#文件格式` 把用户敲的格式名或扩展名解析到它所属的格式，再取出该格式的**全部扩展名**
  （`format_suffixes`），SQL 用 `p.suffix IN (?, ?)`。

``jpg``、``JPEG``、``.jpeg`` 三种写法都落到「JPEG」这一个格式；``tif`` / ``TIFF`` 同理。
`.heic` 与 `.heif` 的标签本来就不同，仍然分成两组 —— 它们不是同一个名字的两份写法。

### 2. 扩展名不再是一个独立的筛选维度

想精确到扩展名仍然可以，但走文件名：`#文件名 .jpeg`。格式栏的语义固定为「格式」，
不再一半是格式、一半是扩展名。

## 后果

- 分组视图少一批同名卡片；一张照片属于哪个组不再取决于它当年被存成什么后缀。
- 检索与分组从此同一个判据：组里能看到的照片，`#文件格式 JPEG` 一定查得到。
- 排序按格式时同格式的照片并列，按文件名兜底（与所有字段同值时的做法一致），
  `.jpeg` 与 `.jpg` 会交错在文件名顺序里，而不是先排完一批再排另一批。
- 不需要迁移：分组状态只持久化字段 id（`group_facet="format"`），组键不落盘，索引 schema 不变。
- 格式栏的组卡片不再显示扩展名；进入组后照片名里仍然看得到。

## 被否决的方案

| 方案 | 否决理由 |
|------|----------|
| 组名改成「JPEG（.jpg）」与「JPEG（.jpeg）」 | 把「文件格式」这一栏改成「扩展名」栏；`tif` / `tiff` 也得跟着拆，用户还得记住每张属于哪一组 |
| 只改分组，搜索保持按扩展名 | 组里看得到 `.jpeg`、`#文件格式 JPEG` 查不到，同一天出现两套口径 |
| 组键保留后缀，只在显示时合并标签 | 两张同名卡片仍会各自存在，合并的只是文案，问题被掩盖而不是消失 |
| 把 `.heic` 与 `.heif` 也合并 | 标签本来就不同（HEIC / HEIF），属于「换格式名」的另一个决定 |
| 给分组卡片加后缀副标题 | 一张卡片的标题要同时回答两个问题，而扩展名在照片名里已经写着 |
