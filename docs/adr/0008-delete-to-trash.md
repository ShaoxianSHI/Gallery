# ADR 0008：删除 = 移到系统废纸篓，日志记账，随时可撤销

- 状态：已接受
- 日期：2026-10-01
- 相关代码：`src/gallery/core/metadata/trash.py`、`src/gallery/core/metadata/undo.py`、`src/gallery/core/metadata/journal.py`、`src/gallery/ui/main_window.py`、`src/gallery/ui/write_ops.py`

## 背景

需求：**⌘⌫ 把选中的照片 / 相册移除掉**。这与约束 1（「绝不删除、移动用户照片」）正面冲突。ADR 0004
已经为**重命名**做过一次显式豁免，这次是第二次，而且危险得多：改名错了照片还在，删错了就是没了。
因此先要说清楚「删掉」在这个软件里到底指什么，再谈怎么做。

## 决策

### 1. 「删除」= 移到系统废纸篓，任何情况下都不 unlink

被删的条目**改名搬家到废纸篓**，文件一个字节都没少，还躺在同一块盘上：

| 文件在哪 | 废纸篓在哪 |
|----------|------------|
| 启动卷（与 `/` 同一设备） | `~/.Trash` |
| 别的卷（外接硬盘、U 盘） | `<卷>/.Trashes/<uid>` |

这两个位置就是访达「废纸篓」自己读的位置，所以用户在访达里也能看见、也能还原 —— 即使 Gallery 已经
退出、日志被删干净，照片还在。同卷内这一步是一次 `rename`：原子的、瞬时的、不产生第二份数据。
**代码里没有 `unlink`、没有 `rmtree`**，删掉的东西永远只是「不在这个相册里了」。跨卷时 `rename` 返回
`EXDEV`，才退化成拷贝 + 删除：拷贝失败原文件分毫未动，删除只在拷贝成功之后发生。

**为什么不用系统的 `NSFileManager trashItem` / `send2trash`**：本机装不了新依赖（离线），而这条规则
本身只有十几行、可以被测试固定 —— 自己拥有它，跨平台降级（没有废纸篓概念的系统直接报「这个系统不
支持移到废纸篓」）和错误提示都更好控制。**为什么不放 `.gallery/trash/`**：那与约束 5 直接冲突 ——
「任何『只有缓存里才有』的数据都是设计缺陷」，照片放进缓存目录就等于告诉用户「删掉 `.gallery/` 没关系」。

### 2. 与重命名共用一摞撤销栈

⌘Z 只有**一摞**待撤销的写操作，改名和移到废纸篓都在里面，栈顶是最近一次：

```
改名 A → 删 B → ⌘Z（还原 B）→ ⌘Z（还原 A 的名字）
```

撤销是**照着日志重放**出来的，不是内存里的栈：改名压栈、撤销弹栈，弹空就没有了。每条日志记录都带一个
`batch`：一次批量删除里的每项各记一条但共用同一个 `batch`，于是**一次 ⌘Z 恢复一整批**。

### 3. 每一次尝试都记账，失败的也记

`.gallery/journal/YYYY-MM-DD.jsonl` 里追加 `trash` / `restore` 记录，字段与改名记录一致（`from` = 原路径，
`to` = 废纸篓里的实际路径）。在动磁盘之前就被拦下的（越权、目标是库根）不写日志；系统拒绝了才写，用户
需要知道「试过但没成」。记账失败不撤销已经完成的移动（照片已经在废纸篓里了），但横幅必须
如实说「没能记下操作日志，⌘Z 撤销不了」。

### 4. 界面照搬访达：⌘⌫ 直接删，不弹确认

- **不弹确认框**：访达里 ⌘⌫ 是不问的，废纸篓本身就是那层保险，再问一遍只是折磨。
- **横幅立刻告诉结果**：「已把 3 项移到废纸篓，⌘Z 可撤销。」—— 尤其删相册时说明「相册和里面的内容
  一起进了废纸篓」。**菜单里的「撤销」跟着栈顶变文案**：「撤销 移到废纸篓」/「撤销 重命名」，栈空时
  禁用 —— 用户在按之前就知道 ⌘Z 会撤掉什么。
- 缩略图**磁盘缓存不删**：文件还在，缓存命中就能秒回。内存里的预览与元数据缓存要清（它们按路径索引，
  而那个路径已经没有文件了）。

### 5. 网格支持多选，重命名仍然是单条

⌘⌫ 作用于当前选中的所有格子（⌘ 点、Shift 连选）。网格由 `SingleSelection` 改为
`ExtendedSelection`，删除时**从后往前**摘行，避免行号前移把自己搞乱。重命名保持单条（ADR 0004 的结论
不变）：批量改名一次改错就是几十张照片找不到。

### 6. 边界

| 约束 | 为什么 |
|------|--------|
| 只删库内的东西 | 与重命名同一条前置条件（`paths.is_within`） |
| 库根与 `.gallery/` 不许删 | 删掉它们，Gallery 自己就找不到照片了 |
| 恢复时原路径被占用就报错，**绝不覆盖** | 被盖掉的是用户的另一张照片 |
| 废纸篓里已经没有这一项，就如实说 | 用户可能清空了废纸篓、可能用访达还原过 |
| 大图页不能删 | 与重命名一致，⌘⌫ 只在网格页生效；大图里的照片回到网格再删 |

### 7. 撤销后的行插在哪

恢复出来的条目按**同一目录内的 (相册在前, 名字) 排序**插回网格 —— 与扫描器的顺序一致（`scanner` 按
名称排序输出）。如果这个目录里的兄弟节点一个都不在屏幕上了（用户把它们都删了），就追加到末尾：顺序在
下一次扫描时自然归位，程序不为了排序而重扫全库。

## 后果

- 那条约束第三次被显式收窄为：「**除用户自己触发的改名、移入废纸篓外，绝不删除、移动或重命名用户
  照片**」。代码里不存在会销毁用户文件的分支。
- ⌘Z 能撤的只有 Gallery 自己做过的操作，且以日志为准 —— 访达里改的名字、还原的废纸篓不会被撤销。
- 跨卷删除不是原子的：拷贝期间断电会留下原文件（安全）；拷贝成功后删除之前断电，废纸篓里多一份、原处
  少一份 —— 两者内容相同，日志里也记着，不会丢。
- 废纸篓满了、系统拒绝写入（只读卷、权限不足）时删除会失败，横幅给出可行动的中文原因。多选之后，
  「重命名」面对的仍只是 current item，两者语义不同，菜单里分开列。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 直接 `unlink` / `rmtree` | 一旦记账失败或用户清了 `.gallery/`，就是不可逆的数据损失。这个软件不提供不可逆的删除 |
| 库内 `.gallery/trash/` | 与约束 5 冲突（见决策 1），照片不能寄居在「随时可删」的缓存目录里 |
| 移到 `~/Pictures/.gallery-trash` 之类自建目录 | 同上，且还要自己管「清空」这件事 |
| 每次删除都弹确认框 | 访达不弹；废纸篓 + ⌘Z 已经是两层保险，弹窗只会让整理变得难用 |
| 删相册时二次确认并显示张数 | 数张数要扫一遍整棵目录树，大相册上要等好几秒。为一句提示付这个代价不值 |
| 每张一张撤销（一次删十张按十次 ⌘Z） | 与「一次 ⌘⌫ 是一次操作」的心智不符，撤销栈用 `batch` 归组即可解决 |
| 撤销后重新扫描整个库 | 删一张就闪回占位框太蠢；插行 + 顺序规则已经够（见决策 7） |
| 给删除单独一个快捷键（Shift+⌘⌫ 彻底删） | v1 不提供任何不可逆的删除入口 |
