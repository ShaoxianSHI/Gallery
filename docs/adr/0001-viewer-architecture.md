# ADR 0001：查看器架构与解码分层

- 状态：已接受
- 日期：2026-10-01
- 相关代码：`src/gallery/core/`、`src/gallery/ui/`

## 背景

Gallery 的第一个可用版本只需做到：选一个文件夹、看到照片概览、点开一张放大。一个只读查看器
并不需要索引 —— 目录遍历在本地磁盘上足够快，缩略图的失效判断只要 `(路径, mtime, 文件大小)`；
索引的价值要到元数据检索与实时刷新（M3/M4）才体现。

## 决策

### 1. 查看器先行，SQLite 索引推迟到需要元数据检索时

查看器是验证「core/ui 分层 + 后台线程模型 + 缓存可丢弃」这三条约束的最短路径。
索引 schema 一旦定下就有迁移成本，没有真实检索需求前不引入。

### 2. core 负责解码，返回裸像素；ui 只负责包装与绘制

`core` 不得导入 Qt，所以解码落在 `core`：`core.media.decode.decode_rgba(path, max_edge=...)`
返回 `RasterImage(width, height, rgba: bytes)`，界面侧用 `QImage(bytes, w, h, w * 4,
Format_RGBA8888).copy()` 包装 —— 解码、缩放与缓存于是都能在无事件循环、无屏幕的 pytest 下覆盖。
两个硬要求：`QImage` 的构造函数**不复制**缓冲区（`bytes` 一旦被回收就是花屏或崩溃），所以必须
`.copy()`；`QPixmap` 只能在 GUI 线程构造，工作线程只产出 `QImage`。

### 3. 大图采用两级加载

先解码到「视口长边 ×1.5」的预览立即显示，再在后台换全分辨率。JPEG 走 `Image.draft()`
按 1/2、1/4、1/8 缩放解码（快一个量级）；12MP 照片的 RGBA 约 48 MB/张、32MP 约 128 MB，
因此**全分辨率图像只保留当前这一张**，替换前先释放上一张，另缓存前后各一张的**预览**（LRU，
上限 3）以免换图白屏。**加载期间不清屏**：上一张留在画面上，只在右上角显示「正在载入…」
（延迟 150ms），解码失败用同一个角落提示、红色底。

### 4. 缩略图缓存可丢弃，key 覆盖全部失效条件

> **位置已被取代**：缩略图不再住 `<库根>/.gallery/cache/`，改按库路径摘要放 `<app cache>/thumbs/`
> （[ADR 0038](0038-unify-cache-location.md) 决策 1）；缓存格式另见
> [ADR 0015](0015-thumbnail-pipeline-speedups.md)。key 的构成与「删掉即可重建」这条约定不变。

key 由 `(绝对路径, mtime_ns, size, max_edge, THUMBNAIL_SPEC_VERSION)` 构成，
`THUMBNAIL_SPEC_VERSION` 变化（算法或 Pillow 大版本升级）即整批失效。带透明通道的存 PNG、
其余存 JPEG；超过上限（默认 2 GiB，`config.toml` 可调）后按修改时间做 LRU 清理。删掉缓存
必须能通过重新扫描恢复等价状态 —— 硬性约定，有测试守着。

### 5. 写入用户目录的行为只有一处，且必须先征得同意

> **已被取代**：[ADR 0038](0038-unify-cache-location.md) 决策 2 取消了这个三选一弹窗 ——
> 开场不再问「缓存放哪里」，库内一切进 `.gallery/`、缩略图进系统目录；`.gallery/` 建不出来时
> 自动降级成内存索引并横幅说明。原来的三个选项是「在库中缓存 / 缓存到系统目录 / 取消」。

### 6. 会话状态存 app 级目录，不进库

> **已被取代**：[ADR 0038](0038-unify-cache-location.md) 决策 4 把界面偏好挪成每库一份、存进该库
> 的 `config.toml`；「最近打开的库」与窗口几何仍留在 app 级。下面这段说的是当时。

`state.json` 放 `~/Library/Application Support/Gallery/`：读 `config.toml` 的时候还不知道库在
哪。也不用 `QSettings` —— plist 不透明、难以在测试里构造与断言。损坏时静默回退到默认值。

### 7. 大图容器用 `QGraphicsView`，不手写缩放

`QGraphicsView` + `QGraphicsPixmapItem` 自带坐标变换、滚动与平滑缩放，`AnchorUnderMouse` 让
缩放围绕光标、`ScrollHandDrag` 提供拖拽平移；自绘 `QWidget` 要自己实现这些，不划算。

### 8. v1 不引入 pytest-qt

Qt 相关的可测逻辑（适配缩放比例、可见区优先级队列）抽成不依赖 Qt 的纯函数模块
（`ui/viewer/zoom.py`、`ui/thumbs/queue.py`），用普通 pytest 覆盖，`ui/` 其余靠离屏冒烟脚本验证。

### 9. 缩略图尺寸用三个离散档位，且每行按窗口宽度铺满

档位为 **112 / 176 / 288 像素**（小 / 中 / 大，默认「中」），用触控板捏合、`⌘`+滚轮或
「视图 → 缩略图大小」切换。

- **为什么离散**：磁盘缓存按固定长边生成，离散档位让「同一张照片」的缓存组合保持少量且
  稳定；连续缩放要么逼出「每个系数一份缓存」，要么永远糊一层。**连续事件还要累积**：捏合与
  触控板滚轮都是一连串小增量，每来一个就切档会从最小直接跳到最大，所以先经累加器累积够
  阈值（捏合 0.1）再切一档。
- **档位是目标而不是结果**：格子实际宽度由视口宽度决定 —— 先按档位挑一个列数，再把可用
  宽度整除分给各列，每行铺满、右侧不留空白，状态栏同时报出档位与实际长边（例如
  「中 · 实际 178 像素」）。最大档 288 不超过缓存长边（默认 512），放大档位不会把小图拉大
  —— 这条不变量由测试守着。
- **Qt 的换行宽度与视口宽度并不严格相等**，宽窗口下会少摆一列、右侧留下整整一列空白。
  与其猜公式，不如排完版后核对一次实际列数（延迟 50ms 等布局稳定），少了就按实测列数重算。
  **量出来的数只对「按当前形态排过版」的那一屏成立**：模型刚换过形态（卡片式 ↔ 分区式）而
  按新形态的重排还没落地时，标题在卡片式的固定格子里只占一格，第一段会被它挤掉一列 ——
  这不是 Qt 摆不下，不能据此修正。修正按宽度记着，只有宽度变过才清，所以按错数修正的后果
  是这一层长期少一列，直到用户换一次档或改一次窗口宽度。
- **滚轮的阈值是 12 像素，不是「角度增量 120」**：Qt 的 macOS 层按设备有没有精确滚动给的是
  **两套单位** —— 传统滚轮给角度增量（一格 120），魔法鼠标与触控板给的是**像素增量**，角度
  那一份只按「1 像素 = 2 个角度单位」折算（一格只有 4，见 Qt 的 `qnsview_mouse.mm`），照角度
  卡阈值会让同一个动作在两种设备上差三十倍。所以先把两份增量折到同一个单位
  （`thumb_sizes.wheel_delta`，有像素就用像素，只给角度的按 120 角度单位 = 20 像素折过去），
  再按 **12 像素**卡：一格是 20，阈值略低于它，好让一格报不足一整行的高精度滚轮也切一档。
- **捏合要限速，键盘与滚轮要排队**：切档带一段 160ms 动画，而网格是「上一段没跑完就不接
  第二段、直接一步落位」的。捏合的意图本来就是连续的，间隔不足的那几下**直接丢掉**
  （限速 220ms，必须不短于动画）；`⇧⌘↑`/`⇧⌘↓` 与 `⌘`+滚轮是每一下都独立的意图，于是
  **排着**等上一段动画跑完再执行（反向连按互相抵销）。**切档不清空画面**：内存里按旧边长
  缩放的缩略图保留，由委托就地缩放到新框显示（略软），新图到了原地替换；清空再重取会让
  整屏先闪成占位框再一张张弹回来。窗口宽度变化导致的长边变化小于 6 像素时不重取。

### 10. 相册模式与平铺模式并存，同一层里相册排在照片前面

- **平铺模式**（默认）：一次递归整库，把所有照片铺在一起。**相册模式**逐层展开：一个子文件夹
  就是一个相册，双击进入，每层只列当前目录、相册在前。两种都保留 —— 想找一张记得大概样子的
  照片时平铺扫一遍最快，按文件夹梳理时逐层进入才看得清结构，所以做成可切换的浏览方式而不是
  改默认行为。**逐层列举走 core 的 `iter_entries` 而不是 `iter_photos`**：相册模式绝不能顺手把
  整棵树走一遍，那等于把平铺模式的代价又付了一次。**界面不许走出库**：`enter_folder` 用
  `paths.is_within` 把关，越界一律拒绝（有测试）。
- **空相册不反复问**：没有封面就画文件夹图标，并把这个路径记进「问过了」的集合。**相册封面
  = 文件夹里找到的第一张照片**（找到即停），不按时间排序取第一张：封面只需要「有张图」。

## 后果

- `core` 保持可脱离 Qt 测试；`ui` 里不允许出现 `PIL`、`open()` 原图。
- 解码路径唯一：任何缩略图与预览都必须经过 `core`，便于将来统一加入颜色管理或 RAW 支持。
- 内存占用有明确上限（全图 3 张 + 缩略图 LRU），不随库规模增长。
- 库内写入只有 `.gallery/` 一处；缩略图是例外，按库路径摘要放系统缓存目录（ADR 0038）。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| `ui` 直接用 `QPixmap(path)` 加载 | 违反分层，HEIC 支持与方向纠正会散落在界面层；解码无法脱离 Qt 测试 |
| 缩略图统一存 PNG | 体积约为 JPEG 的 5～8 倍，5000 张库会到 GiB 级，而照片缩略图不需要无损 |
| 缩略图统一存 JPEG | 带透明通道的 PNG/WebP 透明区域会变黑 |
| 静默创建 `.gallery/` | 违背「默认只读、写入显式」，用户只是想看一眼照片时不应留下痕迹 |
| 用 `QSettings` 存会话状态 | plist 不透明、难以在测试里构造与断言（见决策 6） |
| RAW（CR2/CR3/NEF/ARW）支持 | Pillow 覆盖差，需要引入 rawpy 新依赖，另起 ADR 评估 |
