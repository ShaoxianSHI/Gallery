# ADR 0001：查看器架构与解码分层

- 状态：已接受
- 日期：2026-10-01
- 相关代码：`src/gallery/core/`、`src/gallery/ui/`

## 背景

Gallery 的第一个可用版本要能完成一件事：选一个文件夹，看到里面的照片概览，点开其中一张放大查看。
README 的路线图原本把「库扫描与索引（SQLite）」列为 M1、「浏览界面」列为 M2。但一个只读查看器并不需要索引：

- 目录遍历在本地磁盘上足够快，可以直接流式展示；
- 缩略图缓存的失效判断只需要 `(路径, mtime, 文件大小)`，不需要元数据索引；
- 索引真正的价值在元数据检索与实时刷新（M3/M4）时才体现。

因此本 ADR 把查看器提前到索引之前，并固定查看器的分层与解码策略。

## 决策

### 1. 查看器先行，SQLite 索引推迟到需要元数据检索时

查看器是验证「core/ui 分层 + 后台线程模型 + 缓存可丢弃」这三条约束的最短路径。
索引 schema 一旦定下就有迁移成本，在没有真实检索需求前不引入。

### 2. core 负责解码，返回裸像素；ui 只负责包装与绘制

`core` 不得导入 Qt，因此解码必须落在 `core`：

- `core.media.decode.decode_rgba(path, max_edge=...)` 返回 `RasterImage(width, height, rgba: bytes)`；
- `ui` 侧用 `QImage(bytes, w, h, w * 4, Format_RGBA8888).copy()` 包装成 Qt 图像。

这条约束的直接收益：解码、缩放、缓存逻辑全部可以在没有事件循环、没有屏幕的环境下用 pytest 覆盖。

**两个必须遵守的实现细节：**

1. `QImage` 的构造函数**不复制**传入的缓冲区，Python `bytes` 一旦被回收就是花屏或崩溃，所以必须 `.copy()`。
2. `QPixmap` 只能在 GUI 线程构造（`QImage` 可以在工作线程）。工作线程产出 `QImage`，转 `QPixmap` 一律回主线程。

### 3. 大图采用两级加载

先解码到「视口长边 ×1.5」的预览立即显示，再在后台换全分辨率：

- JPEG 走 `Image.draft()`，按 1/2、1/4、1/8 缩放解码，速度快一个量级；
- 12MP 照片的 RGBA 约 48 MB/张，32MP 的约 128 MB，因此**全分辨率图像只保留当前这一张**，
  替换前先释放上一张；界面另缓存当前照片前后各一张的**预览**（LRU，上限 3），换图时不白屏。
- **加载期间不清屏**：上一张继续留在画面上，只在右上角显示「正在载入…」（延迟 150ms 出现，
  加载快时根本不闪）；解码失败也用同一个角落提示，红色底。切图时闪一下黑屏比多等一会儿刺眼得多。

### 4. 缩略图缓存可丢弃，key 覆盖全部失效条件

缓存文件位于 `<库根>/.gallery/cache/thumbs/<sha1>.<jpg|png>`，key 由
`(绝对路径, mtime_ns, size, max_edge, THUMBNAIL_SPEC_VERSION)` 构成。
`THUMBNAIL_SPEC_VERSION` 变化（算法或 Pillow 大版本升级）即整批失效。
带透明通道的图存 PNG，其余存 JPEG(q=85)。
缓存超过上限（默认 2 GiB，`config.toml` 可调）后按修改时间做 LRU 清理。

删掉 `.gallery/cache/` 必须能通过重新扫描恢复等价状态——这是硬性约定，有测试守着。

### 5. 写入用户目录的行为只有一处，且必须先征得同意

首次打开一个还没有 `.gallery/` 的库时，弹窗询问：

- **在库中缓存**（默认推荐）：创建 `.gallery/config.toml` 与 `.gallery/cache/thumbs/`；
- **缓存到系统目录**：库目录保持一个字节都不写，缓存落到
  `~/Library/Application Support/Gallery/cache/<库路径 sha1>/`，功能不降级；
- **取消**：不打开。

任何情况下都不写入照片目录里的其他位置，也绝不修改原图。

### 6. 会话状态存 app 级目录，不进库

「最近打开的库」和窗口几何存在 `~/Library/Application Support/Gallery/state.json`。
不能存进库里的 `config.toml`——读它的时候还不知道库在哪。也不用 `QSettings`：
plist 不透明、难以在测试里构造与断言。状态文件损坏时静默回退到默认值（它不是数据，丢了无所谓）。

### 7. 大图容器用 `QGraphicsView`，不手写缩放

`QGraphicsView` + `QGraphicsPixmapItem` 自带坐标变换、滚动与平滑缩放，
`AnchorUnderMouse` 让缩放围绕光标，`ScrollHandDrag` 提供拖拽平移。
自绘 `QWidget` 需要自己实现这些，收益只是「更可控」，在本项目里不划算。

### 8. v1 不引入 pytest-qt

Qt 相关的可测逻辑（适配缩放比例、可见区优先级队列）抽成不依赖 Qt 的纯函数模块
（`ui/viewer/zoom.py`、`ui/thumbs/queue.py`），用普通 pytest 覆盖。
`ui/` 的其余部分是装配代码，靠离屏冒烟脚本验证。新增依赖需要更新 README 并说明理由，
目前 pytest-qt 带来的价值不值得这笔账。

### 9. 缩略图尺寸用三个离散档位，且每行按窗口宽度铺满

档位为 **112 / 176 / 288 像素**（小 / 中 / 大，默认「中」），用触控板捏合、
`⌘`+滚轮或「视图 → 缩略图大小」切换。

- **为什么离散**：缩略图磁盘缓存按固定长边生成，离散档位让「同一张照片」的缓存组合
  保持少量且稳定；连续缩放要么逼出「每个系数一份缓存」，要么永远糊一层。
- **档位是目标而不是结果**：格子的实际宽度由视口宽度决定 —— 先按档位挑一个列数，
  再把可用宽度整除分给各列，因此每行都铺满，右侧不会留一块空白。
  状态栏会同时报出档位和实际长边（例如「中 · 实际 178 像素」）。
- **上限**：最大档 288 不超过缓存长边（默认 512），因此放大档位不会把小图拉大。
  这条不变量由测试守着。
- **Qt 的换行宽度与视口宽度并不严格相等**：实测在宽窗口下会少摆一列，于是右边
  留下整整一列的空白。与其猜公式，不如排完版后核对一次实际列数（延迟 50ms，
  等布局落定）：真的少了，就按实测列数重算并留出安全边距，保证这次摆得下。
- **连续事件要攒**：捏合与触控板滚轮都是一连串小增量，每来一个就切档会从最小直接跳到最大，
  所以先经累加器攒够阈值（捏合 0.1）再切一档。
- **滚轮的阈值是 12 像素，不是「角度增量 120」**（这一条后来改过，见下）：
  Qt 的 macOS 层按设备有没有精确滚动给的是**两套单位** —— 传统滚轮给角度增量（一格
  120），魔法鼠标与触控板给的是**像素增量**，角度那一份只按「1 像素 = 2 个角度单位」
  折算（一格只有 4，见 Qt 的 `qnsview_mouse.mm`）。照角度卡阈值，同一个动作在两种设备上
  差三十倍，症状是「魔法鼠标滚一格什么也不发生」。于是先把两份增量折到同一个单位
  （`thumb_sizes.wheel_delta`，有像素就用像素，只给角度的按 120 角度单位 = 20 像素折过去），
  再按 **12 像素**卡：一格是 20，阈值略低于它，好让一格报不足一整行的高精度滚轮也滚一格
  就切一档。传统滚轮那一侧手感不变 —— 网格一次事件只发一个 ±1，多余的档位由累加器的余量吸收。
- **捏合还要限速，键盘与滚轮要排队**：切档带一段 160ms 的动画，而网格是「上一段没跑完
  就不接第二段、直接一步落位」的。手势快起来切档比动画还快，于是每一次切档都掐断上一次，
  画面只是一连串跳变。两条路径的取舍不同 —— 捏合的意图本来就是连续的，间隔不足的那几下
  **直接丢掉**（限速 220ms，必须不短于动画，否则限速形同虚设）；`⇧⌘↑`/`⇧⌘↓` 与 `⌘`+滚轮
  是每一下都独立的意图，丢掉一下就是丢了一次明确的操作，于是**排着**等上一段动画跑完再
  执行（反向的连按会互相抵销）。
- **切档不清空画面**：内存里按旧边长缩放的缩略图保留下来，由委托就地缩放到新框显示
  （略软），新图到了原地替换。清空再重取会让整屏先闪成占位框、再一张张弹回来，
  这种「适应自身大小」的闪烁比稍微软一点难看得多。窗口宽度变化导致的长边变化
  小于 6 像素时不重取。

### 10. 相册模式与平铺模式并存，同一层里相册排在照片前面

- **平铺模式**（默认）保持原行为：一次递归整库，把所有照片铺在一起。
- **相册模式**逐层展开：一个子文件夹就是一个相册，双击进入；每层只列当前目录，
  相册在前、照片在后。
- **两种都保留**：想找一张记得大概样子的照片时，平铺扫一遍最快；按文件夹梳理时，
  逐层进入才看得清结构。它们不是替代关系，所以做成可切换的浏览方式而不是改默认行为。
- **逐层列举走 core 的 `iter_entries`，不是 `iter_photos`**：相册模式绝不能顺手把整棵树
  走一遍 —— 那等于把平铺模式的代价又付了一次。
- **界面不许走出库**：`enter_folder` 用 `paths.is_within` 把关，越界一律拒绝（有测试）。
  库是用户划定的边界，界面不能自己扩张它。
- **空相册不反复问**：没有封面就画文件夹图标，并把这个路径记进「问过了」的集合。
- **相册封面 = 文件夹里找到的第一张照片**（找到即停），不按时间排序取第一张：
  封面只需要「有张图」，为此遍历整个相册不划算。

## 后果

- `core` 保持可脱离 Qt 测试；`ui` 里不允许出现 `PIL`、`open()` 原图。
- 解码路径唯一：任何缩略图与预览都必须经过 `core`，便于将来统一加入颜色管理或 RAW 支持。
- 内存占用有明确上限（全图 3 张 + 缩略图 LRU），不会随库规模增长。
- 库目录在用户拒绝时完全只读，代价是缓存散落在系统目录里。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| `ui` 直接用 `QPixmap(path)` 加载 | 违反分层，HEIC 支持与方向纠正会散落在界面层；解码无法脱离 Qt 测试 |
| 缩略图统一存 PNG | 体积约为 JPEG 的 5～8 倍，5000 张库会到 GiB 级，而照片缩略图不需要无损 |
| 缩略图统一存 JPEG | 带透明通道的 PNG/WebP 透明区域会变黑 |
| 静默创建 `.gallery/` | 违背「默认只读、写入显式」，用户只是想看一眼照片时不应留下痕迹 |
| 用 `QSettings` 存会话状态 | plist 二进制、不透明，测试需要真实用户目录 |
| RAW（CR2/CR3/NEF/ARW）支持 | Pillow 覆盖差，需要引入 rawpy 新依赖，另起 ADR 评估 |
