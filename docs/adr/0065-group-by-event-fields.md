# ADR 0065：按事件字段分组 —— 「分组 → 旅行 / 演出 / 影片」

- 状态：已接受
- 日期：2026-10-17
- 相关 ADR：0043（事件体系，本条延伸其决策 7）、0045（演出）、0063（影片事件）、0038（东西只放两个位置）
- 相关代码：`src/gallery/core/metadata/facets.py`、`src/gallery/core/events/store.py`、
  `src/gallery/core/events/models.py`、`src/gallery/ui/window/ordering.py`

## 背景

分组里与事件相关的只有一条「事件」：一张照片属于哪几次事件就归成几张组卡片。但用户的问法常常是
「按目的地看看所有旅行」「按艺人看看演出」「按番号看看影片」—— 关心的是事件**字段值**，不是事件本身。

事件字段来自 Gallery 自己的库（`events.db` 的扩展表），既不在照片文件上也不在 EXIF 里，所以它
不能走 `PhotoFacets` 那一套：那是「从照片读出来的元数据」，而它可以被下一次索引重建抹掉
（ADR 0043 决策 1 的同一条理由）。

## 决策

### 1. 每一类事件的字段各生成一族分组字段，只含类型独有的字段

字段 id 形如 `event_field:trip:destination`，由 `EventKind.fields` 生成，显示名是「旅行 · 目的地」。
**公共列不进这一族**：按名称分组与「事件」那一档重合，按日期分组与拍摄时间那一档重叠，按备注分组
没有意义。

### 2. `EventRef` 带上这类事件独有字段的文字值

`EventStore.events_for_photos` 在取绑定与事件本体时按类型各接一张扩展表，把这类字段的值一并带回
（几十条事件、一层查一次，与原来那条 JOIN 同一次）。分组算法一行不改：`FacetInput.events` 本来就是
为多归属准备的。

### 3. 「事件那一族」只有一个判据：`facets.is_event_facet`

`needs_metadata` 要为这一族开口子（否则点一次「按旅行·目的地分组」会先起一个后台任务把整库 EXIF
重读一遍），界面据同一个判据决定「要不要在后台取那份事件映射」（`ordering._needs_facet_read`）与
「事件改了要不要重排」（`ordering._groups_by_event`）。判据只此一处，两处各写一遍就会有一处漏掉，
而漏掉的那一处不报错 —— 只是「记完照片，组卡片没变」。

### 4. 菜单挂在「事件」旁边，按类型分三层

「视图 → 分组」里「事件」之后依次是「旅行 / 演出 / 影片」三个子菜单，右侧列出这一类自己的字段。
挑一个就是把这一层按那一栏归拢。菜单项与其余分组项共用一份 `_group_actions`，勾选状态与从
`config.toml` 恢复出来的选择因此走同一条路。

## 后果

- 组键是字段值本身（多值字段按顿号 / 逗号拆开，与关键词同款的多归属）；多个事件写了同一个值时
  同一张照片只进那一组一次。
- 没填这一栏（或不属于这一类事件）的沉到末尾，标题是「未填目的地」这类。
- 数字与日期字段按数值排，其余按名称；方向仍然只由「逆序」一档决定（ADR 0049）。
- 改一次事件之后按它字段分的那一层当场重排。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 把事件字段写进照片的 `PhotoFacets` / 索引 | 事件是重建不出来的用户数据，塞进可重建的缓存表等于让它被下一次索引重建抹掉 |
| 分组时另传一份 `event_id → Event` 的映射 | `build_groups` 只收每张照片的引用；多一条映射就多一处「什么时候失效」要记，而事件改动的那条重排判据会失去对象身份这一层保障 |
| 把公共列（名称、日期、备注）也列进子菜单 | 与「事件」「拍摄时间」两档重合，摆出来只会让人在两个看起来一样的选择之间挑 |
| 一类事件的字段平铺进「分组」主菜单 | 演出有十几个字段，平铺会把主菜单撑到看不见其余字段 |
