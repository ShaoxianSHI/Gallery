# ADR 0019：照片右键菜单里的「复制到相册」与「移动到相册」

- 状态：已接受
- 日期：2026-10-08
- 相关代码：`src/gallery/core/library/scanner.py`、`src/gallery/core/metadata/transfer.py`、`src/gallery/core/metadata/naming.py`、`src/gallery/core/metadata/journal.py`、`src/gallery/core/metadata/undo.py`、`src/gallery/core/library/facade.py`、`src/gallery/ui/menus.py`、`src/gallery/ui/main_window.py`、`src/gallery/ui/write_ops.py`
- 相关：[ADR 0018](0018-paste-into-current-folder.md)（⌘V 粘进当前这一层）、[ADR 0017](0017-copy-file-to-clipboard.md)（⌘C 往剪贴板里放文件）、[ADR 0013](0013-filesystem-watch.md)（新文件怎么显示）、[ADR 0004](0004-rename-on-disk.md)（约束 1）

## 背景

访达的右键菜单里，「拷贝」「拷贝路径」旁边还有一组「把它放到别处去」。Gallery 加到 ⌘C
（ADR 0017）与 ⌘V（ADR 0018）之后，⌘V 只能粘进**当前这一层** —— 用户站在「京都」里按
⌘V，剪贴板里的照片就落进「京都」，而他真正想做的是「挪到奈良去」。要挪就得先在网格里
找到那个相册、切进去、⌘V、再切回来，一趟只为搬几张照片。

用户的要求是：在照片的右键菜单里加两条 —— **复制到相册**与**移动到相册**，摆在
**拷贝路径下面**，且**不设快捷键**。

**「移动到相册」是本项目里第一个会让用户的照片离开原处的操作**，而约束 1 写的是
「绝不删除、移动用户照片」。所以下面几件事要先定死，尤其是「凭什么它可以存在」。

## 决策

### 1. 子菜单列**全库**的相册，标签是相对路径

用户在两个选项里选了「整个库的全部相册」：任意一张照片要能直达任意一个相册。

- **标签写相对路径**（``2025/苏州``，顶层相册就是它自己的名字），不是单纯的名字 ——
  两个年份下面各有一个「苏州」，只写「苏州」用户分不清自己要挪到哪去。
- **按路径序排，一个相册紧跟着它自己的子树**（``京都`` → ``京都/大阪`` → ``京都/宇治``
  → ``奈良``）。判据是**逐段比较**，不是字符串整体排序（后者会把 ``京都2`` 插进 ``京都``
  的子树中间），也不是深度优先的先序（那会让同一个相册的下级散落在整棵树的各处）。
- **清单每次弹出时现列**：用户在访达里新建一个相册，下一次右键就能选到，不必重开软件。
- 代价是相册多时子菜单会很长、需要滚动。用户明确选了「全部」，那就这样。

`recursive` 配置在这里**不生效**：它管的是「全部照片」那个平铺视图要不要扎进子目录，
而逐层浏览任何时候都能进到子相册去。用户把照片移进一个子相册，那个相册在相册视图里
立刻就看得见，不该因为他当初选了「不递归」就挑不了它。

### 2. 复制复用粘贴，移动是新写的一个

「复制到相册」与 ⌘V 是**同一个动作** —— 把若干项变成目标目录里的新文件。因此它们共用
`core.metadata.paste.copy_into`，也共用 `journal` 里 `action=paste` 那一种记录；差别只在
源是剪贴板还是网格里的选择。不另写一份，免得两条「不覆盖」的规矩各自漂移。

「移动到相册」是新的：`core.metadata.transfer`（`move_into` / `undo_move_records`）。

### 3. 移动**进撤销栈** —— 它凭什么可以存在

撤销一次粘贴是删文件，而删除只允许用户在界面上**亲手触发**（约束 1），所以粘贴只记账
（ADR 0018 决策 4）。**撤销一次移动仍然是一次移动**：东西一直都在，只是回到了它原来
待着的地方。于是移动进 `undo._PUSH_ACTIONS`，⌘Z 把它挪回原来的相册。

除了「只在界面上由用户亲手触发」之外，移动满足约束 1 的其余各条：

| 约束 | 移动怎么满足 |
|---|---|
| 不主动动用户文件 | 没有任何后台整理、批量脚本；入口是菜单里那一条，点了才会动 |
| 不改内容 | 像素、EXIF、修改时间一个字节都不改；同卷内只是一次 `rename` |
| 有据可查 | 每一项都写一条 `action=move` 的 journal，一次操作的多项共用一个 `batch` |
| 能退回去 | ⌘Z 一次撤一整批；撤不掉的部分如实报告，不假装成功 |

**原位置被占了就不动它**（与取回废纸篓同一个取向）：用户在这期间自己放了东西进去，
替他腾出位置等于删掉那个东西 —— 那需要用户亲手做。

### 4. 绝不覆盖；已经在那儿就**复制一份**

目标已有同名时按**访达自己的规矩**改叫「一张 2.jpg」，绝不覆盖 —— 那里可能有用户自己
放进去的、还没处理的文件。这条规则原先写在 `paste.py` 里私有的 `_free_name`，现在收到
`core.metadata.naming.free_name_in`，**几处调用方（改名、粘贴、造副本、移动）共用一份实现**。

本来就在目标相册里的**复制一份**（`一张.jpg` → `一张的副本.jpg`）：用户挑了「移动」却什么都
没发生，那是把按下的那个键当成了没按。「已经在那里」按**磁盘上的真实位置**判断（两边都
`resolve()` 过）—— macOS 上 `/var` 链到 `/private/var`，不解析就会把照片真的移走，
而用户要的只是留一份副本。

> **这一条原先是「原样跳过」**，由 [ADR 0044](0044-duplicate-in-place.md) 决策 3 推翻。
> 这一份走粘贴那一条路：记 `action=paste`、**不进撤销栈**（源路径原封不动，「挪回去」无从
> 谈起，而删掉副本就是约束 1）、事件绑定不跟着搬（ADR 0044 决策 5）。

### 5. 两条都只给**照片**菜单

用户要的是照片的菜单。**相册菜单里不出现这两条**：搬相册会牵动整棵子树，照片数量与耗时
都不可预计，而约束 1 明确排除「批量整理」「后台整理」。想挪相册请去访达。

> **已补**（见 [ADR 0020](0020-group-card-operations.md)）：**分组菜单里现在有这两条**。
> 摊平之后它们作用的是组内的**照片**（不是照片所在的目录），所以这条决策真正要挡的
> 「搬相册」那一半依然成立，被挡住的只有搬文件夹。

### 6. 三个写入类任务共用**一道**前置条件

⌘V、复制到相册、移动到相册都会往某个目录里落文件，撞上同一个目标名字时后到的会把
先到的盖掉 —— 那是这个项目最不能出现的一种事。因此它们共用 `MainWindow._write_job`
这一个槽（原先只有粘贴用的 `_paste_job`）。三者都在后台线程上跑（大照片一个几百 MB）。

### 7. 摆放与快捷键

两条摆在**「拷贝路径」正下方、「粘贴」上面**（用户指定的位置）：三者都是「把这一堆东西
放到别处去」，挨在一起才是一族。**不设快捷键**（用户明确要求）：这两条要挑目标，
没有「一个键 = 一个动作」的对应关系。

多选时两条**仍然留着** —— 它们作用于整个选择，而「把这一堆东西挪到那儿去」正是多选
最想干的事。

**库里一个相册都没有时那两条压根不出现**：空子菜单点开是个空框，与「粘不了就不出现」
（ADR 0018 决策 6）、「永远点不动的不如不出现」（ADR 0014 决策 4）同一个取向。

## 后果

- 网格上「会动用户文件」的入口从三个变成**四个**：重命名、移到废纸篓、粘贴、移动到相册。
  其中**三个**进 ⌘Z 撤销栈（粘贴仍然不进）。
- 照片菜单第一次有了**子菜单行**，于是右箭头改由 `ShortcutColumnMenu` 画进最右那一列
  （`owns_submenu_arrows`），与空白处那张菜单一致。样式表测试已跟着改。
- **移走的东西由监听器（ADR 0013）自己从这一层里摘掉**：刻意不重扫当前这一层 ——
  重扫会把网格清空，选中与滚动位置全丢。
- **撤销移动之后不替界面决定往网格里插哪一行**：挪回来的东西不一定在当前这一层
  （用户在哪个相册点的移动，撤回来时人就站在哪儿），所以 `UndoResult.entries` 是空的，
  由监听器去发现，横幅只说发生了什么。
- 跨卷（库在外接盘上、相册横跨两个卷）时 `rename` 返回 `EXDEV`，退化成拷贝 + 删除，
  且**删除只在拷贝成功之后发生**（与 `core.metadata.trash` 同一套做法）。
- 取消只在**项与项之间**生效：移一半停下来会让用户自己都说不清哪些被移了，那比移完更糟。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 子菜单只列当前这一层的相册 | 深层相册里的照片就挪不到别处去了；用户明确选了「全部」 |
| 标签只写相册的名字 | 两个年份下的「苏州」分不清；访达的路径栏也是相对路径 |
| 复制与移动各写一份实现 | 两条「不覆盖」「已经在那儿就跳过」的规矩迟早漂移（ADR 0018 决策 3 已有先例） |
| 移动不进撤销栈（只记账） | 那样用户就是在用一条**不可逆**的命令整理自己的照片库；撤销一次移动仍然是移动，约束 1 不拦 |
| 撤销移动 = 把文件挪回，若原位置被占就改个名 | 替用户腾位置要删掉他放进去的东西，那是删除 |
| 移动相册（相册菜单里也给这两条） | 一次动辄整棵子树，属约束 1 排除的「批量整理」；用户要的是照片 |
| 给这两条设快捷键 | 要挑目标，没有「一键 = 一动作」的对应；用户明确不要 |
| 移走之后立刻重扫当前这一层 | 会清空网格（选中与滚动位置全丢），而监听器已经把该做的做完了 |
| 每一项弹一次确认 | 访达不这么做；用户要的就是「点了就去」 |
| 把 `.gallery` 也列成可选相册 | 照片挪进去就再也不会被扫到（扫描跳过隐藏项），等于 Gallery 自己弄丢了 |
