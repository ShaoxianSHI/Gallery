# ADR 0049：相册、组卡片、照片共用一个排序方向

- 状态：已接受（决策 1 由本条自己修订过一次，见「决策 1 的修订」）
- 日期：2026-10-08
- 相关 ADR：0009（分组与排序）、0028（相册封面）
- 相关代码：`src/gallery/core/library/groups.py`、`src/gallery/core/metadata/facets.py`、
  `src/gallery/ui/window/ordering.py`、`src/gallery/ui/write_ops.py`

## 背景

网格这一层上摆着三种东西，而它们原先各有各的排序规矩，彼此不通气：

| 内容 | 原先的顺序 | 受「视图 → 排序 → 逆序」影响？ |
|------|-----------|------------------------------|
| 相册卡片 | 永远按名称升序（`scanner._sort_key`、`model._sort_key`） | 否 |
| 组卡片 | 时间类新→旧，其余按名称升序（`Facet.newest_first`） | **否** |
| 照片 | 选中的字段 + 「逆序」 | 是 |

于是有两处读起来像出了毛病：

1. **同一层里两样东西朝着相反的方向**。相册卡片 A→Z，按月份分出来的组卡片却是 2026 → 2023。
   两者都不是「错」的，但用户看到的是「相册和分组排序相反」。
2. **「逆序」这一档只动照片**。用户勾上它，组卡片纹丝不动、相册卡片纹丝不动 ——
   一个叫「逆序」的东西只翻了网格里的一部分。

## 决策

### 1. 「逆序」就是字面的 `reverse`，而**所有字段默认一律升序**

网格里的东西按同一个尺子排队：名称 A→Z、数字小→大、时间旧→新。「逆序」翻过来。

这一条最初不是这么定的，中间改过一次，记在这里是因为**改的理由才是决策本身**。

#### 决策 1 的修订

第一版把方向表达成「字段的属性」：每个字段带一个**自然方向**（拍摄时间、修改时间、
年月日、事件 = 新→旧，其余 = 升序），而「逆序」是**偏离**它。这么定是为了同时满足
「默认最新在前」与「时间分组仍然新→旧」——按字面 `reverse` 读，后者会被翻成最旧在前。

改掉的理由是**它没有兑现自己的承诺**：那一版里时间类仍然是唯一一档降序的，
于是「修改时间默认新→旧」与同一张菜单里其余十一档的升序摆在一起，读起来仍然像
一个特例 —— 用户要的是「所有东西都往小到大 / 从旧到新」，而那一版给的是
「所有东西升序，除了时间」。**特例本身就是不一致的来源**，多一个字段就多一处要记的方向。

于是全部改成升序：`Facet.newest_first` 这个字段与 `SortOrder.newest_first` 那个属性
一起删掉，`descending` 回到字面的 `reverse`。少一个概念，也少一处能走错的地方。

代价是明确的：**按年 / 月 / 日分组与按事件分组也变成旧→新**（2023 → 2026），
这与多数相册软件的惯例相反。它换来的是整个网格只有一把尺子 —— 相册、组卡片、
照片、每一个字段，翻的方向都是同一个。

### 2. 相册卡片不开放排序字段，但方向跟着那一档

相册是文件夹，没有拍摄时间也没有相机，所以**排序字段菜单里没有它**（问的是「按什么排」，
文件夹能按的只有名字）。但**方向**统一：勾「逆序」时相册卡片 Z→A。

### 3. 相册卡片永远排在照片与组卡片之前

不变。这是既有心智（先看文件夹、再看按元数据归拢出来的东西），与方向无关。

## 后果

- **一处方向判据**：`SortOrder.descending`。照片（`sort_photos`）、组卡片（`build_groups`）
  与相册卡片（`ordering._reorder_level`）各问一次，三者因此不可能再走散。
- **「没值的那一组沉底」必须显式摘出来**。原先它靠 `_group_sort_key` 把日期键**取负**
  实现（`-0.0` 大于任何负日期），而那只在新→旧时成立 —— 升序下 0 是最小值，
  那一组会窜到**最前面**。现在 `Facet.group_order` 可以交回 `None` 表示「没有值」，
  `build_groups` 显式把它接到末尾，与 `sort_photos` 对没值的照片同一处理。
  **`_event_group_order` 返回 `None` 而不是 0** 也是同一件事。
- **新建相册那张卡片要重排之后才问行号**。`insert_entry` 按「同名相邻、升序」找位置，
  那是**扫描顺序**；勾了逆序时它落在错的地方，而且此后没有任何东西会把它挪回来
  （相册不参与 `sort_facet`，重排那道闸也不会因为它重排）。
- 老库的 `config.toml` 里的 `sort_descending` **不需要迁移**：它从头到尾都是字面反向。
- 「按拍摄时间排序」与「按修改时间排序」两档方向一致（都是升序）——它们是同一个量，
  不该给出相反的默认方向。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 每个字段带一个「自然方向」，「逆序」偏离它（第一版） | 时间类仍是唯一一档降序的，菜单里读起来仍是个特例；多一个字段就多一处要记的方向 |
| 给相册开放排序字段（修改时间、文件大小累计…） | 修改时间的 mtime 会被「新建/移入文件」改掉，老相册会莫名跳到最前面；大小要遍历整棵子树，大库上明显变慢 |
| 相册卡片固定 A→Z，不受「逆序」影响 | 就是改之前的样子：一个叫「逆序」的开关只翻了网格的一部分 |
| 取消「逆序」，改成每个字段各自的方向 | 用户没有任何办法表达「我要反着来」，而这一档是有用的 |
| 时间类保持新→旧，其余升序（0009 决策 5 的原样） | 就是「相册与分组方向相反」那个报障本身 |
