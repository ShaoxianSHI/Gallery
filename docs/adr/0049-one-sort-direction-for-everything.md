# ADR 0049：相册、组卡片、照片共用一个排序方向

- 状态：已接受
- 日期：2026-10-08
- 相关 ADR：0009（分组与排序）、0028（相册封面）
- 相关代码：`src/gallery/core/library/groups.py`、`src/gallery/core/metadata/facets.py`、
  `src/gallery/ui/window/ordering.py`、`src/gallery/ui/browser/model.py`

## 背景

网格这一层上摆着三种东西，而它们原先各有各的排序规矩，彼此不通气：

| 内容 | 原先的顺序 | 受「视图 → 排序 → 逆序」影响？ |
|------|-----------|------------------------------|
| 相册卡片 | 永远按名称升序（`scanner._sort_key`、`model._sort_key`） | 否 |
| 组卡片 | 时间类新→旧，其余按名称升序（`Facet.newest_first`） | **否** |
| 照片 | 选中的字段 + 「逆序」，默认修改时间**升序** | 是 |

于是有两处读起来像出了毛病：

1. **同一层里两样东西朝着相反的方向**。相册卡片 A→Z，按月份分出来的组卡片却是 2026 → 2023。
   两者都不是「错」的，但用户看到的是「相册和分组排序相反」。
2. **「逆序」这一档只动照片**。用户勾上它，组卡片纹丝不动、相册卡片纹丝不动 ——
   一个叫「逆序」的东西只翻了网格里的一部分。

还有一件本来就欠着的：默认那一档是**修改时间升序**，于是打开一个库看到的是**最旧**的照片在最前面。

## 决策

### 1. 「逆序」是偏离字段的自然方向，不是字面的 `reverse`

每个字段带一个**自然方向**（就是原有的 `Facet.newest_first`，语义从「组的默认排列方向」
扩成「这个字段天然怎么排」）：时间类（拍摄时间、修改时间、年月日、事件）是新→旧，
其余（相机、城市、关键词、所在文件夹、格式…）是按名称升序。

「逆序」= 偏离它。因此：

| 内容 | 默认 | 勾「逆序」后 |
|------|------|-------------|
| 修改时间 / 拍摄时间 | 新 → 旧 | 旧 → 新 |
| 年 / 月 / 日、事件分组 | 新 → 旧 | 旧 → 新 |
| 相机 / 城市 / 关键词 / 文件夹分组 | A → Z | Z → A |
| 相册卡片 | A → Z | Z → A |

**为什么不把「逆序」当成字面的 `reverse`**：那样「默认最新在前」就得让修改时间的默认档
变成 `descending = true`，而**时间类分组的自然方向也得跟着变成升序**（否则组卡片会退回
最旧在前）—— 一次「让默认看起来对」的改动会把分组视图里最常用的那一档弄反。
把方向表达成「字段的属性」而不是「配置的布尔」，默认档就只需要 `sort_descending = false`
这一种值，而它在每一类字段上都读作「自然的那个方向」。

### 2. 相册卡片不开放排序字段，但方向跟着那一档

相册是文件夹，没有拍摄时间也没有相机，所以**排序字段菜单里没有它**（问的是「按什么排」，
文件夹能按的只有名字）。但**方向**统一：勾「逆序」时相册卡片 Z→A。

**方向不能取自排序字段的自然方向**：修改时间的自然方向是「新→旧」，拿它来排相册，
默认就变成 Z→A 了 —— 相册没有时间可言。所以相册直接看 `order.descending` 本身。

### 3. 相册卡片永远排在照片与组卡片之前

不变。这是既有心智（先看文件夹、再看按元数据归拢出来的东西），与方向无关。

### 4. 默认那一档打开就是最新在前

由决策 1 直接得到：默认排序字段是修改时间，它的自然方向就是新→旧，而「逆序」默认没勾。
因此**不必**新增配置项，也不必改 `sort_descending` 的含义（它仍然是「偏离自然方向」，
`false` 依旧是绝大多数库 config.toml 里存着的那个值）。

## 后果

- **一处方向判据**：`SortOrder.newest_first`。照片（`sort_photos`）、组卡片（`build_groups`）
  与相册卡片（`ordering._reorder_level`）各问一次，三者因此不可能再走散。
- **「没值的那一组沉底」改成显式摘出来**。原先它靠 `_group_sort_key` 把日期键**取负**
  实现（`-0.0` 大于任何负日期），而取负只在新→旧时成立 —— 方向一翻那一组就窜到最前面。
  现在 `Facet.group_order` 可以交回 `None` 表示「没有值」，`build_groups` 显式把它
  接到末尾，与 `sort_photos` 对没值的照片同一处理。
- **新建相册那张卡片要重排之后才问行号**。`insert_entry` 按「同名相邻、升序」找位置，
  那是**扫描顺序**而不是显示顺序；勾了逆序时它落在错的地方，而且此后没有任何东西会
  把它挪回来（相册不参与 `sort_facet`，重排那条闸也不会因为它重排）。
- **`_event_group_order` 返回 `None` 而不是 0**（同上：0 配取负是巧合，不是判据）。
- 老库的 `config.toml` 里的 `sort_descending` **不需要迁移**：它的含义没变，而默认档
  「最新在前」是由字段的自然方向给出的。
- 「按拍摄时间排序」也一并变成默认新→旧（原先是升序）。这不是新决定，是决策 1 的推论：
  两个字段是同一个量，不该给出相反的自然方向。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 「逆序」= 字面的 `reverse`，默认档改成 `descending = true` | 时间分组会跟着变成最旧在前（决策 1），且要在两处各配一次默认值 |
| 给相册开放排序字段（修改时间、文件大小累计…） | 修改时间的 mtime 会被「新建/移入文件」改掉，老相册会莫名跳到最前面；大小要遍历整棵子树，大库上明显变慢 |
| 相册卡片固定 A→Z，不受「逆序」影响 | 就是今天的样子：一个叫「逆序」的开关只翻了网格的一部分 |
| 取消「逆序」，改成每个字段各自的方向 | 用户没有任何办法表达「我要反着来」，而现在这一档是有用的 |
