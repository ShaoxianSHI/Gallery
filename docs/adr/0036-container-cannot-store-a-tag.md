# ADR 0036：容器存不下的标签，写回时压根不发

- 状态：已接受
- 日期：2026-10-06
- 相关 ADR：0030（元数据写回）、0031（位置的双向编辑）、0032（可编辑的拍摄时间）
- 相关代码：`src/gallery/core/metadata/writeback.py`、`src/gallery/core/metadata/place_edit.py`

## 背景

用户在 HEIC 照片上改地点，保存之后**什么都没写进去**，横幅报的是：

> 写入没有生效，照片已经恢复原样：IPTC:City、IPTC:Province-State、IPTC:Country-PrimaryLocationName。

这不是界面或索引的问题，是写回层向一个存不下那些字段的容器发了请求。逐格式实测
（exiftool 13.55，字段集取 `WRITABLE_TAGS` 全集，逐标签单发再回读）：

| 格式 | IPTC 三层 | EXIF GPS 四标签 | XMP 三层 | EXIF 拍摄时间 | 写入行为 |
|------|-----------|-----------------|----------|---------------|----------|
| JPEG / PNG / TIFF | ✓ | ✓ | ✓ | ✓ | — |
| **HEIC / HEIF** | **✗ 丢弃** | ✓ | ✓ | ✓ | 退出码 0，一句警告都没有 |
| **WebP** | **✗ 丢弃** | ✓ | ✓ | ✓ | 同上 |
| **GIF** | **✗ 丢弃** | **✗ 丢弃** | ✓ | **✗ 丢弃** | 同上 |
| BMP | — | — | — | — | **明确报错**「not yet supported」 |

HEIF 家族的 item 体系里根本没有 IPTC；exiftool 收到 IPTC 赋值时**返回 0**、不警告、什么都不写。
而 `ExifToolWriter.write` 的 argv 上固定带 `-q -q`，连它本来会给出的 `1 image files unchanged`
也一并吞掉 —— 于是这一路**从头到尾没有任何信号**。

## 决策

### 1. 写之前就不发，而不是发完再认

`plan_place_edit` 对三层地名**永远同时生成 XMP 与 IPTC 两份**（ADR 0030 决策 1），这个「两份都写」
本身没错 —— 它是给只读 IPTC 的老软件留的。错的是**不看你往哪种容器里写**。

于是加一张**按容器的存储缺口表**（`UNSTORABLE_TAGS`），在 `_checked()` 里过滤掉存不下的标签 ——
那一处本来就是白名单的唯一出口，把能力检查放在同一个前置条件上，不另开一条路。

**HEIC / HEIF / WebP / GIF 只写 XMP，不写 IPTC。** 这不是降级到一个次要的副本：读取侧本来就是
XMP 优先（`_xmp_value(raw, "City") or first_value(raw, "IPTC:City")`），Lightroom 与
Capture One 也读 XMP —— **IPTC 才是那个只服务于老软件的兼容副本**。

### 2. 按后缀判，不做格式嗅探

判据取自 `path.suffix`，与 `decode.py`、`is_supported_photo` 是同一套 —— Gallery 全程按后缀认格式，
**嗅探内容会在这里变成唯一一处例外**。代价说清楚：一个 HEIC 文件被错命名成 `.jpg`，表就判错了，
于是退回今天这个行为（写进去、回读对不上、按原值回滚、横幅报错）。**这是既有行为，不会更糟**，
而错名文件在相册里本就不该存在；真要根治得让 exiftool 自己报格式，那是另一个话题。

### 3. 被过滤掉的标签不进 journal

`changes` 里只有真正发出去的那些，所以撤销（⌘Z）也只撤那些 —— **没写过的字段不该出现在回滚记录里**：
撤销时去「恢复」一个从未存在过的 IPTC，反而会造出一条不存在的记录。

### 4. 全被过滤掉时要说清楚是哪种「没东西可写」

「本来就没改」与「这个格式存不下」是两回事，**共用一句「没有要写入的改动」会把后者说成前者**，
用户于是以为自己没保存成功、再点一次保存。前者静默返回即可，后者必须抛错并点名格式。

### 5. BMP 不进这张表

exiftool 对 BMP **明确报错**且返回非 0，那条路本来就是通的，`_explain` 会说「这个格式改不了…的元数据」。
**这张表只装静默丢弃的那些** —— 一条会说话的错误比一张我们自己维护的表更准，而让 BMP 静默「什么都不写」
才是真的坏。

## 后果

- HEIC / WebP 的地点编辑从「整个写不进去」变成「写得进去，只存 XMP」。**横幅与界面一个字都不用改**
  —— 用户从没在编辑 IPTC，IPTC 对现代软件本来就是冗余的（本次修的是行为，不是文案）。
- GIF 的坐标与拍摄时间同样只存 XMP。这是同一张表的自然结果，**不是顺手加的特例**。
- 表是**实测**来的，不是从文档推的 —— 加一行格式前先跑一遍实测，猜错一行就是一次「地点写不进去」。
- 回读校验与「对不上就整体回滚」（ADR 0030 决策 3）**一个字没动** —— 它继续兜着那些表没覆盖到的
  情形（比如错命名）。本次治的是根因，不是把校验放松。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 回读时放过对不上的标签，算它「写成了」 | 那是在撒谎：文件里确实没有这个值，面板与别的软件都读不到 |
| 只回滚对不上的字段，让部分写入留下 | 一次保存变成「一半成功一半失败」而用户看不出来，且根因没治 —— 存不下的字段下一次还会失败 |
| 界面提示「HEIC 不支持 IPTC」 | 用户没在编辑 IPTC；对他可见的是「地点写不进去」。修好之后就不存在这件事了 |
| 自己嗅探文件内容判断真实格式 | 全项目按后缀认格式，这会成为唯一一处例外，而错命名文件不值得为它开这个口子 |
| 把 BMP 也放进表里「静默跳过」 | 会把一句现成的清楚错误换成一句沉默的失败 |
