# ADR 0078：修正 0077——Apple 地图的落点同样要 GCJ-02

- 状态：已接受（取代 0077 的决策 2）
- 日期：2026-10-24
- 相关 ADR：0077（国内坐标先转 GCJ-02）、0075（大图页把拍摄位置开到地图里）、
  0076（Google 地图那一项走 PWA）
- 相关代码：`src/gallery/core/external/maps.py`、`src/gallery/core/places/gcj.py`

## 背景

0077 判断「Apple 自己处理国内底图偏移，所以 Apple 那条保持 WGS-84」。这个判断是错的，
错在把**链接的坐标空间**当成了**标记点在图上的位置**：

- Apple 的 `maps://` 与它「拷贝链接」里的 `coordinate=` 确实按 WGS-84 记；
- 但中国大陆的底图瓦片是 GCJ-02，标记点落在图上时用的还是原始坐标 —— 于是 WGS 点会偏
  西北几百米，真实位置在显示位置的东南。
- 反向验证过：把坐标换成 GCJ-02 再打开，落点就贴住真实位置。这不是 Apple 独有的问题，
  公开的同类反馈（Immich #32317）里也是同一张照片、同一个 Apple 地图，WGS 偏、GCJ 准。

所以「链接里是 WGS」不能推出「地图上显示得对」。用户看到的是图上的点，要按那个来。

## 决策

1. **Apple 与 Google 一律先转 GCJ-02**：`apple_deep_link` 与 `google_web_link` 都在拼
   URL 之前调用 `wgs_to_gcj`。
2. **只对中国大陆生效**，港澳台与国外原样（规则与换算都在 `core/places/gcj.py`，
   见 0077 决策 3）。
3. **链接形式不变**：仍是 `maps://?ll=lat,lon&q=lat,lon`。`ll` 定位、`q` 落点；
   不用 `https://maps.apple.com/place?...` —— 那个地址在 macOS 上会交给浏览器，
   不会打开「地图」应用。

## 后果

- Apple 地图上的标记点与真实位置对齐；Google 那条的结论不变。
- **地点卡片上的地址可能对不上**：Apple 的地理编码按 WGS-84 解释这个 GCJ 坐标，卡片可能
  报出附近另一个地点。这一条接受：这个动作要的是「在图上是哪儿」，卡片不是真值来源。
- Google 的卫星图是 WGS 对齐的，切到卫星图仍可能看着偏；街道/地点视图优先（0077 已记）。
- 地点反查、分组、写回都不经过这一步，EXIF 的真值不动。

## 被否决的方案

- **Apple 保持 WGS**（0077 原来的做法）：用户实测就是偏的，且能稳定复现。
- **两家都用 `maps.apple.com/place?coordinate=` 这类网页链接**：macOS 上只会开浏览器，
  而这一项要的是系统「地图」窗口。
- **按「链接给的是 WGS」推断落点也对**：链接的坐标空间与底图的绘制空间不是一回事。
