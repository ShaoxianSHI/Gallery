# ADR 0009：按元数据分组与排序 —— 分组卡片、批量读取、facet 索引

- 状态：已接受
- 日期：2026-10-03
- 相关代码：`src/gallery/core/metadata/facets.py`、`src/gallery/core/metadata/batch.py`、`src/gallery/core/library/index.py`、`src/gallery/core/library/groups.py`、`src/gallery/ui/browser/model.py`、`src/gallery/ui/browser/grid.py`

## 背景

扫描出来的网格顺序只有一种：相册在前，同一层里按名称（`scanner.iter_entries`）。用户真正想看的
排列往往在元数据里 —— 按拍摄月份、按相机、按城市、按文件夹。要求是：

- **分组**：选一个字段，网格按它分成若干组；
- **排序**：在组内（或未分组时整层）按某个字段排序，支持正序与逆序。

麻烦在于 `PhotoRef` 只有 `path / size / mtime`，**扫描全程不读 EXIF**：扫几万张照片时每多一次
`open()` 首屏就慢一分。元数据现在是「用户选中哪张，才起一次 exiftool 子进程」（`core.metadata.exif`），
一次约 50ms。按元数据排序就意味着要给当前层**每张照片**读一次元数据 —— 5000 张照片按这个办法
是 4 分钟，功能等于不存在。

## 决策

### 1. 分组 = 相册卡片，双击进入

分组后的网格里，照片被换成一张张**组卡片**（封面 + 组名 + 张数），与现在的文件夹相册卡片
完全同形、同操作：双击进入，进入后这一组的照片铺满网格。

**为什么不是「整行组标题 + 照片」的分节视图**（macOS 照片那种）：那要求网格支持跨列的标题行，
而 `QListView` 的 IconMode 每个条目占一格，要做就得整块重写排版 —— 现有 `_cell_size_for` 里
那套「少摆一列就把右边空一列」的修正逻辑（`grid.py`）全部作废，回归风险与工作量都远超收益。
相册卡片式的代价是「同一时刻只看得到一个组」，用一次双击换掉。

组卡片同样不可改名、不可移到废纸篓：它不是磁盘上的东西，操作只在进入之后对照片本身进行
（界面会明确说明，不静默忽略）。

### 2. facet：分组 / 排序用的原始值，不是格式化字符串

新增 `core.metadata.facets`：每个字段给出一个**可比较的原始值**（`aperture` 是 `2.8`、
`captured` 是 epoch 秒、`iso` 是 `400`），以及分组时用的**组键与显示名**。

**为什么不复用 `MetadataReport`**：面板要的是给人看的串（`f/2.8`、`1/2000 秒`、`2024 年 5 月`）。
按这种串排序，`1/2000 秒` 与 `1/400 秒` 的先后取决于字典序，结果是错的；按串分组更是把
`ISO 100` 和 `ISO 1000` 分成两组。显示归格式化，排序归原始值。

取值只解析**我们点名要的标签**（`-EXIF:DateTimeOriginal -IPTC:City …`），不拉全量标签：
5000 张照片的全量 JSON 有几十 MB，点名要的那些只有几 MB，子进程也快得多。

### 3. 一次子进程读一批，不是每张一次

`core.metadata.batch` 把当前层的照片按 400 个一批交给 exiftool（`-j -G -sort -charset utf8`），
一批一个子进程，用 `Popen` 轮询以便随时 `terminate` —— 取消延迟在一批之内（约 1~2 秒），
切库时不会留下野进程。

argv 长度是硬约束（macOS `ARG_MAX` 约 1MB），所以分批而不是一次传一万个路径；批大小取得
足够大，把「每文件几十毫秒的启动开销」摊薄到可以忽略。

**没装 exiftool 时**退回 Pillow 逐张读基础 EXIF（不开子进程，反而更快）。Pillow 读不到
IPTC / XMP，于是「国家 / 省州 / 城市 / 关键词」在菜单里**直接置灰并写明原因**，而不是让用户
分出一个「全都没有」的组。

### 4. 结果落盘到 `.gallery/index.db`，按 `(路径, 大小, mtime)` 失效

`core.library.index` 是一张极窄的 SQLite 表：一行一张照片，只存上一步那几个 facet 值。
命中判据是 `(size, mtime_ns)` 与扫描时一致 —— 文件改过就当没有，重读一次就更新。

- **首次**分组 / 排序要几秒（取决于库大小）；**之后**换库再回来是瞬时的。
- 表在 `.gallery/` 内（用户选「缓存到系统目录」时落到 `~/Library/Application Support/Gallery/cache/index/`），
  符合红线 5：删掉整个目录必须能靠重扫 + 重读恢复到等价状态，索引里**没有任何唯一数据**。
- 只在用户真的用了分组 / 排序时才创建与写入：打开库仍然只读。

### 5. 排序对「有值 / 没值」分别处理

没写拍摄时间的照片排在哪里是个真问题。规则统一为：**没值的永远在最后**（正序逆序都是），
组内则单独归到一个「时间未知」之类的组，不与有值的组混排。

数值型（光圈、快门、ISO、焦距、像素）按数值排；同值按文件名兜底，保证顺序稳定可预期。

### 6. 入口只在菜单，选择记进会话

「视图 → 分组 ▸」「视图 → 排序 ▸」两个子菜单，与既有的「浏览方式」「缩略图大小」一致，
不占照片区的高度（这个项目一直刻意不加工具栏）。选择写进 `state.json`（`SessionState`），
下次打开直接沿用；非法字段值静默回退为「不分组」，与会话的既有容错策略一致。

分组字段里时间有三个粒度（年 / 年月 / 年月日），排序字段与分组字段是两套独立列表：
不是每个能分组的字段都适合排序（文件夹可以分，关键词排序没意义）。

## 后果

- 扫描仍然是「只 stat 不读 EXIF」，首屏不受影响；元数据只在用户点了分组 / 排序之后才读。
- 组是**派生视图**：进入组之后再改照片的元数据（比如写回拍摄时间），组卡片要重新读一次索引
  才会变；这一版不做实时重算，排序改变后由用户再触发一次分组即可。
- 按「关键词」分组时一张照片可以属于多个组，因此各组张数之和大于照片总数 —— 这是标签的
  通常语义，组内进入后仍能按当前排序看到全部相关照片。
- 相册模式下子文件夹卡片排在组卡片之前，保持「先看相册、再看分组照片」的既有心智。
- 索引 schema 变了（新增 facet 列）时旧表读不出来怎么办：schema 版本号存在
  `PRAGMA user_version`，对不上就整表重建 —— 反正它是可重建的缓存。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 整行组标题的分节视图（Photos.app 那样） | 要重写网格排版，作废现有自适应列宽的全部修正，回归风险远超收益（见决策 1） |
| 每张照片起一次 exiftool | 5000 张约 4 分钟，功能不可用（见背景） |
| 一次 exiftool 传全部路径 | macOS `ARG_MAX` 约 1MB，万张照片直接 `E2BIG`；分批还能顺带拿到取消点 |
| 在内存里缓存 facet，不落盘 | 每次启动都要重付几秒到几十秒；`.gallery/` 里已经有索引的位置，白放着不用 |
| 直接按 `MetadataReport` 的显示串分组 / 排序 | `1/2000 秒` 与 `1/400 秒`、`ISO 100` 与 `ISO 1000` 会排错（见决策 2） |
| 一次性把整库的 facet 都灌满索引 | 用户只想看一个文件夹，却为全库付代价；而且照片本来就在变 |
| 组卡片可改名 / 可删 | 它不是磁盘上的东西，操作语义无处落地（见决策 1） |
| 分组 / 排序做成窗口上的常驻下拉条 | 与本项目「不加工具栏、不占照片区」的既有取舍相反；菜单里两个子菜单已经够用 |
