# ADR 0040：在当前视图内筛选（检索条件的第二个作用域）

- 状态：已接受
- 日期：2026-10-06
- 相关代码：`src/gallery/core/library/search.py`、`src/gallery/core/library/index.py`、
  `src/gallery/core/library/config.py`、`src/gallery/ui/window/search_flow.py`、
  `src/gallery/ui/window/widgets/search_field.py`、`src/gallery/ui/main_window.py`、
  `src/gallery/ui/window/navigation.py`、`src/gallery/ui/window/widgets/breadcrumb.py`
- 相关：[ADR 0026](0026-search.md)（搜索：胶囊、条件语法、`photos` 表索引）、
  [ADR 0033](0033-calendar-view.md)（日历视图）、[ADR 0038](0038-unify-cache-location.md)（库级界面偏好）

## 背景

ADR 0026 做出来的检索只有一种作用域：**横跨整个库** —— 条件一提交，整层就被检索结果接管，面包屑报库名、
当前目录与分组从那一行上消失（决策 1b）。这对「找一张照片」是对的选择（用户恰恰说不清它在哪个相册里），
但有一类用户不找照片而是**浏览**：他正在月视图里看 2024 年 5 月，想把这一屏里没有 Canon 拍的那些去掉 ——
换掉整层既不是他要的（他还要在这个视图里继续翻），也打断了他刚才的上下文。

要补的正是这一种。条件语法完全不变（`#相机 Canon` 两边一样），变的只是「这些条件管到哪儿」。

## 决策

### 1. 条件有**两种作用域**，用一个开关切换

| 作用域 | 常量 | 条件的作用 |
|---|---|---|
| 整库检索 | `SEARCH_SCOPE_LIBRARY` | **接管**当前层，横跨全库（ADR 0026 决策 1） |
| 当前层筛选 | `SEARCH_SCOPE_LEVEL` | **收窄**当前层，视图本身不动 |

**默认是整库检索**：新用户不该一装上就与 ADR 0026 那样不一样，而「筛选」是主动去开的那一个。全窗口凡
「条件非空就意味着什么」的地方一律问 `_is_library_search()`，不再问 `bool(self._conditions)`：两者的差别
有七处（`_start_scan`、`_shows_calendar_page`、`set_browse_mode`、`enter_folder`、监听器的两处、空层提示），
**各自判一次就一定会漏一处**。

筛选时**条件跟着用户走**：切浏览方式、进出相册、进出分组、日历切 `Y`/`M`/`W`，条件都留着；只在换库时清空
（条件属于那个库，ADR 0026 决策 10 已经拒绝过把它记进会话）。

### 2. 不把作用域塞进 SQL，而是**求交**

范围不在查询里收：这一层的照片**照常枚举**（相册 / 平铺 / 分组快照各走各的现成路径），随后拿一份「命中
路径集合」与它求交。理由有两条，第二条是决定性的：**分组那一层的范围根本没法翻译成 SQL 谓词** —— 它是上一次
`build_groups` 算出来的组快照，而组标识到 facet 值的映射逐字段不同；真要用 SQL 表达范围就得写成
`p.path IN (?, ?, …)`，于是要处理 SQLite 的变量上限与分块（999 到 32766 不等），而一层几千张是常事。

于是只多了一个查询 `search.build_match_query`（`SELECT p.path`），它与 `build_query`、`build_count_query`
**共用同一个 `_where()`**：「命中」这件事仍然只有一处定义（ADR 0026 决策 6 的那条原则）；取哪几列各写各的，
所以那条查询的每个字段**仍要拿真 schema 执行一遍**。

**`build_match_query` 既不排序也不截断** —— `RESULT_LIMIT` 在这里等于**静默丢命中**：命中八千张而当前层
的那几张排在第 5001 名之后时，用户看到的是「一条都没有」，而那不是答案，是查询自己偷偷少给了。整库检索
可以截断（那一层的结果本来就是给人浏览的前几百张），相交不行：**交出来的每一张都得是对的**。

### 3. 插在 `_staged` 上、`_apply_ordering` 之前

收窄是**一次相交**，不是另写一条列举链 —— 分桶、排序、缩略图预取、焦点恢复、空层提示、监听增量全都原样
复用，与整库检索共用同一条收尾路径（ADR 0026 决策 7：**新写一条平行路径才是 bug 的来源**）。具体形态是
`OrderingMixin._order_now()` 这**一个漏斗**：所有出口都走它，它先问筛选、收窄，再排序；漏斗两端调的是
`_apply_ordering` 而不是漏斗自己（排序完再回到漏斗就是递归到自己）。

落在 `_staged` 上而不是模型上：这一层还没显示（换层时暂存区优先），在那里收窄才不会先摆一屏未筛选的、
再换成筛过的。**顺序不能反**：facet 读取会**写**索引而筛选查询要**读**索引，所以漏斗必须挂在 facet 读取
那一侧。

**两个「假阴性」陷阱都要堵**：文件表还没建 → 沿用 `_start_search` 那道前置条件，挂起等那一遍跑完、由
`_on_photo_index_done` 补跑（空结果会让用户再也不筛第二次）；facet 还没读 → `#相机 Canon` 同理
（`facets` 表只有读过 EXIF 的照片才有行），所以 `_needs_facet_read()` 要把「条件要元数据」也算进去。

**相册卡片按子树收留**：一张都不命中照片的子相册卡片不摆出来（摆着一排点进去全是空的相册，等于骗用户
白点一次）；子树里有命中的留着当导航。判据由 `search.albums_kept` 一次算完 —— 一次遍历把命中按「相对库根的
第一段」分桶，代价是 O(命中数) 而不是 O(卡片 × 命中数)。卡片的位置用它**自己**、命中照片的位置用它的
**父目录**（两者不是同一个函数）：拿 `relative_folder` 去算一张卡片会把卡片自己的名字也去掉，于是所有卡片
都短了一级、谁也匹配不上。

### 4. 面包屑反过来：范围变了才藏路径

筛选时范围没变，于是照旧报完整路径与当前那一组，只把结尾那一段换成「筛选后（N）」—— 藏掉路径是在说一件
不存在的事（同 ADR 0026 决策 1b，只是那里范围**真的**变成了整库）。空层提示同理：筛选时说「当前这一层里
没有符合这些条件的照片」，而不是整库检索那句「这些筛选条件下没有照片」（后者在筛选下是骗人的）。

### 5. 切换按钮摆在胶囊右边，两处入口共用一份状态

> **「可勾选」与「选中时整枚按钮填满高亮色」已被
> [ADR 0042](0042-the-scope-switch-is-an-action.md) 决策 1 取代** —— 那一枚是一次性动作，不摆选中态；
> **界面上说「此刻是哪一头」的是胶囊的占位文字与菜单里那一项的勾**（后者由
> [ADR 0069](0069-scope-switches-only-from-the-toggle.md) 删掉，只剩占位文字）。下面「两处入口共用一份
> 状态」仍然成立（状态仍由 `set_search_scope` 一个入口改）。

一个按钮（**图标现画**，仓库里不放素材；与胶囊共用同一份样式来源与同一个绘制规矩），摆在搜索胶囊**右边**
—— 同一个胶囊里的同一套条件语法，改的只是它们管到哪儿。图标是**上下两支反向的横向箭头**（上面朝左、下面
朝右），不是漏斗：漏斗读起来是「把东西筛掉」，而这一枚按钮是个**掉个头**的开关，两支反向的箭头说的正是
这件事。按钮**不挂悬浮提示** ——「此刻是哪一头」紧挨着就写在胶囊的占位文字里，提示能说的只有「按下去会做
什么」，而那正是这两支箭头。

**对齐的是胶囊的右缘，不是按钮的右缘**：`MARGIN_RIGHT` 量的是整块的右边距，而面包屑那几枚条件胶囊是胶囊
的下属概念，对齐到按钮的右缘（更靠右）会在中间空出一截，看着像那几枚条件不属于任何一个框。菜单里另有
一个可勾选项（「筛选当前视图」），与按钮走**同一个入口**，所以两处永远说同一句话 —— **那一项已由
[ADR 0069](0069-scope-switches-only-from-the-toggle.md) 删掉**，作用域只从这一枚按钮切换。

### 6. 作用域是**库级**偏好，条件仍然不是

作用域记进那个库的 `config.toml` 的 `[ui]`（与浏览方式、分组、排序、缩略图档位同一套，ADR 0038 决策 4）：
「我习惯用筛选」是关于这个库的偏好，换库不该传染。**条件本身仍然不进会话**：条件是一次性的选择，而作用域
是个偏好。开库时 `resolved_search_scope()` 对来路不明的值回退到整库检索（`[ui]` 是软件自己写的表，手改坏
一个值不该让库打不开）。

### 7. 筛选时 ⌘V 与 ⇧⌘N 让路

这一层显示的不是全部内容，粘进去 / 新建出来的照片可能一条都不出现（没命中条件）。而它们恰恰是**会动用户
文件**的那一类（约束 1），不该在用户看不清全貌时发生 —— 真要粘，先撤掉筛选。撤光条件后两条立刻回来，
不许留在关着的状态上（用户看不出为什么按不动）。

### 8. 日历那一侧：视图逻辑零改动，但条件要摆到工具条上

`_shows_calendar_page` 放行之后，筛过的引用照常喂进分桶（`_feed_calendar`），月视图只显示命中的格子，而
`Y`/`M`/`W` 与筛选互不干扰（`set_photos` 不重跑，条件自然跟着走）—— **日历的绘制逻辑一个字都没改**。
**但条件胶囊必须也摆到工具条上**（决策 9 的一半）：这一行占掉的就是网格页那条面包屑（ADR 0033 决策 5），
而筛选时用户看不到网格页 —— 胶囊只摆在面包屑上，就等于「加了条件却不知道加了什么」。

### 9. 胶囊摆**年 / 月 / 周左边**，两处共用同一份胶囊

摆左边而不是右边：右边那一头就是分段选择器，而胶囊按录入顺序从右往左排开（ADR 0026 背景第 4 条）的话，
最后几枚会**压在那三个按钮上面** —— 叠着的那一组是永远点不到的那个。**与面包屑共用同一个 `ChipButton` 与
同一份样式**（`breadcrumb.build_chip`）：两处各派生一遍，过一阵就是「日历上那几枚比网格上那几枚浅一档」，
而没人说得清哪一档是对的。两个控件接到**同一个**处理函数上（`_on_condition_edited` /
`_on_condition_removed`），所以「日历上撤掉了、网格页上还留着」这种不一致不可能发生。

**宽度不够时收掉尾部那几枚，而不是把每一枚都压成省略号**：标题是「我在看哪一段」，条件是附注，所以空间紧
的时候先让附注让路。但「让路」**不等于按比例压缩每一枚** —— 压到尺寸提示以下时 `QToolButton` 会省略文字，
于是长条件变成「拍摄时…1 ✕」，用户读到的是一条**不存在的条件**，而点它撤掉的是另一条。所以是「完整摆下
前 N 枚 + 一枚 `+N`」，而 **`+N` 按完整列表的序号点**，条件被点掉时索引不会错位。

**那一块让路要用 `setMaximumWidth`，不能用 `QSizePolicy.Ignored`** —— 后者丢掉尺寸提示，布局于是给 0 宽，
整块连同胶囊一起消失。**那个上限不能在 `set_conditions` 里算**（它常发生在布局跑过之前，那时 `self.width()`
还是 0），要放 `resizeEvent` 里顺带重排。胶囊还会吃到工具条样式表的级联 —— 它自己那几条 `palette(text)` /
`palette(mid)` 会被 `QStyleSheetStyle` 换成它自己那份调色板，所以那条回归测试**量画出来的像素**（浅色与
深色各一遍，下限 4.5:1），不量 `palette()`。

### 10. 摆胶囊的那一句要放在 `_update_breadcrumb` 的**每一个早退之前**

`MainWindow._update_breadcrumb` 有三条早退（点出来的那一格、没有库或无条件、整库检索）。把摆胶囊写在**末尾**
就漏掉了「条件撤光」那一步 —— 而那一步正好走的是「无条件」的早退：模型里条件确实是空的，所以量模型的那条
回归测试会一路绿，**回归测试量的是工具条上真的什么都没有**。`+N` 那枚是 `QLabel` 不是按钮：摆的是数量，
不是能点的东西，给它指针光标会让用户以为点得动。

### 11. `Esc` 只管位置；撤条件挪到 `⇧Esc`

**取代 ADR 0026 决策 10**（那里把条件排在文件夹 / 分组 / 日历那一格**之前**，理由是「条件又深一级」）；
后果是**只要有条件就永远退不出位置**：按 `Esc` 看到的是一条条件被撤掉而**位置纹丝不动** —— 而那两件事在
屏幕上分不出来。**退不动的时候也不顺手撤一条**，那与它是同一个毛病。所以是**改用别的键**（而不是「先退
位置、撤条件排在最后」）：`Esc` 纯粹退位置，撤条件单独给 `⇧Esc`，两者彻底分开，绝不互相抢；菜单里
「上一级」旁边多一行「撤掉最后一条筛选条件」。

三条随之而来的决定：

- **`_on_search_dismissed` 改走 `pop_last_condition`**，不再转给 `go_up`：搜索框那一处的语境是**条件**，
  转给 `go_up` 会让「在搜索框里按 Esc」也变成「退一层」—— 而它在条件为空时本来就该什么都不做。
- **`⇧Esc` 那一行不限于网格页**：`⇧Esc` 挂在窗口上（`WindowShortcut`），条件是跨页的，在日历那一页也还在；
  没条件时**关掉**，而不是按下去什么也不发生。
- **整库检索与在当前层筛选共用同一条 `go_up`**，所以两边一起挪 —— 只挪一半就是同一键两种行为。

**快捷键要单独断一条**（发真实 `QTest.keyClick`，不是调方法）：方法在而键没挂上、上下文写错、或被输入框
先忽略掉，都不会让直接调方法的那几条用例变红。

### 12. 「正在改哪一条」不许粘住：**走开就是放弃**

条件**不许粘在「正在改」这一态上**：不接着改、又走开了，之后敲的每一条都会顶掉它。根因是
`_editing_condition` **粘住** —— `_on_search_submitted` 按它分岔，有它走 `self._conditions[editing] = …`
（**就地替换，条目数不增加**），没有它走 `append`；而焦点离开输入框原先不清它，于是屏幕上只看得见「条件
变了」，看不见「我刚才点过一枚胶囊」。

**三个「走开」的出口**，都汇到已有的 `_cancel_condition_edit`（不新造概念）：

| 触发 | 落点 |
|---|---|
| **焦点离开输入框**（回退） | `_on_search_active_changed(False)` |
| 点网格空白处 | `_on_background_activated` 开头，与已有的 `is_renaming()` 早退同一理由 |
| 切换浏览方式 | `set_browse_mode` 里，排在 `_is_library_search()` 之前 |

三个决定：

- **回退挂在 `editing_changed(False)` 上，而不是焦点事件上**：离屏下窗口拿不到真实焦点，而 `focusOutEvent`
  的**先后顺序**量不出来 —— 一旦点胶囊本身被拆成「失焦 → 获焦」，功能会当场自毁。
- **`_cancel_condition_edit` 里加一道前置条件**：没在改任何一条时**什么都不做**。回退那条在失焦时也会调它，
  而那一刻用户很可能正在**输入一条全新的条件**（`_editing_condition` 是 `None`）—— 那时把输入框清掉就是
  凭空删掉他刚敲的字，**比原 bug 更糟**（它丢的是没确认的东西）。
- **日历工具条与网格页面包屑完全一致**：两处胶囊都是正文改、✕ 撤，接到同一个处理函数上；两处都必须能改，
  别为了「统一」把其中一处改成只读。

**放弃 ≠ 撤销**：放弃修改**不动条件本身**（胶囊原样留着），所以回归测试里每一条都同时断「editing 清了」
与「条件还在」。

### 13. 条件只有三个下场，扫出来锁定

「除了点 ✕ 之外任何情况下不消失」这句话的**可查形式**：`test_only_three_things_can_take_a_condition_away`
用 AST 扫出全仓库每一处改动 `self._conditions` 长度的写法，只允许那三样（点 ✕、改这一条时回车替换、
换库 / 切到整库检索）；清单本身被挪走或改名时那条断言要红，而不是悄悄放行。

**为什么非要扫而不靠几条行为用例**：这一族 bug 的形状是「某处 `_editing_condition` 粘住 → 下一次提交
静默替换」，任何一条行为用例都只能盯住**它已知的那几条路径** —— 新加一条「清条件」的路（换作用域、
换分组、回退到大图页）时，行为用例一条都不会红。扫 AST 而不是扫文本，是因为文档里到处是
`self._conditions[editing] = …` 这样的片段，按行扫会把注释与 docstring 一起算进来。

## 后果

> **其中「`Esc` 只管位置」这一条由 [ADR 0041](0041-the-level-stack.md) 补完**：搜索结果「接管当前层」
> 而它既不是文件夹也不是分组，于是 `_can_go_up()` 恒为 `False`，`Esc` 退出搜索本来没人管（搜索后直接
> 能退是**巧合**，那时焦点还在搜索框里）。ADR 0041 把搜索结果变成栈上一帧，那两条不用专门修 —— 它们是
> 模型的结果。

- 新增的公开接口：`search.build_match_query` 与卡片判据 `search.albums_kept`（`core/library/search.py`）、
  `Library.matching_paths`、`FacetIndex.match_paths`、`SearchFlowMixin` 的 `_start_level_filter` /
  `_on_level_filtered` / `_on_filter_failed` / `_cancel_level_filter`、`ScopeToggle` 与 `funnel()`
  （`ui/window/widgets/search_field.py`）、`ui/calendar/toolbar.py` 的胶囊区与 `set_conditions()`、
  `breadcrumb` 的 `chip_style`（由 `_chip_style` 转公开）与 `build_chip()`（两处摆胶囊走同一个出口）。
- **`ScopeToggle` 不另开顶层模块**：它与胶囊共用同一套几何常量与样式来源，拆出去反而要把这些复制一遍。
- 监听器在有条件时**一律重跑**（与整库检索同一处）：真增量要逐张判断「新照片命不命中」，那还是得查索引，
  而 `_reload_level` 已经把整条链接通了。
- 日历上点开一格之后再加条件**退回日历页**（`_reload_level` 清 `_drill_photos`，与整库检索同一处理）：
  那一格的照片本来就来自筛过的桶，再筛一遍等于给同一条路径写第二套筛选逻辑。
- 测试：真 schema + 无 LIMIT + 卡片判据（`tests/core/library/test_search.py`）、作用域往返
  （`tests/core/library/test_config.py`）、端到端（`tests/ui/test_filter_flow.py`）、胶囊的位置 / 显隐 /
  点击 / 可读性 / 撤光即消失 / 溢出收尾（`tests/ui/calendar/test_toolbar.py`）；
  `tests/ui/test_external_button.py` 那两条让位的断言要跟着加上按钮那一份。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 把范围写进 SQL（`p.path IN (...)` / 相册前缀） | 分组那一层的范围是算出来的，翻译不成谓词；`IN` 还要处理变量上限与分块（决策 2） |
| 给 `search_photos` 加一个 `scope` 参数 | 同一份代码要同时处理「返回一层」与「返回一份可相交的集合」两种形状，而后者不该带 `RESULT_LIMIT` |
| 另写一条「筛选专用」的收尾链 | ADR 0026 决策 7 已经点名：另写一条平行路径才是 bug 的来源 |
| 筛选时把相册卡片全收起来，只摆照片 | 用户就没法再往子相册里钻了；而「哪些子相册里有我要的东西」正是筛选要回答的问题之一（决策 3） |
| 相册卡片全部保留、不参与筛选 | 会出现「卡片里其实一张都没有」，得点进去看到空层才知道 |
| 条件也记进会话 | 条件是一次性的选择；跨启动记住一串条件只会让人莫名其妙（ADR 0026 决策 10 已经这么定过） |
| 两段式分段控件（搜索 \| 筛选） | 胶囊左边要多长一截，且两格共享圆角轮廓这件事要另写一遍绘制；一个按钮够用（决策 5）—— ADR 0042 又把那一枚改成了一次性动作 |
| 筛选时仍允许 ⌘V / ⇧⌘N | 粘进去的照片可能一条都不显示，而那是会动用户文件的操作（决策 7） |
| 条件用**另一种语法**区分搜索与筛选 | 用户要学两遍，而其中一遍是他不用的那个；两者的差别是范围而不是写法 |
