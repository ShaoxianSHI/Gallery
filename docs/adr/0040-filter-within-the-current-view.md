# ADR 0040：在当前视图内筛选（检索条件的第二个作用域）

- 状态：已接受
- 日期：2026-10-06
- 相关代码：`src/gallery/core/library/search.py`、`src/gallery/core/library/index.py`、
  `src/gallery/core/library/config.py`、`src/gallery/ui/window/search_flow.py`、
  `src/gallery/ui/search_field.py`、`src/gallery/ui/main_window.py`、
  `src/gallery/ui/navigation.py`、`src/gallery/ui/panels/breadcrumb.py`
- 相关：[ADR 0026](0026-search.md)（搜索：胶囊、条件语法、`photos` 表索引）、
  [ADR 0033](0033-calendar-view.md)（日历视图）、[ADR 0038](0038-unify-cache-location.md)（库级界面偏好）

## 背景

ADR 0026 做出来的检索只有一种作用域：**横跨整个库**。不管用户当时在哪个相册、哪个分组、
日历的哪一层，条件一提交，整层就被检索结果接管 —— 面包屑报库名、当前目录与分组从那一行上
消失（决策 1b）。

这对「找一张照片」是对的选择（用户恰恰说不清它在哪个相册里，那正是他要搜索的原因）。但有一类
用户不找照片，而是**浏览**：他正在月视图里看 2024 年 5 月，想把这一屏里没有 Canon 拍的那些
去掉；他在某个相册里翻，想只看 ISO 高于 1600 的。在这两种场景里，条件的作用范围是**他眼前
这一层** —— 换掉整层既不是他要的（他还要继续在这个视图里翻），也打断了他刚才的上下文
（年月日历停在哪一段、面包屑上的路径）。

要补的正是这一种。条件语法完全不变（`#相机 Canon` 两边一样），变的只是「这些条件管到哪儿」。

## 决策

### 1. 条件有**两种作用域**，用一个开关切换

| 作用域 | 常量 | 条件的作用 |
|---|---|---|
| 整库检索 | `SEARCH_SCOPE_LIBRARY` | **接管**当前层，横跨全库（ADR 0026 决策 1） |
| 当前层筛选 | `SEARCH_SCOPE_LEVEL` | **收窄**当前层，视图本身不动 |

**默认是整库检索**：那是从前唯一的那一种行为，新用户不该一装上就与从前不一样，而「筛选」是
主动去开的那一个。

全窗口凡「条件非空就意味着什么」的地方一律问 `_is_library_search()`，不再问
`bool(self._conditions)`。两者的差别有七处（`_start_scan`、`_shows_calendar_page`、
`set_browse_mode`、`enter_folder`、监听器的两处、空层提示），**各自判一次就一定会漏一处**，
而漏掉那处的症状（筛选时日历被换成网格页、进相册时条件被清掉）看起来都像「另一个功能坏了」。

筛选时**条件跟着用户走**：切浏览方式、进出相册、进出分组、日历切 `Y`/`M`/`W`，条件都留着。
只在换库时清空（条件属于那个库，留在一个已关掉的文件夹上是 ADR 0026 决策 10 已经拒绝过的事）。

### 2. 不把作用域塞进 SQL，而是**求交**

范围不在查询里收：这一层的照片**照常枚举**（相册 / 平铺 / 分组快照各走各的现成路径），随后拿
一份「命中路径集合」与它求交。

两条理由，第二条是决定性的：

- **分组那一层的范围根本没法翻译成 SQL 谓词** —— 它是上一次 `build_groups` 算出来的组快照，
  而组标识到 facet 值的映射逐字段不同；
- 而真要用 SQL 表达范围，就得写成 `p.path IN (?, ?, …)`，于是要处理 SQLite 的变量上限与分块
  （默认上限 999 到 32766 不等）。按当前层的规模，一层几千张照片是常事。

于是只多了一个查询 `search.build_match_query`（`SELECT p.path`），而它与 `build_query`、
`build_count_query` **共用同一个 `_where()`**：「命中」这件事仍然只有一处定义（ADR 0026 决策 6
的那条原则）。取哪几列各写各的，所以那条查询的每个字段**仍要拿真 schema 执行一遍** ——
拍摄时间那一列的错（`captured_at` vs `captured`）就是这么抓到的。

**`build_match_query` 既不排序也不截断。** `RESULT_LIMIT` 在这里等于**静默丢命中**：命中八千张
而当前层的那几张排在第 5001 名之后时，用户看到的是「一条都没有」，而那不是答案，是查询自己
偷偷少给了。症状与「这一层真的没有」完全一样，没有任何线索指向它。整库检索可以截断（那一层
的结果本来就是给人浏览的前几百张），相交不行：**交出来的每一张都得是对的**。

### 3. 插在 `_staged` 上、`_apply_ordering` 之前

收窄是**一次相交**，不是另写一条列举链。于是分桶、排序、缩略图预取、焦点恢复、空层提示、
监听增量全都原样复用 —— 与整库检索共用同一条收尾路径（ADR 0026 决策 7 的同一条原则，
另写一条平行路径才是 bug 的来源）。

具体形态是 `OrderingMixin._order_now()` 这**一个漏斗**：所有出口都走它，它先问筛选、收窄，
再排序。漏斗两端调的是 `_apply_ordering` 而不是漏斗自己（排序完再回到漏斗就是递归到自己）。

落在 `_staged` 上而不是模型上：这一层还没上屏（换层时暂存区优先），在那里收窄才不会先摆一屏
未筛选的、再换成筛过的。

**两个「假阴性」陷阱都要堵**：

- **文件表还没建** → 一条都命中不了。沿用 `_start_search` 那道闸：挂起等那一遍跑完，
  由 `_on_photo_index_done` 补跑。用户看到空结果就再也不会筛选第二次了。
- **facet 还没读** → `#相机 Canon` 同理（`facets` 表只有读过 EXIF 的照片才有行）。
  `_needs_facet_read()` 因此要把「条件要元数据」也算进去。

**顺序不能反**：facet 读取会**写**索引，而筛选查询要**读**索引 —— 所以漏斗必须挂在 facet
读取那一侧，facet 先于筛选完成。

**相册卡片按子树收留**：一张都不命中照片的子相册卡片不摆出来（摆着一排点进去全是空的相册，
等于骗用户白点一次）；子树里有命中的留着当导航。判据由 `search.albums_kept` 一次算完 ——
一次遍历把命中按「相对库根的第一段」分桶，代价是 O(命中数) 而不是 O(卡片 × 命中数)。

卡片的位置用它**自己**、命中照片的位置用它的**父目录**（两者不是同一个函数）—— 拿
`relative_folder` 去算一张卡片会把卡片自己的名字也去掉，于是所有卡片都短了一级、谁也匹配不上。
这条是写完就立刻踩到的：四条用例同时变红才看出来不是「卡片不该留」而是「卡片算错了位置」。

### 4. 面包屑反过来：范围变了才藏路径

ADR 0026 决策 1b 说检索时只报库名，理由是范围**真的**变成整库了 —— 留着「旅行 ▸ 2024」读起来
就是「在这个文件夹里搜到 4 张」，而实际那 4 张大半在别处。

筛选时范围没变，**藏掉路径同样是在说一件不存在的事**：照旧报完整路径与当前那一组，只把结尾
那一段换成「筛选后（N）」。空层提示同理：筛选时说「当前这一层里没有符合这些条件的照片」，
而不是整库检索那句「这些筛选条件下没有照片」（后者在筛选下是骗人的）。

### 5. 切换按钮摆在胶囊右边，两处入口共用一份状态

一个可勾选的按钮（**图标现画**，仓库里不放素材；与胶囊共用同一份样式来源与同一个绘制规矩），
摆在搜索胶囊**右边** —— 同一个胶囊里的同一套条件语法，改的只是它们管到哪儿。

图标是**上下两支反向的横向箭头**（上面朝左、下面朝右），不是漏斗：漏斗读起来是「把东西筛
掉」，而这一枚按钮是个**开关**，两支反向的箭头说的是「掉个头」。按钮**不挂悬浮提示** ——
开着还是关着已经由整枚按钮的填充色说清楚了（见 `tests/ui/test_filter_flow.py`），再挂一句
提示是把同一件事说两遍。

`MARGIN_RIGHT` 量的是**整块**的右边距，而面包屑那几枚条件胶囊仍然对齐**胶囊的右缘** ——
它们是胶囊的下属概念，对齐到按钮的右缘（更靠右）会在中间空出一截，看着像那几枚条件不属于
任何一个框。

菜单里另有一个可勾选项（「筛选当前视图」），与按钮走**同一个入口**，所以两处永远说同一句话。

### 6. 作用域是**库级**偏好，条件仍然不是

作用域记进那个库的 `config.toml` 的 `[ui]`（与浏览方式、分组、排序、缩略图档位同一套，
ADR 0038 决策 4）：「我习惯用筛选」是关于这个库的偏好，换库不该传染。

**条件本身仍然不进会话**：条件是一次性的选择，而作用域是个偏好。开库时 `resolved_search_scope()`
对来路不明的值回退到整库检索（`[ui]` 是软件自己写的表，手改坏一个值不该让库打不开）。

### 7. 筛选时 ⌘V 与 ⇧⌘N 让路

这一层显示的不是全部内容，粘进去 / 新建出来的照片可能一条都不出现（没命中条件），用户会
以为坏了。而它们恰恰是**会动用户文件**的那一类（红线 1），不该在用户看不清全貌时发生 ——
真要粘，先撤掉筛选。撤光条件后两条立刻回来，不许留在关着的状态上（用户看不出为什么按不动）。

### 8. 日历那一侧：视图逻辑零改动，但条件要摆到工具条上

`_shows_calendar_page` 放行之后，筛过的引用照常喂进分桶（`_feed_calendar`），月视图只显示
命中的格子，而 `Y`/`M`/`W` 与筛选互不干扰（`set_photos` 不重跑，条件自然跟着走）—— **日历的
绘制逻辑一个字都没改**。

**但条件胶囊必须也摆到工具条上**（决策 9 的一半）：这一行占掉的就是网格页那条面包屑
（ADR 0033 决策 5），而筛选时用户看不到网格页 —— 胶囊只摆在面包屑上，就等于「加了条件却不知道
加了什么」。

### 9. 胶囊摆**年 / 月 / 周左边**，两处共用同一份胶囊

摆左边而不是右边：右边那一头就是分段选择器，而胶囊按录入顺序从右往左排开（ADR 0026 决策 4）
的话，最后几枚会**压在那三个按钮上面** —— 两组控件叠在同一处，而叠着的那一组是永远点不到的
那个（用户原话：「和相册视图一致的话会和这几个按钮重叠」）。

**与面包屑共用同一个 `ChipButton` 与同一份样式**（`breadcrumb.build_chip`）：两处各派生一遍，
过一阵就是「日历上那几枚比网格上那几枚浅一档」，而没人说得清哪一档是对的。两个控件接到
**同一个**处理函数上（`_on_condition_edited` / `_on_condition_removed`），所以「日历上撤掉了、
网格页上还留着」这种不一致不可能发生。

**宽度不够时收掉尾部那几枚，而不是把每一枚都压成省略号**：标题是「我在看哪一段」，条件是附注，
所以空间紧的时候先让附注让路。但「让路」**不等于按比例压缩每一枚** —— 压到尺寸提示以下时
`QToolButton` 会省略文字，于是长条件变成「拍摄时…1 ✕」，用户读到的是一条**不存在的条件**，
而点它撤掉的是另一条（症状与「删错条件」一模一样）。所以是「完整摆下前 N 枚 + 一枚 `+N`」。

**`+N` 按完整列表的序号点**：条件被点掉时走的是它在**完整列表**里的序号，所以收起来的那几枚
撤掉之后索引不会错位。

三个坑，都是实测出来的：

- **不能用 `QSizePolicy.Ignored` 让胶囊那一块让路** —— 它**丢掉尺寸提示**，布局于是给 0 宽，
  整块连同里面的胶囊一起消失（`geometry().width() == 0`）。附注要的是「最多占这么多、别再抢」，
  那是 `setMaximumWidth`。
- **那个上限不能在 `set_conditions` 里算** —— 它常发生在布局跑过之前，那时 `self.width()`
  还是 0，算出来是个 0 宽的上限（实测胶囊当场消失）。放 `resizeEvent` 里（顺带在那里重排，
  拖宽窗口时收起来的那几条要跟着回来）。
- **胶囊第一次吃到了工具条样式表的级联**：它自己的样式表里那几条是 `palette(text)` /
  `palette(mid)`，而工具条带着样式表 —— 按模块文档里记着的那个坑，`QStyleSheetStyle` 会给这一支
  塞它**自己那份**调色板，而工具条的样式表是在换外观**之后**才重铺的，于是胶囊可能照着上一次
  那份画。所以那条守护**量画出来的像素**（浅色与深色各一遍，下限 4.5:1），不量 `palette()`。

### 10. 摆胶囊的那一句要放在 `_update_breadcrumb` 的**每一个早退之前**

`:meth:`MainWindow._update_breadcrumb`` 有三条早退（点出来的那一格、没有库或无条件、整库检索）。
把摆胶囊写在**末尾**，就漏掉了「条件撤光」那一步 —— 而那一步正好走的是「无条件」的早退：

> 用户原话：「点击关闭似乎会先删掉第一个筛选，然后删掉第二个筛选，但是 UI 上第二个一直存在不消失」。

**症状之所以是「切到相册视图再切回来就好了」**：切视图会重走一遍没有早退的那条路，于是清干净了。
换句话说，那不是「偶尔不更新」，而是**每一条早退路径都漏，而绕一圈能绕过去**。

模型里条件确实是空的 —— 所以「量模型」的守护会一路绿。守护量的是**工具条上真的什么都没有**。

`+N` 那枚是 `QLabel` 不是按钮：摆的是数量，不是能点的东西，给它指针光标会让用户以为点得动。

### 11. `Esc` 只管位置；撤条件挪到 `⇧Esc`

**取代 ADR 0026 决策 9**（「`Esc` 分三种……否则才是撤掉最后一条，撤到 0 条才回到上一级」）。那一版把
条件排在文件夹 / 分组 / 日历那一格**之前**，理由是「条件又深一级」；后果是**只要有条件就永远退不出
位置**：

> 用户原话：「点开一个格子后，esc 退出一层就会清空一个筛选条件」（相册与日历**两边都有**）。

按 `Esc` 看到的是一条条件被撤掉而**位置纹丝不动** —— 而那两件事在屏幕上分不出来，用户会以为程序
卡住了。**退不动的时候也不顺手撤一条**：那与上面是同一个毛病（用户完全无法预期）。

**用户选定的是「改用别的键」**（而不是「先退位置、撤条件排在最后」）：`Esc` 纯粹退位置，撤条件
单独给 `⇧Esc`，两者彻底分开，绝不互相抢。菜单里「上一级」旁边多一行「撤掉最后一条筛选条件」。

三条随之而来的决定：

- **`_on_search_dismissed` 改走 `pop_last_condition`**，不再转给 `go_up`。搜索框那一处的语境是
  **条件**（它在筛选这一族的流程里），转给 `go_up` 会让「在搜索框里按 Esc」也变成「退一层」——
  而它在条件为空时本来就该什么都不做。
- **`⇧Esc` 那一行不限于网格页**：`⇧Esc` 挂在窗口上（`WindowShortcut`），条件是跨页的，在日历
  那一页也还在，所以它在哪一页都要能用。没条件时**关掉**，而不是按下去什么也不发生。
- **整库检索与在当前层筛选共用同一条 `go_up`**，所以两边一起挪 —— 只挪一半的话，用户在检索结果里
  按 `Esc` 撤一条条件、在日历里按 `Esc` 却退出那一格，而那不是「两种模式的心智不同」，是同一键两种行为。

**快捷键要单独钉一条**（发真实 `QTest.keyClick`，不是调方法）：方法在而键没挂上、上下文写错、或
被输入框先吃掉，症状都是「按了没反应」，而直接调方法的那几条照样绿。

### 12. 「正在改哪一条」不许粘住：**走开就是放弃**

> 用户原话：「在相册视图切到日历视图后再增加一个筛选条件会取代之前的筛选条件」。

**根因不是「切视图」** —— 试过四种顺序（相册→日历、日历→相册、经全部照片、一直待在日历），
只要不点胶囊，条件都加得进去。真正的原因是 `_editing_condition` **粘住**：

`_on_search_submitted` 按它分岔 —— 有它走 `self._conditions[editing] = …`（**就地替换，条目数不
增加**），没有它走 `append`。而**焦点离开输入框原先不清它**，所以：点一下胶囊正文 → 没接着改 →
去做别的 → 之后敲的每一条都在顶掉那一条。屏幕上只看得见「条件变了」，看不见「我刚才点过一枚胶囊」。

**三个「走开」的出口**，都汇到已有的 `_cancel_condition_edit`（不新造概念）：

| 触发 | 落点 |
|---|---|
| **焦点离开输入框**（兜底） | `_on_search_active_changed(False)` |
| 点网格空白处 | `_on_background_activated` 开头，与已有的 `is_renaming()` 早退同一理由 |
| 切换浏览方式 | `set_browse_mode` 里，排在 `_is_library_search()` 之前 |

三个决定：

- **兜底挂在 `editing_changed(False)` 上，而不是焦点事件上**：离屏下窗口拿不到真实焦点（实测
  `QTest.mouseClick` 在 offscreen 里不产生焦点切换），而 `focusOutEvent` 的**先后顺序**量不出来
  —— 一旦点胶囊本身被拆成「失焦 → 获焦」，功能会当场自毁。信号是「焦点已经离开」这件事本身，稳。
- **`_cancel_condition_edit` 里加一道闸**：没在改任何一条时**什么都不做**。兜底那条在失焦时也会
  调它，而那一刻用户很可能正在**输入一条全新的条件**（`_editing_condition` 是 `None`）——
  那时把输入框清掉就是凭空删掉他刚敲的字，**比原 bug 更糟**（它丢的是没确认的东西）。
- **日历工具条与网格页面包屑完全一致**：两处胶囊都是正文改、✕ 撤，接到同一个处理函数上。别为了
  「统一」把其中一处改成只读 —— 用户明确要两处都能改。

**放弃 ≠ 撤销**：放弃修改**不动条件本身**（胶囊原样留着）。它与「点 ✕ 撤掉一条」必须分开，所以
守护里每一条都同时断「editing 清了」与「条件还在」。

### 13. 条件只有三个下场，扫出来钉住

「除了点 ✕ 之外任何情况下不消失」这句话的**可查形式**：`test_only_three_things_can_take_a_
condition_away` 用 AST 扫出全仓库每一处改动 `self._conditions` 长度的写法，只允许那三样（点 ✕、
改这一条时回车替换、换库 / 切到整库检索）。

**为什么非要扫而不靠几条行为用例**：这个 bug 的形状是「某处 `_editing_condition` 粘住 → 下一次
提交静默替换」，任何一条行为用例都只能盯住**它已知的那几条路径**。新加一条「清条件」的路
（换作用域、换分组、回退到大图页）时，行为用例一条都不会红。

三个实现要点，都是实测出来的：

- **扫 AST 而不是扫文本**：文档里 `self._conditions[editing] = …` 这样的代码片段到处都有
  （写清楚为什么是「就地替换」就得写它），按行扫会把注释与 docstring 一起算进来 —— 那条守护
  第一次跑就抓到了我自己写的一段说明文字。
- **判据按「方法调用 / 赋值 / `del`」三类节点**：读（`for x in …`、`len(…)`）与改顺序的
  （`.sort()`）走的不是任何一支，天然不算。
- **清单本身也要看着点**：允许项被挪走或改名时那条断言会红，而不是悄悄放行。

## 后果

> **其中「`Esc` 只管位置」这一条已被 [ADR 0041](0041-the-level-stack.md) 补完**：本篇把条件
> 移出 `go_up` 时（「`Esc` 只管位置」，决策 11），**没有问「那 `Esc` 退出搜索由谁来管」** ——
> 答案是没人管。搜索结果「接管当前层」而它既不是文件夹也不是分组，于是
> `_can_go_up()` 恒为 `False`：搜索后直接按 Esc 能退出是**巧合**（那时焦点还在搜索框里，
> 走的是搜索框自己的 Esc），进一趟分组、焦点回到网格就没反应了。ADR 0041 把搜索结果变成栈上
> 一帧，那两条不用专门修 —— 它们是模型的结果。

- `core/library/search.py` 多一个查询与一个纯函数；`Library.matching_paths` 与
  `FacetIndex.match_paths` 各一条入口。
- `ui/window/search_flow.py` 多一组方法（`_start_level_filter` / `_on_level_filtered` /
  `_on_filter_failed` / `_cancel_level_filter`）与一个 `SearchFlowMixin` 上的状态判据。
- `ui/search_field.py` 多一个 `ScopeToggle` 与一个 `funnel()`（不新开顶层模块：它与胶囊共用
  同一套几何常量与样式来源，拆出去反而要把这些复制一遍）。
- `ui/calendar/toolbar.py` 多一个胶囊区与 `set_conditions()`；`breadcrumb._chip_style` 变成公开的
  `chip_style`，并多一个 `build_chip()`（两处摆胶囊的地方走同一个出口）。
- **日历那一页的工具条上多了一组胶囊**，这是这个需求在界面上唯一的新增控件。
- 监听器在有条件时**一律重跑**（与整库检索同一处）：真增量要逐张判断「新照片命不命中」，那
  还是得查索引，而 `_reload_level` 已经把整条链接通了。
- 日历上点开一格之后再加条件**退回日历页**（`_reload_level` 清 `_drill_photos`，与整库检索
  同一处理）：那一格的照片本来就来自筛过的桶，再筛一遍等于给同一条路径写第二套筛选逻辑。
- 测试：`tests/core/library/test_search.py`（真 schema + 无 LIMIT + 卡片判据的纯函数）、
  `tests/core/library/test_config.py`（作用域往返）、`tests/ui/test_filter_flow.py`（端到端）、
  `tests/ui/calendar/test_toolbar.py`（胶囊的位置、显隐、点击、可读性、撤光即消失、溢出收尾）。
  `tests/ui/test_external_button.py` 那两条让位的断言要跟着加上按钮那一份。

## 被否决的替代方案

| 方案 | 否决理由 |
|------|----------|
| 把范围写进 SQL（`p.path IN (...)` / 相册前缀） | 分组那一层的范围是算出来的，翻译不成谓词；`IN` 还要处理变量上限与分块（决策 2） |
| 给 `search_photos` 加一个 `scope` 参数 | 同一份代码要同时处理「返回一层」与「返回一份可相交的集合」两种形状，而后者不该带 `RESULT_LIMIT` |
| 另写一条「筛选专用」的收尾链 | ADR 0026 决策 7 已经点名：另写一条平行路径才是 bug 的来源 |
| 筛选时把相册卡片全收起来，只摆照片 | 用户就没法再往子相册里钻了；而「哪些子相册里有我要的东西」正是筛选要回答的问题之一（决策 3） |
| 相册卡片全部保留、不参与筛选 | 会出现「卡片里其实一张都没有」，得点进去看到空层才知道 |
| 条件也记进会话 | 条件是一次性的选择；跨启动记住一串条件只会让人莫名其妙（ADR 0026 决策 10 已经这么定过） |
| 两段式分段控件（搜索 \| 筛选） | 胶囊左边要多长一截，且两格共享圆角轮廓这件事要另写一遍绘制；一个可勾选按钮够用（决策 5） |
| 筛选时仍允许 ⌘V / ⇧⌘N | 粘进去的照片可能一条都不显示，而那是会动用户文件的操作（决策 7） |
| 条件用**另一种语法**区分搜索与筛选 | 用户要学两遍，而其中一遍是他不用的那个；两者的差别是范围而不是写法 |
