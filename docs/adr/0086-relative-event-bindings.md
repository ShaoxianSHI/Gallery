# ADR 0086：事件绑定按相对库根的键保存 —— 整个库搬走或复制之后关联还在

- 状态：已接受
- 日期：2026-10-24
- 修改：0043 决策 8 的「绑定按绝对 `path` 记」；0048 决策 1 的「封面存绝对路径」
- 相关 ADR：0028（相册封面存相对路径）、0038（东西只放两个位置）、0043（事件体系）、
  0048（事件封面）、0064（库文件被换掉时自愈）
- 相关代码：`src/gallery/core/paths.py`、`src/gallery/core/events/{schema,store}.py`、
  `src/gallery/core/library/{search,index,facade}.py`、`src/gallery/core/events/orphans.py`、
  `src/gallery/core/metadata/{journal,undo,rename,transfer}.py`

## 背景

事件本体（名称、日期、字段）跟着 `.gallery/events.db` 一起搬，但**照片与事件的绑定**以及
**事件封面**原来存的是绝对路径。于是把一个库文件夹挪到另一个位置（或复制一份）之后：

| 情形 | 原来的表现 |
|---|---|
| 旧文件夹已经不在 | 开库的孤儿检查把它们归进 `vanished` 一档（父目录 `ENOENT`，默认「先不清」）——数据还在，但新位置上这些照片不属于任何事件，封面退回第一张 |
| 旧文件夹还在（复制） | 完全静默：旧路径仍然有效，新副本的照片一张都没绑上，旧副本继续拥有这些关联 |
| 把文件夹搬回去 | 关联恢复 —— 数据没丢，只是路径对不上 |

应用内的改名、移动到相册、撤销，以及**应用开着时**监听器报上来的外部改名与移动，都走
`EventStore.follow_moves`（ADR 0043 决策 8）。「整个库根被搬走、应用没开着」这一条 ADR 当时就明确
排除在外，而它恰好是最常见的一种搬法。

这个决定可以借 ADR 0028 的原话：绝对路径「在库里挪个位置、换台机器就全废了」。相册封面早就是相对
路径，事件这边没有理由不一样 —— 尤其 `events.db` 本身就在库里，**相对库根**才是它天然的键。

## 决策

### 1. 库里存「相对库根的键」，读出来仍然是绝对路径

`ev.photo_events.path` 与 `ev.events.cover_path` 都改存 :func:`gallery.core.paths.library_key`：

- 库内路径 → 相对库根的 posix 串（`京都/海边-02.jpg`）；
- 库外路径 → 原样绝对路径；
- **前导 `/` 是分辨这两档的唯一判据** —— 相对键不会以它开头。

库外那一档不是设计的第二条路，而是给三样东西留的出口：旧库里的记录、撤销日志里的旧值，以及
`bind()` 这个公开接口。界面上的照片一律来自索引，一定在库内；所以正常使用不会产生库外键。
读取走 :func:`gallery.core.paths.path_of_library_key`，绝对键原样返回。

### 2. 转换只发生在 `EventStore` 的边界上，界面仍只看绝对路径

`Event` / `EventRef` / `Orphan` / `EventWriteOutcome.unbound` 仍然按绝对路径给出，`EventStore`
在读写 SQL 的两侧换算。这样 `groups.py`、`event_edit.py`、孤儿检查、缩略图流水线一个字都不用改，
也不会出现「同一个东西两套路径空间」散在十几个调用点上。

`events_for_photos()` 特别处理返回值：它按调用方传进来的那个 `Path` 对象作字典键，而不是把库里
读出的键直接拼回路径 —— 否则「同一个文件夹两种写法」会让 `refs[photo.path]` 静默取空。

### 3. 检索的 `EXISTS` 子查询带库根前缀，索引仍存绝对路径

事件条件原来写 `pe.path = p.path`，现在写 `p.path = ? || pe.path`，前缀由
:func:`gallery.core.paths.library_key_prefix` 算出（末尾一定带 `/`）。`FacetIndex.search()` 与
`match_paths()` 多一个可选的 `root`，由 `Library` 传入；没有事件条件时不必给，给了也不参与 SQL。

**索引里不改成相对路径**：那是可重建的缓存，而全应用（扫描、模型、缩略图、监听器）都以绝对路径为
主键。把索引也改成相对等于把这条转换扩散到每一层，收益却只是省掉一个前缀参数。

### 4. 封面跟着绑定一起改成键

ADR 0048 决策 1 选绝对路径的唯一理由是「封面与 `photo_events.path` 必须是同一套路径空间」。绑定一
改，封面必须同时改，否则两者连直接比较都做不到。封面的不变式（非空时必须是这次事件的一条绑定）与
解绑 / 孤儿清理时清空封面的做法都不变。

### 5. journal 也存键，撤销才跨得过搬家

删除事件时 journal 记的是绑定清单，编辑事件时记的是封面原值 —— 它们都住在 `.gallery/journal/` 里，
会跟着库一起搬。所以这两处也改存键；撤销时再换算回来。旧记录里是绝对路径的：

- 仍在当前库根下的，撤销时一并归成键；
- 指向旧根的（升级前就搬过的库），保持原样 —— 那与 ADR 0043 决策 8 排除的「应用没开着时的外部
  改动」是同一类信息缺失，不靠猜。

### 6. `follow_moves` 不变，但它现在搬的是键

应用内改名、移动、撤销以及监听器报上来的移动，仍然要在同一个事务里搬 `photo_events.path` 与
`cover_path`。目录那一支的 `LIKE '旧前缀/%'` 在相对键上同样成立（`京都` → `奈良`），所以实现只是把
旧 / 新路径先过一遍 `_key`。**整个库根改名**不需要它：键没有变，下次在新位置打开就指对了。

### 7. schema 升到 5：只 `UPDATE` 值，不重建表

`SCHEMA_VERSION` 从 4 升到 5，迁移步把**当前库根下**的绝对路径改成键：

```sql
UPDATE ev.photo_events SET path = substr(path, ?) WHERE path LIKE ? ESCAPE '\';
UPDATE ev.events SET cover_path = substr(cover_path, ?)
 WHERE cover_path LIKE ? ESCAPE '\';
```

（`substr` 用的是「库根前缀 + `/`」之后那一位；`LIKE` 的模式走 `core.sql.like_pattern` 转义。）
不重建表、不动事件与其余字段，符合 ADR 0048 决策 3 的迁移规矩；库外的绝对路径一条都不碰。

**不做「旧根推断」**：升级前就已经搬过库的库，路径指向旧根，无法可靠地与当前根对应。按公共前缀猜
旧根，猜错就是把关联绑到**另一张同相对位置的照片**上；宁可不修，让孤儿检查照旧把它们报成「相册不
存在」，由用户决定要不要清。以后若要做，另开 ADR 做成一次显式确认的「重新关联」，不在迁移里悄悄做。

### 8. 孤儿检查的三档不变

`all_bindings()` 读出来仍是绝对路径，`orphans.py` 的「目录可读 / `ENOENT` / 不知道」三档、默认
「先不清」的确认框、不记 journal 且不可撤销，全部照旧。移动整个库之后，键在新根下都指得对，孤儿
检查自然什么都找不到；真正的删除与未挂载的盘仍然分得开。

## 后果

- **整个库搬家、换台机器、复制一份**，事件与照片的关联都还在；复制出来的库是一个独立可用的库，
  两边不再争同一批绝对路径。
- **索引重建、清缓存、切库**仍然一个字节都不碰 `events.db`（ADR 0043 决策 1 的测试继续有效）。
- **不做的事**：网页里那种「重新关联旧路径」的界面、按内容哈希绑定、在索引里存相对路径。
- **已知边界**：应用开着时把库根整个搬走，监听器仍然看不见（它盯的是库根，不是父目录）；重启到新
  位置即可，关联不会丢。升级前已经搬过库的库不会被自动纠正（决策 7）。
- **回归测试**：`tests/core/events/test_relocation.py` 盯「存的是键」「移动 / 复制 / 检索 / 撤销跨得
  过搬家」「库外仍是绝对路径」；`tests/core/events/test_store.py` 盯 4 → 5 迁移只改值且不碰库外行。

## 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 在 `events.db` 里记「上次的库根」，开库时发现根变了就重写前缀 | 这是用户明确不要的方案。复制整个库时两份根都在，分不清关联该归谁；同一个库在两台机器上同步时还会互相改写。相对键没有「哪一份才是真的」这个问题 |
| 绑定按内容哈希记 | 一次绑定要读整个文件算哈希，而「记录为」是高频批量操作；ADR 0043 已否决过一次 |
| 保留绝对 `path`，再加一列相对路径作回退 | 两份真相源，每一次写入、每次改名、每次撤销都要保证两列同步；漏一处不报错 |
| 把索引 `photos.path` 也改成相对 | 索引是缓存，而全应用以绝对路径为主键；转换面从事件库扩散到扫描 / 模型 / 缩略图 / 监听器 |
| 迁移时按公共旧前缀推断旧根并自动改写 | 猜错就是把照片关联绑到另一张照片上。数据安全上，宁可留着 stale 行让用户看见 |
| 迁移时只改库内绑定，不改 journal | 删除事件后搬库再 ⌘Z，会把绑定恢复到旧绝对路径上；journal 会跟着库走，没理由不改 |
| 干脆禁止库外绑定（`bind()` 直接抛） | 撤销删除旧事件、公开 API 与旧记录都会撞上它；一条库外记录不该让整次撤销失败 |
| 把「相对 / 绝对」做成界面上的选项 | 用户不关心存储格式，而两套模式意味着两套测试与两套失效路径 |
